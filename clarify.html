管理者分工與最小權限

App access（應用程式使用權）回答「這個帳號是否能使用某個應用程式的功能」；管理角色回答「是否能修改某個範圍的設定」。專案瀏覽與工作項目安全性則回答「能否看某份資料」。這三個問題要分開檢查。

例如，一名管理者可以負責組織的人員安排，但某張敏感工作項目仍受專案權限與安全性等級限制。不要把組織管理者畫成所有工作項目內容的自動讀者。另一個方向也一樣：能閱讀和更新任務的Member，不代表有權編輯共用工作流程。

目前介面還會出現Site admin、User access admin與App admin等名稱。它們用來理解操作入口與分工，不表示April 2025的三種核心考綱角色被自行擴寫成新的考試領域。面對題目，先用題目明確提供的角色與能力作判斷。

工作類型與方案：讓每種工作走對設定

對公司管理型的一筆 Bug，先看專案使用哪些方案，再以工作類型找對應。工作流程方案（workflow scheme）決定 Bug 使用哪個 workflow；這條線管理狀態、轉換與規則。

畫面線有兩層：工作類型畫面方案（issue type screen scheme）將 Bug 對應至某個 screen scheme；screen scheme 再把 Create、Edit、View 操作對應到 screen。Screen 裡才列出欄位與分頁。

把欄位加進某個看似名稱正確的 screen，若對應鏈沒有走到它，使用者就不會看到預期結果。

傳統欄位設定線則由 field configuration scheme 將 Bug 對應到 field configuration，後者定義必填等欄位行為。這與 custom field context 的適用專案／類型、預設值／選項不同；第 3.2 課會把它們接起來。

找不到明確類型對應時，要檢查該方案的 Default 對應，而不是直接假設類型没有任何設定。新類型新增後，測試「Create 看什麼、Edit 能填什麼、走哪些狀態、有哪些必填要求」比單看清單更完整。

版本提醒：現行 Jira 正逐步把 field configuration 與 field configuration scheme 合為 field schemes。考綱沿用傳統兩層術語；若實際站台已顯示新名稱，先辨識使用哪種經驗，再按目前官方說明查看欄位可用性及必填設定。

不要硬找已不存在的舊選單。

工作類型與方案：讓每種工作走對設定

Time tracking 至少要分辨 Original estimate（原始估算）、Remaining estimate（剩餘估算）與 Time spent（已登錄工時）。父工作可以有自己的工時；子工作也可以各自記錄。查看彙總時，並不是把所有子工作的 worklog 複製到父工作。

合成資料：父工作自己已用 1 小時、剩餘 2 小時；子工作 A 已用 2 小時、剩餘 1 小時；子工作 B 已用 3 小時、剩餘 4 小時。若畫面選擇 Include subtasks，已用合計為 6 小時，剩餘合計為 7 小時。父工作本身仍是已用 1、剩餘 2；報表的 Σ 類欄位代表加總口徑。

不要把「父工作估算 7 小時」再加上已包含同一批工作內容的子工作 7 小時，誤以為真正有 14 小時工作。先約定父工作自己記錄的是額外協調時間還是整包工作的估計，並在閱讀報表時標明是否含子工作。

本段只談時間追蹤。Story points 是另一種估算尺度，不能因為工時會彙總，就推論所有 Scrum 報表的 Story points 都以相同方式加總；也不能把 Epic、父工作及 subtask 的各種報表口徑混為一談。

工作類型與方案：讓每種工作走對設定

團隊管理型專案由專案管理者從 Space settings／Project settings → Work types／Issue types 管理本地工作類型。不要照抄公司管理型的全域 issue type scheme 教學路徑。

新增類型之後，還可以調整它的欄位與 workflow，讓 Bug 與一般 Task 蒐集不同資訊、走不同程序。

模板是起點：文件列出的初始 Kanban 類型是 Task，Scrum 是 Story，但這不是「Kanban 不能有 Story」或「Scrum 不能有 Task」的限制。先依團隊語言和需求選分類，再設計流程，避免為了模板名稱扭曲實際工作。

同名不代表同一個管理物件。兩個團隊管理型專案都有 Bug，不足以證明它們共用欄位、workflow 或工作類型本體。診斷時需要確認專案管理型態與物件來源；第 3.2 課再說明本地欄位與目前可重用的 Jira-admin shared fields。

目前 team-managed 官方文件限定自行建立的是 standard work type；若需要 Epic 或 Subtask 的特殊功能，應新增其建議的內建類型，不要另造一個同名的普通類型來假扮。名稱相同不會自動帶來階層、board 分組或進度功能。

工作類型與方案：讓每種工作走對設定

在文件查核的現行建立方式中，先開啟要拆分的父工作，選摘要下方 Add or create related work，再依管理型態選 Create subtask 或 Add a child work item，填摘要與必要欄位。

公司管理型若沒有選項，查 subtasks 是否啟用、類型是否在專案方案中，以及 Create work items 權限；團隊管理型則查專案是否已有 Subtask 類型。

Scrum 的公司管理型 backlog 可開 Epic panel，建立 Epic，再把標準工作放入相應成果；也可由全域 Create 選 Epic。

Kanban 也有這些用途，但該 board 的 backlog 和 Epic panel 要先啟用，不能因 panel 沒出現就斷言 Kanban 不支援 Epic。團隊管理型也可從全域 Create 或已啟用的 backlog 建立 Epic。

連到 Epic 的目前欄位常叫 Parent；較舊 Kanban 文件仍可能寫 Epic Link。從 Epic 移除一筆工作的父子關聯，不等於刪除那筆工作。若文件另談 Epic Status，要與一般 workflow Status 分開理解；

一個 Epic 的彙整狀態也不能證明所有子工作已經過合法完成轉換。

工作類型與方案：讓每種工作走對設定

本課用 Epic → standard work item → subtask 當初學者的常見模型，幫助你分清成果、工作與執行拆分。這個模型不應被背成所有 Jira Cloud 版本都永遠禁止其他支援的關聯。

查核日的 Create a work item and a subtask 官方文件另明列：company-managed software 可使用 Add parent 將 subtask 直接連到 Epic 層。

相對地，team-managed 的 subtasks 官方文件仍明列 subtask 建在標準工作之下，不能直接置於 Epic 層之下。這是管理型態與現行產品差異，本課原創題目不以未交代版本的絕對禁止句設陷阱。

目前 team-managed Epic 文件也要求 parent 關係維持相同管理型態：company-managed 工作對 company-managed parent，team-managed 工作對 team-managed parent。跨專案與跨管理型態是兩個不同問題。

正式操作前仍需核對站台提供的入口和權限，不在正式資料上用試錯方式探索。

欄位與 context：讓資料可用、可填、可比較

Context 像是欄位的使用範圍與內容規則。它能限定專案、工作類型，並針對範圍提供選項與預設值。Global context 表示廣泛適用；專案限定的 context 則讓同一欄位在某些專案使用特定設定。

合成例：共用的「作業區域」欄位，在 WEB 專案提供 Checkout、Account，在 STORE 專案提供 Counter、Kitchen。兩個 context 都使用同一個欄位，因此報表可依同一欄位查詢，但選項不必強迫全站使用一大串不相關清單。

規劃 context 時，列出「哪個專案 × 哪些類型 → 哪些選項 → 預設值」。避免給同一範圍含糊或重疊的規則；若畫面不允許某種重疊，要改規劃，而不是假設多個 context 的值會一起合併。檢查既有 global context 也很重要，否則只盯新 context 容易漏掉真正使用的範圍。

Context 名稱是管理者辨識用的，不等於使用者會看到另一個欄位名稱。設定預設值是在支援往後的資料輸入，不是已驗證的歷史資料回填方案。若要改既有值，另做資料影響分析與授權過的變更計畫。

Context 有效不等於欄位一定出現在每個操作畫面。公司管理型還要檢查 screen 與欄位行為；team-managed 要檢查該 work type 的欄位安排。這是第 3.3 課排錯流程的起點。

欄位與 context：讓資料可用、可填、可比較

Screen 或 layout 是呈現設定。把一個欄位從某個畫面移走，只能證明那個畫面不再提供原本的呈現；不能據此保證其他檢視、匯出、搜尋或整合都看不到資料。不要把「我在目前頁面看不到」當作已通過存取控制測試。

合成例：你想把人事評語從一般 Task 旁邊藏起來。正確的下一步是回到權限與工作項目可見性的設計，而不是承諾拖到 Hidden 就能安全保存機密。這裡說的是安全設計邊界，並不假裝本課已測試所有欄位的 API 行為。

如果遇到 Required 卻無可用輸入位置，先沿 context、field configuration、Create screen 檢查，不要單靠 UI 出不出現推論資料已有效。實際錯誤訊息與租戶配置才是定位依據。

欄位與 context：讓資料可用、可填、可比較

團隊管理型專案可以在專案內新增本地欄位，再把它拖入所需 work type 的欄位配置。已在同一專案其他類型建立的欄位可重用；重用同一欄位時，它的名稱與選項是共用資料定義，不能假設每個 work type 都得到獨立副本。

本地新建欄位通常限定該 team-managed 專案，不可因為別的專案也取同名就當成跨專案共用。若組織需要一致欄位，現行文件另提供重用 Jira 管理者建立之 eligible shared field 的方式。

先查 Add fields 是否列出該欄位，以及來源是否為 Jira-admin 管理的欄位。

官方 context 文件明確指出：要在 team-managed 使用欄位，其 context 的 work type 選擇必須包含 Any work type。還要檢查相關專案範圍、支援的欄位種類與當前功能；不能把 Any work type 當成單一充分條件，保證任何欄位都出現在任何專案。

版本釐清：目前同一篇 team-managed fields 文件同時包含新版的管理者欄位重用步驟與較舊的不可跨管理型態共用句子。本課採「本地欄位保持本地；合資格的全域管理欄位按 context 與可用介面查核」的精確說法。

考題若問某個實際操作，本教材會明列欄位來源與條件，不出以矛盾敘述猜答案的題目。

欄位與 context：讓資料可用、可填、可比較

April 2025 考綱使用 field configuration 與 field configuration scheme 兩個術語。現行官方文件說明 field schemes 正逐步取代兩者，把欄位可用性、不同類型的必填與說明整合在一處。

因此本課的概念學習要保留兩個問題：「哪個欄位可在這種工作使用」以及「欄位在此處有何行為」。如果你的租戶已切換 field schemes，以新介面查它；context 仍有選項與預設值的角色。不要把新 field scheme 與原本 field context 當作同義詞。

這是產品版本對照，不是自行宣告考綱已更新，也不要求你背誦尚未在租戶出現的按鈕。實際工作先核實介面版本，再參照當前官方頁面。

Screen 與 layout：把資料放在正確的操作位置

讀取順序是「專案 → issue type screen scheme → 指定 work type 的 screen scheme → 目前操作的 screen」。每一層都是對照表，不能省略。

例子：REPAIR 的類型畫面方案把 Bug 對應 Bug screens，把 Task 對應 General screens。

Bug screens 中 Create 使用 Intake screen，Edit 使用 Diagnosis screen，Default 使用 Detail screen。建立 Bug 走 Intake；編輯 Bug 走 Diagnosis；

沒有明確設定 View 時，走 Default 的 Detail。

兩種 Default 也要分清楚。類型畫面方案的 Default 是「沒有明確類型對應時用哪個 screen scheme」；screen scheme 的 Default 是「沒有明確操作對應時用哪個 screen」。同一個字放在不同層，處理的是不同缺省情況。

Transition screen 是 workflow 上的另一路輸入點。例如「關閉」時要求 Resolution、檢查結果，不應只靠 Create/Edit/View 的 screen scheme 推論；要查該 transition 上是否要求顯示畫面。

Screen 與 layout：把資料放在正確的操作位置

團隊管理型從專案 Work types 選 Bug、Task 等類型，加入或拖動欄位，決定每種工作所需資訊。這裡不是先建立公司管理型 screen scheme；管理者應使用該管理型態提供的編輯介面。

合成例：Bug 放「重現步驟」「實際結果」，Task 放「預期交付物」。需要共用「作業區域」時，重用同一專案已建立的欄位，或依 3.2 的條件選 eligible admin-created shared field；不要為排版方便就建立一堆同名副本。

把某欄位從 work type 配置移出，與刪除欄位本體是不同決策。移除前仍應查資料、報表與 automation 的使用方式。若欄位在同專案多個類型共用，變更其名稱或選項可能一起影響其他類型；移動顯示位置則是另一種設定責任。

實際介面會隨欄位管理新版本更新。教學操作先確認 Space settings 的 Work types／Fields 顯示方式，再讀當前官方頁面；不要用舊截圖上的像素位置當必要知識。

Screen 與 layout：把資料放在正確的操作位置

第一步，界定症狀：誰在哪個專案、哪個 work type、哪個操作看不到哪個 field？若只有一位使用者的 Create 缺欄位，先檢查個人 Show fields／All fields；這比立刻修改共享 scheme 的風險低。

第二步，確認 field 身分與 context。名稱相同可能選錯欄位；context 不包含目前專案或類型時，要處理適用範圍。第三步，檢查 field configuration／field scheme 是否允許可用、是否隱藏或有必填要求。

第四步，沿兩層畫面方案找到真正的 Create/Edit/View screen，而不是只找名稱包含專案名的 screen。第五步，若是詳細頁問題，再檢查 layout 的 Hidden、Hide when empty、欄位空值以及共享 View screen。

最後，以原本受影響使用者及一筆合成資料重新驗證相同操作。若問題是權限或特殊欄位限制，按錯誤與官方規則另查；不把「多加到幾個 screen」當成萬用解法，也不把 screen 當成保護所有資料的防線。

公司管理型 workflow：從狀態、規則到正確結案

合成「Approve」轉換從 Review 到 Done。先用 condition／Restrict transitions 判斷目前這個人是否能使用，例如只准 Reviewer 角色。這是可用性檢查；在典型舊編輯器中，條件不成立時使用者不會看到轉換按鈕。

若需要當下補資料，可以設定 transition screen／Request input，要求填驗收紀錄或選 Resolution。畫面提供輸入機會，但「畫面上有欄位」本身不保證每條呼叫路徑都送入合法內容。

Validator／Validate details 檢查轉換前資料是否合格，包括剛在 transition screen 填的值。若驗收紀錄空白，validator 可拒絕完成。使用者可能看得到按鈕、開得了畫面，卻在提交時收到錯誤；這與 condition 的典型表現不同。

Post function／Perform action 則在轉換執行後處理附帶更新，例如設定 Resolution。Validator 失敗時，不應期待目的狀態或完成後動作照樣成功。設計時把「必須先滿足」放在檢查層，把「通過後寫入」放在動作層。

記憶方式不是背四個英文順序，而是問目的：「誰可以？」偏限制；「現在收什麼？」偏輸入；「輸入有效嗎？」偏驗證；「成功後改什麼？」偏動作。這是概念順序，不是允許你任意改動所有內建 post function 的系統執行順序。

現行 advanced workflow 文件特別警告：保留必要的 Generic event post function，不要修改、刪除或任意重排必要系統步驟。需要自訂事件時，依目前支援方式另外新增自訂 post function；

較舊事件教學若示範修改既有 Fire a…，不能直接視為現行流程的安全步驟。

公司管理型 workflow：從狀態、規則到正確結案

Workflow 決定合法狀態與轉換；board 將查詢到的工作按狀態映射到 column。多個 statuses 可以放進同一欄，例如 Testing 和 Review 都放在「驗收中」。因此 column 數量不必等於 status 數量。

如果某個 status 沒有映射到 board 欄位，相關工作可能在此 board／backlog 消失，卻仍能透過搜尋找到。先確認 board filter、權限與 status mapping，不要把沒顯示誤當成資料刪除。

Scrum board 的完成判斷尤其要查最右欄。即使狀態叫 Done，若沒有映射到代表完成的最右欄，sprint 結束時可能被當成未完成。Kanban 的欄位映射也影響呈現與流動；特定 backlog、子篩選與隱藏完成工作設定另查相應功能。

將 Review 從一欄重新映射到另一欄，是改 board 呈現；把一筆工作從 Review 轉到 Done，是改工作狀態。兩者不能混為一談。

若使用 simplified workflow，部分 board 管理動作會連帶建立狀態，這是有條件的整合行為，不能當成所有公司管理型 workflow 的規則。

公司管理型 workflow：從狀態、規則到正確結案

重新開啟不是只把 Done 改回 In progress。完成原因應被清除，讓依 Resolution 判斷的功能也恢復未解決口徑。舊編輯器可見 Clear Field Value post function；

現行 Edit a workflow’s rules 文件則說明以 Update a work item field 的 Perform action 在重新開啟路徑清除 Resolution，並確認順序正確。實際空值選項依租戶介面查核。

合成完整路徑：Review → Complete → Done 時設定 Fixed；Done → Reopen → In progress 時清除 Resolution。若有 Done → Rework 與 Done → Reopen 兩條不同路徑，都要檢查清除邏輯。

JQL 從一句需求寫出可驗證的搜尋

AND比OR先結合，完整優先序是括號、比較、NOT、AND、OR。官方進階搜尋概覽有一句簡化的left-to-right，專門Cloud優先序文件則明確列出上述順序。本課採專門文件，並以括號明示意圖，避免靠語感解讀長條件。

需求「LAB內，指派給我或還沒有人接手」應寫project = LAB AND (assignee = currentUser() OR assignee IS EMPTY)。

若漏括號，project = LAB AND assignee = currentUser() OR assignee IS EMPTY會等同(project = LAB AND assignee = currentUser()) OR assignee IS EMPTY，於是其他專案的未指派工作也可能進來。

用三筆合成資料手算：LAB-1由我承辦、LAB-2未指派、DOC-1未指派。正確括號式回傳LAB-1與LAB-2；漏括號式還多DOC-1。這不是搜尋引擎亂抓，是你把最後一個OR放到整體範圍。每次改括號都應用至少一筆「應該入選」與一筆「不該入選」的反例驗證。

JQL 從一句需求寫出可驗證的搜尋

要查2026年9月建立的資料，先指定時區，再用created >= "2026-09-01" AND created < "2026-10-01"。這個半開區間包括9月1日午夜，也包括9月30日任何時間，但不包括10月1日午夜。

比寫「<= 9月30日」更不容易漏掉最後一天，因為沒有時分的日期按午夜解讀。

相對時間與日曆邊界不同：created >= "-7d"是相對執行時間往前七天；created >= startOfDay("-7d")從七天前的日開始。若現在是15:00，兩者下界可相差15小時。

要查昨日全天，使用created >= startOfDay("-1d") AND created < startOfDay()。

日期與時間搜尋依設定時區解讀。跨地區團隊應先約定用哪個時區，再評估邊界資料。不要將due純日期的概念和created日期時間混在一起，也不要靠畫面顯示的年月日推斷UTC時刻。本課時間題會把時區與精確資料完整給定。

只寫created >= startOfMonth()是本月起至目前存在的符合資料，不等同一份永遠固定的月報。要重跑歷史報告，保存明確起迄日期；要每日自動更新視圖，才使用相對函式。這是查詢設計目的的選擇，不是語法誰比較高級。

篩選器 儀表板與訂閱 共享方法不等於共享資料

建立群組訂閱需Manage group filter subscriptions全域權限，且建立者只能選自己所屬的群組。群組名出現在公司通訊錄不代表它就是可選的Jira群組；外部郵件群組別名也不是同一機制。

Jira群組訂閱的查詢結果對每位收件者計算。若filter是assignee = currentUser()，寄給測試員甲時currentUser是甲，寄給乙時是乙，不會全部沿用建立訂閱者。每人的可見資料也可能不同，所以「全群組收到同一個filter」不等於收到相同列表。

合成例：LAB-1由甲承辦、LAB-2由乙承辦，兩人都能讀這兩筆。對assignee = currentUser()的群組訂閱，甲得到LAB-1，乙得到LAB-2。若改用固定assignee值，才是在查固定人員；若以一個信箱帳號接收後再外部轉寄，不能聲稱Jira會在轉寄時替每位成員重新執行。

群組越大，每人各跑一次查詢的成本越高。適合有共同清單用途、範圍清楚且頻率合理的群組；不適合為了提醒單一事件就每分鐘把大查詢寄給全站。此處是營運設計建議，並非額外考綱的新技術功能。

篩選器 儀表板與訂閱 共享方法不等於共享資料

建立自己的dashboard與分享給別人是不同能力。分享首先檢查Share dashboards and filters全域權限；現行官方Cloud分享KB也要求Browse users and groups，這讓使用者能在分享欄位查找人或群組。

舊文件的Create Shared Object名稱常對應這類分享能力，閱讀時要對照現行名稱。

還要有權管理該filter或dashboard的分享，不能因全域可分享就任意改別人的物件。Viewers和Editors應按用途分開：只看報表的團隊給viewer，少數維護者才給editor。若找不到群組，先查可見性與全域能力，不要改成public來繞過。

即使同時能開dashboard與filter，每一筆工作仍依讀取者的Browse與安全層級過濾。合成案例：主管看見18筆、同事看見12筆，不必先認定gadget壞了；先用同一filter比較權限範圍，再檢查JQL中currentUser()。報表共享本身沒有授予額外資料權限。

批次操作與搬移 先預測資料變化再確認

Team-managed與company-managed有不同的設定模型。官方沒有把team-managed直接切成company-managed的原生開關；先准備目的專案，再搬移工作。Scrum或Kanban都需要檢查目的board與workflow，不能把方法名稱當成資料相容保證。

由company-managed搬到team-managed：component與version資料會遺失，即使搬回也不能恢復；有些全域自訂欄位值可能仍存於背景，但沒有對應到目標的本地欄位，所以看起來空白。看不到值與值已刪除是不同情況，不得統稱全部都會保留或全部都會消失。

反向搬移時，需準備company-managed的work types、workflow、欄位context與screens，以及permission scheme。team-managed自訂欄位不能只靠同名就期待自動保留；官方要求重建與配置。

Story points和Story point estimate是不同欄位，估算資料與Velocity／Burnup歷史不能假設會轉移。

安全規劃是在隔離、已授權環境以合成資料驗證，列出每種資料的保留、轉換與不可恢復狀態。禁止把正式專案來回搬一次當驗證：對component和version，搬回不是復原機制。需要回復能力時先設計經驗證的備份與復原計畫，而不是只保留舊連結。

批次操作與搬移 先預測資料變化再確認

先選目的專案與work type，它們決定目的workflow及欄位模型。來源的Review狀態若在目的流程不存在，需選相當狀態，例如In Progress類別的Validation。不要只按字母或畫面順序配到Done，否則團隊會誤認已完成。

目的必填欄位沒有來源值時，要提供合理值；若UI支援Retain，需核對欄位名稱、型別與實际支援條件。兩個叫Region的欄位不一定同ID或同context，不能只看名稱就保證值已對應。搬移確認頁逐欄檢查的是資料轉換，而不是單純搬資料夾。

父工作有subtasks時，子工作也需搬到目的專案；需把階層與目標類型納入計畫。搬移後key通常改成目的專案key，舊連結可自動導向，但board filter、依專案key寫的JQL與自動化範圍仍應重查。保留可追溯的來源key及目的key清單比假設所有周邊設定自動更新更可靠。

全站預設值與介面 先分清影響誰

Look and feel位於System的User Interface區。它涵蓋logo、站台title、favicon及部分色彩設定；色彩需檢查深色主題的可讀性。網站識別圖不是專案logo；改全站logo不會替每個工作項目添加分類或改權限。

日期格式也要按適用範圍理解。現行文件指出某些格式設定適用calendar和timeline，其他功能可能依語言偏好。時區決定日期時間顯示與解讀，格式決定長相，二者都不是改寫工作項目真正建立時刻。

管理者提出「全站日期顯示一致」時，先問是顯示格式、語言還是時區，再挑正確層次。不要因為看見Yesterday就去改資料日期；相對日期顯示與實際儲存時間可同時存在。

全站預設值與介面 先分清影響誰

Settings→System→Default dashboard可新增gadget與Edit Layout；預設dashboard不能刪除。其viewer範圍目前可選My organization或Public，不能像一般dashboard任意指定某一群組、專案或個人。

gadget能否看到還受使用者權限影響，例如Administration gadget不會對非管理者顯示。資料型gadget也可能依底層filter與工作項目可見性產生不同結果。放在「全站入口」不代表需要授予每人全站資料權限。

附件 工時與連結 三種功能的層次排查

App navigator加入名稱與URL，是讓人更容易去某個網站；可依群組顯示或Hide。隱藏捷徑不會取消目的站權限，顯示捷徑也不會讓本來沒權限的人登入。各應用的導覽可見性可能需分別設定。

AppLinks則是讓應用之間交換資料或整合功能，例如在Jira看相關開發資訊；牽涉認證、遠端帳號權限及連線條件。OAuth流程與可能的持續存取必須由有權人員核准，本課不會建立認證、開網路或輸入憑證。

需求「在選單加公司手冊入口」通常是navigator link；需求「從Jira讀取另一Atlassian應用的相關資訊」才要評估受支援整合／AppLink。某些AppLink會自動出現在navigator，但這不表示兩種設定相同。

例如LAB-1 blocks LAB-2，從LAB-2看就是is blocked by LAB-1。Link type同時有Name、Outward description、Inward description；它們說明方向，不是建立兩條互相重複的關係。設定錯方向會讓依賴閱讀與JQL判讀混亂。

狀態 結案原因與優先順序 共用值的治理

Team-managed的status可被同一專案的多個work type workflow共用。從Space settings→Work types→Edit workflow更名或改category時，如果是共用status，會更新該專案其他使用它的workflow。

不要把team-managed理解成每種work type完全獨立、永不共用。

若需求只改目前workflow，現行文件提供在「This status is shared across multiple workflows」警示下使用「Change status for these work items only」。

這會複製status及其transitions和rules供目前流程使用，再Update workflow確認適用work types。這條具體分支與直接改共用名稱不同。

新增status也要對應到board column；預設未對應的狀態不會在board顯示。工作仍存在不等於每張board都會顯示它。更名、改category、刪除status和移除board對應是四種不同影響，應分別測試，不把「board看不到」當成工作刪除。

狀態 結案原因與優先順序 共用值的治理

Subtasks預設可用；在Settings→Work items→Subtasks能管理這類型態。官方要求停用前先把現有subtasks轉成standard work types。這表示「從今天不想再用子工作」仍牽涉舊資料，不能假設按Disable就保留全部原階層且只禁止新建。

轉換要先核對目的standard類型的workflow、欄位與關係，也要檢查依賴subtask狀態的父工作blocking condition，以及自動建立subtasks的automation。若資料轉換未完成，先不要執行全站停用。刪除某個subtask類型與停用整個subtask能力是不同範圍。

合成規劃：LAB有兩筆仍在進行的子工作、DOC沒有。必須先列出兩筆的轉換目的與原父工作追溯方式，再請負責人確認；不能因DOC沒用就認為全站可直接停用。這個檢查也適用其他共用功能：先盤點使用者與資料，再談關閉。

備份與匯入 先辨識工具再談還原

第一種Restore是Archive清單中的解除封存：它讓現有站台的專案恢復使用，不是讀取備份。封存不會刪掉共享workflow與scheme，工作會離開一般搜尋，但原本有權的人仍可能透過直接連結查看且不可編輯。封存不是安全性封鎖，也不是備份。

第二種是Server／Data Center XML匯入Cloud。官方紀錄JRACLOUD-81072描述來源先封存、再匯出Server XML並匯入Cloud後，目的專案變未封存。這是明示來源平台與工具的已知案例，不能擴張成任何Cloud備份都會取消封存。

第三種是Cloud-to-Cloud Copy Data。CLOUD-12072記錄此路徑的封存專案在目的站變未封存。第四種JCMA則有官方遷移指引說可在Cloud的Archived projects查看與restore遷移的封存專案。兩種工具不能互相覆蓋對方的資料；要看記錄描述的確切路徑。

第五種新Atlassian Backup and Restore的支援表明列Archived projects，表示它包含封存專案這類資料；表格沒有明說所有還原後archive旗標。

第六種Cloud來源Backup Manager完整備份經Import Jira Cloud還原：本次讀取的直接官方資料仍未確立archive旗標究竟保留或取消，也未證實「匯出前必須先解除封存」。

所以這裡的正確管理能力包括說清楚未知範圍。不能把舊site-import網址轉向JCMA後的內容當成原XML機制的證據，也不能用Server XML或Copy Data的已知問題替Cloud Backup Manager猜唯一答案。

若正式遷移必須保證archive狀態，應先取得針對此路徑的官方確認或在隔離授權環境驗證。

備份與匯入 先辨識工具再談還原

一般專案管理者不是整站備份／還原操作的當然執行者。管理者CSV匯入文件要求Jira administrator；但全域權限頁又明確表示單獨Administer Jira不涵蓋整站import/export。不要把CSV與整站XML兩種動作混成一張權限表。

對傳統Backup Manager／Import Jira Cloud，應由負責站台資料管理的組織／站台管理人員確認當前管理介面中的實際可用權限與政策。已讀現行匯出／匯入頁未完整列出所有集中式與原始管理介面的最低角色組合，因此本課不編造「只要某群組名稱就一定可以」。

已確立的是：僅能管理專案或僅有Administer Jira，不能作為整站備份權限已驗證的證據。

新Atlassian Backup and Restore FAQ則明確要求organization admin加app admin。還原後app access可能涉及帳務，文件要求再確認才套用。組織也能封鎖匯出；看到按鈕或持有某個稱號不能繞過資料政策。

正式計畫應記錄來源讀取、目的覆寫、匯出限制與執行者的能力，缺一項就停止。
