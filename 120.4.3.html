Automation：用事件、條件、範圍與執行身分推導結果

先理解用途，再判斷設定與結果。

官方目標 4.3 · 來源內容版 2026-10-05.complete-draft

閱讀前提

知道 work item、work type、status、parent／subtask 的基本關係。

理解能看到工作與能編輯或轉換工作是不同權限；本課會把 actor 的權限重新接到流程。

先認識名詞

Automation rule / flow：由事件啟動，按條件執行一連串動作的自動化；現行文件常稱 flow。

Trigger：啟動一次規則執行的事件或時間，例如工作建立、狀態轉換、排程、手動啟動。

Condition：決定是否繼續或走哪條路的判斷；本身不等於修改工作。

Action：規則實際做的事，例如寫入欄位、轉換工作、加入紀錄。

Branch：把後續處理切到相關工作，例如 parent、subtasks、linked work items。

Smart value：以雙大括號讀取規則執行中的資料，例如 {{issue.key}}。

Actor / owner / initiator：Actor 執行動作；owner 負責規則；initiator 是觸發事件的人。三者不必相同。

JQL：Jira Query Language：以欄位、運算子與值找出符合條件工作的查詢語法；查詢本身不修改資料。

先描述要減少的重複工作，再拆成規則

合成團隊每當子工作完成，都要打開父工作、檢查其他子工作、再決定父工作是否能完成。如果交接頻繁，人容易漏查。Automation 能把這段一致且可驗證的流程交給系統執行，但它需要明確規則，不能只寫「幫我處理好」。

把需求改寫成：「當一筆 Subtask 轉到完成類別時，檢查它的父工作；只有當全部 subtasks 都完成、父工作還沒完成，才走父工作合法的完成轉換。」這句話已包含 trigger、相關工作範圍、condition 與 action，也揭露必須另查 actor 權限。

本課先用紙上資料和只寫合成值的 Log action 推演。不要一開始就用真實客戶工作測試大量編輯、外部通知、刪除或跨專案動作。先把一次執行說清楚，再逐步擴大。

Project scope 與 global scope：可處理的地方，不是無限權限

Project rule 只在指定專案範圍運作。Multi-project rule 適用明列的多個專案；Global rule 可能涵蓋整個 Jira 站台。某些現行介面也有依專案類型等範圍；核心概念都是先知道規則允許在哪些地方作用。

合成例：DEV 的 Bug 完成後，要更新 OPS 中一筆 linked Task。只把 OPS 工作的 key 寫進 smart value 或 JQL，不會自動擴大單專案規則範圍。應先選擇包含 DEV 與 OPS 的適當 multi-project scope，且 actor 在兩邊都需具備相應能力。

規則管理權與執行權分開。專案管理者通常可管理本專案 automation，Jira 管理者可管理全域層設定；全域設定也可以限制專案管理者的自動化管理能力。所以某人是 project admin，仍不一定能建立任意跨專案規則。

Global scope 不會讓 actor 跳過 Browse、工作項目安全性、Edit 或 Transition 權限。範圍回答「這條規則設計上涉及哪裡」；權限回答「這個 actor 能對這筆工作做什麼」。兩者缺一，都可能使預期動作不成立。

選最窄且足夠的範圍是本課建議。把兩個專案的需求直接做成全站規則，會擴大誤觸發與維護風險。實際使用量與方案限制會更新，上線前查當前方案文件；本課不以易變額度數字作記憶題。

規則由哪些零件組成，執行一次時怎麼讀

Trigger 是起點，告訴系統什麼時候開始。手動 trigger 適合隔離測試；建立、欄位變更、轉換或排程等 trigger 用來表達真正事件。Trigger 選錯，即使後面動作完全正確，也可能一直不跑或過度執行。

Condition 用來篩選本次是否符合需求。一般 condition 不成立，後續那條處理路徑就不往下做；這可能是正常結果，不必當成故障。例如只處理 Bug，但觸發的是 Task，正確行為可能就是不更新任何工作。

Action 才是修改或輸出的步驟，例如 Edit work item、Transition work item、Log action。Action 的順序必須和資料依賴一致；若前面尚未確認對象或內容，不應先發通知或覆寫欄位。

Branch 讓後續元件改針對另一筆相關工作執行。它不是一般 if/else 的同義詞：if/else 選處理路徑，related-work-item branch 換目前處理的工作。兩者可以出現在同一條規則，但應分開閱讀。

Rule details／Settings 還有名稱、說明、owner、actor、scope、錯誤通知與誰可以編輯。另有是否允許其他 automation 觸發此規則的選項。當規則彼此更新相同資料時，先檢查循環與重複執行風險，不要為了「讓它跑」就把所有相互觸發都打開。

處理相關工作：先選關係，再分清「檢查」與「對它動作」

Related items 可以是 subtasks、parent、Epic 子工作或透過連結類型相連的工作。Parent-child 是階層關係；blocks／is blocked by 等是一般連結關係。不要因為都叫「相關」就認為同一個 branch 會自動包含全部。

Related-items condition 主要檢查相關工作是否存在或是否滿足條件；related-items branch 則讓裡面的動作逐筆對相關工作執行。合成例：「所有 subtasks 都 Done？」是檢查；「把每個 subtask 加上標籤」是對它們逐筆動作。

在 parent branch 內，{{issue}} 指目前被處理的 parent；{{triggerIssue}} 仍指最初觸發的 subtask。若你在分支內用 {{issue.key}} 記錄來源，就會得到父工作 key，而非原本子工作。後面的 smart values 段會用數據再演一次。

跨專案連結也必須同時符合 scope 與權限。連結存在，不代表 actor 一定看得到對方，也不代表可以更新對方。還要檢查連結方向，避免把「阻擋我」與「被我阻擋」的工作用反。

多工作分支可能平行執行，沒有先處理 A 再處理 B 的保證，主線也可能在分支完成前往下走。因此不能依賴「前一個 branch 更新的值一定在下一個 branch 可見」來做累加或依序決策。需要這種保證時應重新設計資料依賴，不能只把圖排得從左到右。

If/else：不符合第一種情境時，仍可有另一條明確處理路徑

一般 condition 像一道門：不符合就不做後面的動作。If/else 則能表達替代處理：「如果風險是 High，標記 needs-review；否則，標記 routine」。不符合 High 並不是整個需求不存在，而是要走另一種動作。

合成例：當工作建立，若 work type = Bug 且 Priority = Highest，走高優先分流；否則若 work type = Bug，走一般 Bug 分流；其餘不做本規則的指派。把條件排序和適用情境寫清楚，避免多個彼此不排他的獨立 if 動作反覆覆寫 Assignee。

需要同時滿足多條件，與只需任一條件成立，是兩種不同的邏輯。先用自然語言標示「而且」或「或者」，再選介面相應的組合方式。不要只因為條件都寫在同一個方框裡，就忽略它們的組合規則。

題目或實務例若缺少值，先決定空值要走哪條路。例如 Risk 為空，不應自動當成 Low，除非需求明確如此。設一個待補資料分支，通常比把未知值當成安全值更容易檢查。這是本課的設計建議。

Smart values：雙大括號是取值，欄位路徑要跟著目前工作讀

{{issue.key}} 代表目前工作 key；{{issue.summary}} 代表摘要；{{issue.status.name}} 代表可讀的狀態名稱。雙大括號內是受支援的資料路徑，不是要貼上的中文欄名，也不是任意可執行程式。現行 UI 改叫 work item，這些語法仍保留 issue；project token 也仍對應 space。

合成資料：觸發工作是 DEMO-12，parent 是 DEMO-3。在主線讀 {{issue.key}} 得 DEMO-12；進入 parent branch 後，{{issue.key}} 得 DEMO-3，{{triggerIssue.key}} 仍得 DEMO-12。這樣才能寫「因 DEMO-12 完成而檢查 DEMO-3」而不把來源與目標搞反。

取值要知道型態。{{issue.status}} 與 {{issue.status.name}} 的意義不相同，前者在文件中是狀態 ID，後者是名稱。若把不符合動作期待的值送到 Transition，可能得到找不到目的狀態的錯誤。

若需要自訂欄位值，先從官方可用 smart values 與欄位身分確認正確路徑，再用 Log action 在合成工作上驗證。空值、缺 parent、選項物件與清單的情況都要測；不要看到預覽字串就假設所有資料都會有值。

JQL 與 smart values 也不同：JQL 像「statusCategory = Done」是查詢條件；smart value 是執行時取得實際資料。即使兩者放在同一個規則中，也要分清哪段在選資料、哪段在讀值。

Actor 是實際執行者；規則 owner 很有權限也不能代替它

Owner 用來負責與維護規則；Actor 是執行動作、在工作歷史中留下執行身分的帳號；觸發人則是引起事件的使用者。除非規則明確把觸發人設為執行身分，不能預設「誰按按鈕，就以誰的權限跑」。

Jira 的預設 actor 通常是 Automation for Jira。若改為特定使用者，這個人必須具備目標工作所需權限；如果離職、停用或群組改變，規則可能受影響。這是身分治理風險，不能只在第一次成功時驗證一次。

依動作列最小權限需求：讀取工作先看 Browse 與個別工作安全性；編輯要 Edit；轉換要 Transition，並需有合法 workflow 路徑與適用規則。能建立規則、能看工作、能編輯、能轉換，都不是同一件事。

若 actor 為 Automation for Jira，官方排錯會檢查 atlassian-addons-project-access 角色是否有動作所需權限。不要因看到這個名稱就把所有權限一口氣放寬；先確定受影響的工作、動作、scope 與安全性，再由合適管理者做必要調整。

錯誤「actor 無法看見工作」也可能出現在工作已被其他處理刪除的情況。先確認目標仍存在，避免將每個查不到工作的結果都誤診成權限不足並過度授權。

完整推演：最後一個 subtask 完成時才考慮完成父工作

合成輸入：DEMO-3 是父 Task；DEMO-11 已 Done；DEMO-12 剛轉為 Done；DEMO-13 還在 In progress。Trigger 捕捉 DEMO-12 的完成事件，再確認觸發類型是 subtask，避免把 Epic 子工作和標準工作混用。

進入 parent branch 後，處理目標變成 DEMO-3。以 related-items condition 檢查 parent 的 subtasks 是否全部符合完成條件。此案例 DEMO-13 尚未完成，所以不執行父工作的完成 action，這是正確結果。

若 DEMO-13 之後也完成，再次檢查時所有 subtasks 都符合，仍要確認 parent 尚未完成、workflow 有合適轉換、actor 可執行且必要欄位齊全。滿足後才能執行 Transition action。規則不是直接把任意 status 文字寫進去就能越過 workflow。

相近時間兩個子工作完成可能產生兩次規則執行。設計上先檢查父工作目前狀態，並避免重複通知或不可重複動作；不要依賴分支恰好按順序執行。若規則行為涉及多筆更新，更要看每次 audit log 與實際結果。

在公司管理型父工作，完成轉換的 Resolution 邏輯也應一併驗證，沿用 4.1 的責任設計。Automation 觸發正確不代表流程資料一定一致；仍需查 status、Resolution、board 等不同口徑。

從 audit log 倒推：沒觸發、沒符合、找不到目標、沒權限是不同問題

先確認是否有本次 execution。若沒有，查規則是否啟用、trigger 是否真的發生、scope 是否涵蓋，以及事件是否來自另一條 automation 而不被允許觸發。不要先重建一整條規則。

若有 execution，逐步看 trigger 得到哪筆工作、哪個 condition 通過或停止、branch 選了哪些對象、smart value 解析成什麼，以及哪個 action 回報錯誤。使用最少的合成識別資訊寫 log；不要把敏感內容或憑證寫進稽核紀錄。

若 Transition 失敗，按順序查目前狀態是否有到目的狀態的適用路徑、目的值是否合法、actor 是否能查看及轉換、workflow condition／validator／property 是否允許。不能因為「automation 是系統做的」就預期跳過流程。

修正後重新測同一種合成案例，並讀實際工作歷史與相關欄位。規則能保存，只代表設定可被保存；一次 audit log 成功也只能證明該次執行，不能替代缺值、錯誤身分、跨專案等負面案例。

考綱 rule 與現行 flow：保持概念，查核介面

2025 考綱的 automation rule，在現行文件可能寫 automation flow，建立介面也可能提供 template、從零開始、Rovo 或 Studio。Trigger、condition、action、branch、scope、actor 仍是本課要掌握的核心。

本課不把 Rovo 生成、Operations team scope、第三方付費 action 或外部連線配置當成新增考點。若日後需要它們，應按當前權限、資料分享與方案條件另行學習；不能把 AI 生成一條流程當成已經驗證正確。

紙上與隔離環境演練：先只記錄，再預測狀態

先以紙上推演完成。若要實際操作，只能使用另行授權、隔離且可丟棄的練習環境；使用合成資料，先確認沒有共用正式設定或真實通知收件者。這些步驟是文件查核的練習設計，並非已替你執行或驗證成功。

自我檢查與理由

自我檢查

「子工作完成」代表父工作一定也完成嗎？

查看答案與理由

不一定。還要檢查其他子工作、父工作目前狀態、可用轉換和 actor 權限。

自我檢查

DEV 規則要更新 OPS 的 linked item，只要 actor 在 OPS 有權限就夠了嗎？

查看答案與理由

不夠。規則 scope 也必須包含相關專案；同時要滿足該動作所需的權限與設定。

自我檢查

condition 不符合後沒有任何 Edit action，是否一定是錯誤？

查看答案與理由

不一定。若此筆不屬於需求範圍，沒有動作就是預期結果；要對照條件與執行紀錄。

自我檢查

只想確認所有子工作已完成，而不是逐一編輯它們，應先選 condition 還是多子工作 branch？

查看答案與理由

先選能檢查相關工作的 condition；branch 的用途是切換處理對象並執行裡面的動作。

自我檢查

要求 High 風險做 A，其餘做 B，若只放「Risk = High」一般 condition 後接 A，是否完整？

查看答案與理由

不完整。它只表達符合時做 A；不符合後停止，沒有表達 B。應設計 if/else 或其他明確替代路徑。

自我檢查

parent branch 中要取得最初觸發子工作的 key，應讀 {{issue.key}} 還是 {{triggerIssue.key}}？

查看答案與理由

{{triggerIssue.key}}。此時 {{issue.key}} 已指向 parent branch 正在處理的父工作。

自我檢查

Owner 是 Jira admin，但 actor 沒有 OPS 的 Transition 權限，跨專案轉換是否自動成功？

查看答案與理由

不會因 owner 是管理者而取得 actor 缺少的權限；還需有合法轉換及其他適用條件。

自我檢查

DEMO-12 完成，但 DEMO-13 還在 In progress，父工作這次應該發生什麼？

查看答案與理由

相關工作條件不通過，父工作不應因這次規則而完成；不需要把「沒有 action」當成故障。

自我檢查

規則可保存，但轉換失敗，是否應先將 actor 升為最高管理者？

查看答案與理由

不應。先用 audit log 查目標、路徑、值、必要權限與 workflow 規則，修最小必要原因。

自我檢查

介面改叫 flow，就能省略 scope 和 actor 查核嗎？

查看答案與理由

不能。名稱改變不會消除規則的作用範圍與執行權限。

版本與實測範圍

以 April 2025 ACP-120 考綱概念為主。現行文件可能寫 space、work item、work type、automation flow，分別對應考綱 project、issue、issue type、automation rule。所有案例與題目均為原創合成資料，非官方考題。操作路徑經官方文件查核，未在特定租戶實測。教材不連接 Jira，不會替你執行任何真實管理動作。
