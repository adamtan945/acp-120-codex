公司管理型通知 從事件到正確收件者

先理解用途，再判斷設定與結果。

官方目標 5.1 · 來源內容版 2026-10-05.complete-draft

閱讀前提

先理解工作項目、專案與工作流程transition。

閱讀權限需同時考慮Browse Projects／Browse Spaces與工作項目安全性。

如要另行實作，限有明確授權的隔離測試專案與測試收件者；本節先做紙上推演。

先認識名詞

Event 事件：Jira用來表示某件事已發生的訊號，例如工作項目建立或留言新增。事件不等於工作流程狀態。

Notification scheme 通知方案：將事件對應到收件者類型的共用設定，再由專案使用它。

Project role 專案角色：同一個角色名稱，在不同專案可以由不同成員擔任。

Watcher 關注者：追蹤某筆工作項目的人；watch本身不會授予閱讀權限。

通知的目的與四段判斷

通知的目的是讓需要接手工作的人知道變更。先從業務句子開始：「設計完成時，請負責驗收的人檢查」。再拆成發生什麼、誰需要知道、在哪些專案適用，以及是否能讀這筆資料。若一開始就把所有群組加到每個事件，會讓大家收到大量不需要的信，反而錯過真正的交接。

公司管理型的主要關係是專案→通知方案→事件→收件者。方案可以共用；對共享方案增加一個收件角色，會改變所有使用該方案的專案。只有建立方案而沒有將專案關聯到它，該專案的行為不會因此改變。

把收件者列入方案仍只是候選資格。Jira還會檢查能否看見工作項目，以及個人通知偏好。若人員不能Browse該專案，或被工作項目安全層級排除，不應收到該工作項目的事件通知。通知設定不是存取權限的替代品。

先查共用範圍 再配置方案

開始前要確認自己有Jira管理權限、專案是company-managed，而且找到目前使用的方案。列出共用此方案的專案和各專案角色成員。若需求只針對一個專案，先評估建立獨立方案；不要為了解決一人的郵件量直接改動大家的共用方案。

現行文件路徑是Settings→Work items→Notification schemes。新增方案並命名用途；找到事件列的Add，選收件者類型及所需參數。方案的編輯即時儲存，因此「還沒按Save」不一定代表沒有影響。專案的Space settings→Notifications→Use a different scheme用來切換關聯。

文件中的space對應考綱project，並不表示要新建另一種容器。檢查變更應包含設定前後的關聯、事件列，以及每一個受影響專案的角色解算。真正寄信測試要另行取得授權，使用沒有真實資料的工作項目，不要在正式專案製造測試噪音。

判斷實際事件 不只看按鈕名稱

建立、更新、指派、留言新增、留言編輯、工作日誌新增與更新各有對應事件。公司管理型文件特別指出：刪除留言使用Work item updated，不是獨立的「留言刪除」事件。若把收件者只加到Work item commented，不能期待它涵蓋所有留言相關動作。

Resolved、Closed、Reopened、Generic與custom event可能由工作流程transition發出。工作項目目前的status叫「Ready」不會自動產生一個Ready事件。要查看transition實際的發送事件設定，再回頭檢查通知方案。

合成案例：LAB-18的摘要被更正、接著加入留言、最後刪除那則留言。逐次對應為更新、留言新增、更新。這是在練習辨識訊號；是否各收到一封信還要看收件者、偏好及批次摘要，不能把事件數直接當郵件數。

用角色表達責任 用欄位表達每筆工作的參與者

Current assignee是目前承辦者；Reporter是回報者；Current user是觸發這次事件的操作者，不是永遠指管理員。All watchers是該筆工作的watchers。單一使用者、群組和專案角色則各代表固定個人、站台群組、在該專案擔任指定角色的人。

跨專案重用時，角色通常比硬寫群組合適。例如LAB的Reviewers是測試員甲，DOC的Reviewers是測試員乙；兩者共用一份「Review requested→Reviewers」設定，也能通知各自負責的人。直接加入固定群組會把同一群人套到所有使用方案的專案。

若每筆工作由不同人驗收，可以用User Picker或Multi User Picker自訂欄位值作收件者。Group Picker也有相應類型。欄位沒有填人，就沒有這條動態來源的候選收件者；增加欄位顯示不會自動增加通知對應。角色或欄位成員仍需通過閱讀權限。

自訂交接通知需要三個接點

假設標準事件不能清楚表達「送交內容審查」，可建立Review requested自訂事件。第一個接點是System→Events中的事件定義，依官方流程使用Generic event郵件模板。第二個接點是在該專案使用的通知方案內，將Review requested配到Reviewers。

第三個接點是工作流程：選擇從Writing到Review的transition，使用該編輯器支援的額外事件動作發出Review requested，並依流程草稿機制發布。自訂事件舊教學示範傳統Post functions與Publish draft；現行advanced workflow文件則明確警告不可改刪必要的Generic event post function，建議另加自訂post function。實作應保留必要事件，核對當前編輯器支援方式；不能照舊步驟直接替換必要事件。

只建事件沒有觸發點，事件就不會因狀態名稱相似而自動執行。只改transition但方案沒收件者，也不會憑空知道要通知誰。若workflow和notification scheme各自共用，兩種影響範圍都要盤點：流程決定哪些transition發出訊號，專案方案決定訊號送給誰。

收不到信時 依序檢查而不是擴大權限

先記錄一筆合成事件的時間、操作者、工作項目、預期收件者與實際變更，再確認事件與方案。接著檢查候選收件關係、Browse權限、安全層級、個人通知偏好，以及郵件服務與收件匣。這能把「沒被選成收件者」「不能看資料」「自己關閉該類通知」「郵件傳遞問題」分開。

自我操作不寄信是常見原因：Jira預設不通知自己的變更，個人可調整。一般活動也可能合併成摘要，官方目前說可延遲最多約10分鐘；新指派、提及等重要通知有不同處理。測試時不要以按下按鈕後一秒沒信就判定方案失效。

誤解一：把使用者加到所有群組就能修好通知。這可能同時擴大資料存取，卻沒有修正錯誤事件。誤解二：個人勾選所有通知可以繞過管理者停用。個人設定是支援範圍內的篩選，不能自行新增管理者未提供的事件路徑。

圖解與逐步理解

事件

由 transition／操作發出事件。

方案候選

專案通知方案決定候選收件者；共用方案改動可能影響多專案。

資料權限

Browse 與工作項目安全性再檢查候選能否讀取。

個人偏好

支援類別的個人偏好可能排除活動郵件。

自我檢查與理由

自我檢查

一份通知方案供LAB與DOC使用。只想調整LAB，為何要先查關聯？

查看答案與理由

直接改共享方案可能同時改變DOC。先查共用範圍，再選獨立方案或確認共同變更。

自我檢查

公司管理型工作項目的留言被刪除，要查哪個事件？

查看答案與理由

查Work item updated；不是只查Work item commented。

自我檢查

兩專案由不同人擔任Reviewers，如何重用通知？

查看答案與理由

方案以專案角色為收件者，角色成員在各專案解算；不以相同群組硬綁兩專案。

自我檢查

自訂事件建好了但未寄信，還少哪兩個接點？

查看答案與理由

通知方案中的事件收件對應，以及workflow transition發出該事件的設定；有效流程草稿需發布。

自我檢查

收件者在方案內但不能讀該工作項目，是否應收到內容？

查看答案與理由

不應。通知不是繞過Browse和安全層級的途徑；另查個人偏好不會改變此門檻。
