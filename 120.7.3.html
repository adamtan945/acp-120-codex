狀態 結案原因與優先順序 共用值的治理

看圖建立心像，用例子理解，再動手驗證。

官方目標 7.3 · 來源內容版 2026-10-05.complete-draft

先看懂這張圖

狀態、結案原因與優先順序回答不同問題

Status回答進度，Resolution回答為什麼結束，Priority回答多重要。共用值更名會影響所有引用者，workflow複製不代表status也深度複製。本節只更名專用教學status並觀察兩個教學流程，禁改共享正式值。

用一個例子理解

LAB-WF-A與LAB-WF-B共用獨立status「LAB Review」。更名「LAB Peer review」應在兩流程可見，category仍In progress；LAB-131 Priority=High、Resolution空白，三欄位不互相取代。

閱讀前提

能分辨workflow status、transition和board column。

了解company-managed可共用配置，team-managed也可能在同一專案內共用status。

本節只規劃變更及合成測試，不在正式站台新增或改名全域值。

動手驗證

更名一個僅兩測試流程引用的status

文件查核設計；未租戶實測。完成下列步驟後，以你看到的結果判斷是否成功。

這次要驗證

  • 先預測：改A使用的共用status只影響A嗎？
  • 先預測：High Priority或Done名字能取代Resolution嗎？

準備環境

角色
  • Jira管理員負責查status引用與兩個workflow；測試使用者可讀LAB-131。
方案與功能
  • Company-managed Jira Cloud；只改特建LAB status，不新增或更名全站共用Resolution／Priority。
先備與假資料
  • 兩個獨立教學workflow均引用LAB Review，且沒有其他引用；記錄名稱、category、board對應與JQL基準。
  • 介面分批推出可能顯示專案（project／space）、工作項目（issue／work item）、工作類型（issue type／work type）；依物件與官方文件辨認入口。
隔離範圍
  • 僅限已核准獨立教學站台的LAB專案（project／space）；資料、名稱與測試身分均為合成，不連正式站台。
  • 只用既有核准測試帳號，不邀請真實人員；測試站台須預先隔離郵件、外部整合與非實驗automation，未確認隔離時改用紙上模式。

先預測，再驗證

先預測：改A使用的共用status只影響A嗎？

比較預測與理由

不是；同一status更名傳到所有引用它的workflow，因此B也需驗證。

先預測：High Priority或Done名字能取代Resolution嗎？

比較預測與理由

不能。優先順序、流程位置與結案資料用途不同。

記住這個心像 同名值先看物件身分，共用值先看所有引用，再看資料與報表。

還原與收尾

  • 將LAB Peer review更回LAB Review，保持category，重新檢查A/B與教學JQL。
  • 不刪status、Resolution、Priority或停用subtasks；無需要的實驗automation保持停用。

沒有支援的環境：無權限或無教學站台：觀察／紙上替代

  • 依本章官方來源辨認設定物件；只看文件，不在自己的正式站台尋找替代操作。
  • 在紙上列出本章假資料、每一步預測與可見結果，再逐項核對checks答案。

驗證界線 此替代只能證明理解與推演；未建立或修改Jira，不能記為租戶操作驗證。

深入查閱

把圖中的關係對回設定

以下保留本節考點與細節。沿用圖中的角色、假資料與步驟，逐段確認原因。

先認識名詞

Status 狀態：工作在流程中的位置，例如Writing、Review、Done。

Status category 狀態分類：把細部狀態歸到To do、In progress、Done三種大類，用於顯示和報表。

Resolution 結案原因：Company-managed工作為何已處理完成，例如Fixed或Duplicate；未設定值與名叫Unresolved的值不同。

Priority 優先順序：表達重要性或緊急程度；不等於工作進度，也不等於board上的手動Rank。

Subtask 子工作：隸屬父工作、可分派和追蹤的較小工作項目。

用三個問題選欄位

同一筆工作可以同時是High priority、In Review status、Resolution尚未設定。Priority回答先處理多重要；Status回答現在走到哪裡；Resolution回答為何結束。

想表示客戶問題很急，應調Priority，而不是把狀態改成Urgent再讓流程與報表難以解讀。

Status category把多個細部狀態彙整。例如Writing與Review都屬In progress，不代表兩者是同一個status。改名Review→Peer review只是名稱變更；改category到Done則改變它的分類語意，應分別審查。

Resolution空值代表尚未設定結案原因。不要新增名為Unresolved或None的Resolution想表示未完成：它本身仍是有值，與真正空值不同。完成狀態也不應只憑名字判斷；

company-managed workflow應在適當結案transition設定Resolution，報表才有一致依據。

建立值之後 還要把它用在正確位置

新增status時先檢查能否重用語意相同的既有值，避免大量近似名稱。從Workflows編輯目標workflow，Add status可選既有status或建立名稱與category；接著確認入站和出站transitions。若允許Any status進入，等於大幅開放路徑，應符合團隊流程需求。

只有新增一個名稱不會完成流程設計。

Resolution由Jira管理者在Settings→Work items→Resolutions管理，適用company-managed。建立「Duplicate」等值後，還要決定哪個transition自動設定、或在哪個結案screen請人選擇。

若加到一般create/edit畫面而誤填值，可能讓未完成工作出現在已完成報表中。

Priority在Settings→Work items→Priorities管理名稱、說明、圖示與顏色，再由priority scheme決定專案使用的集合。新priority會進入包含所有priority的default scheme，不能保證每個自訂scheme也自動採用。

定義新值前先說清楚與既有High的差別，避免增加選項却沒有一致使用標準。

改名會改共用物件的現在名稱

複製workflow不等於獲得獨立status；先確認引用再改名。

一個status可被多個workflow引用；改這個status的名稱會傳到所有引用它的流程與專案，而不是只影響當前開啟的workflow。workflow複製也不應被當成已深度複製每個status；應先看共用物件關係，才決定改既有值或建立新的獨立值。

Resolution與Priority也是共用值。改名需讓使用中的團隊理解新舊詞彙的對應，並檢查JQL字面值、automation條件、報表說明和翻譯。這些是變更驗收清單，不是宣稱所有引用一定自動改寫或一定失效；只有實際檢查才能確定各種引用的行為。

合成例：兩個workflow都使用同一個Review status。設計團隊希望叫Design review，營運團隊仍需要通用Review。若改同一物件名稱，營運也會看到新名，超出需求。先評估建立獨立狀態並在特定流程替換，且對既有工作規劃必要對應，不能為了縮小範圍直接刪掉共用status。

官方明說status更新不會自動通知使用它的團隊；所以發布後還有溝通與驗收工作。名稱改善應同時更新教學指引，讓使用者知道原本Review去哪了，而不是等人報錯才解釋。

停用子工作前先處理既有資料

本節不執行全站停用或轉換正式子工作。

Subtasks預設可用；在Settings→Work items→Subtasks能管理這類型態。官方要求停用前先把現有subtasks轉成standard work types。這表示「從今天不想再用子工作」仍牽涉舊資料，不能假設按Disable就保留全部原階層且只禁止新建。

轉換要先核對目的standard類型的workflow、欄位與關係，也要檢查依賴subtask狀態的父工作blocking condition，以及自動建立subtasks的automation。若資料轉換未完成，先不要執行全站停用。刪除某個subtask類型與停用整個subtask能力是不同範圍。

合成規劃：LAB有兩筆仍在進行的子工作、DOC沒有。必須先列出兩筆的轉換目的與原父工作追溯方式，再請負責人確認；不能因DOC沒用就認為全站可直接停用。這個檢查也適用其他共用功能：先盤點使用者與資料，再談關閉。

Team-managed的共用範圍也要查

Team-managed的status可被同一專案的多個work type workflow共用。從Space settings→Work types→Edit workflow更名或改category時，如果是共用status，會更新該專案其他使用它的workflow。

不要把team-managed理解成每種work type完全獨立、永不共用。

若需求只改目前workflow，現行文件提供在「This status is shared across multiple workflows」警示下使用「Change status for these work items only」。

這會複製status及其transitions和rules供目前流程使用，再Update workflow確認適用work types。這條具體分支與直接改共用名稱不同。

新增status也要對應到board column；預設未對應的狀態不會在board顯示。工作仍存在不等於每張board都會顯示它。更名、改category、刪除status和移除board對應是四種不同影響，應分別測試，不把「board看不到」當成工作刪除。

圖解與逐步理解

Status／category

進度狀態與高層分類不同。

Resolution／Priority

結案原因與優先程度各有不同意義。

共用 ID

共享 status 改名影響所有引用。

局部需求

Team-managed 也須查專案內共用狀態；只改此流程可另行複製。

自我檢查與理由

自我檢查

一筆High、Review、Resolution空白各代表什麼？

查看答案與理由

優先重要性高、流程在審查、結案原因未設定；三欄意義不同。

自我檢查

從某workflow改共用status名字，只改這條流程嗎？

查看答案與理由

不是。所有引用同一status的workflow／專案都受到名稱更新；先查使用範圍。

自我檢查

停用subtasks前的資料前提是什麼？

查看答案與理由

先將既有subtasks轉成standard work types，並評估父子關係、流程與automation影響。

自我檢查

Team-managed只想改Bug流程的共用status，該留意哪個分支？

查看答案與理由

直接改會影響同專案所有共用workflow；可使用文件的Change status for these work items only複製分支，再確認更新套用類型。
