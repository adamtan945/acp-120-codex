管理者分工與最小權限

「最大的管理角色最省事」會掩蓋真正需求。較可靠的問法是：要改哪個物件、誰受影響、能否由既有較小範圍的角色處理？這是教材的管理決策方法，不是鼓勵學員在正式站台試著提升自己的權限。

「管理群組的名稱一定固定」也不可靠。應檢查群組實際被授予什麼角色或權限，避免因名稱像admin就認定具備某項能力。移除角色後仍能操作，也可能來自另一個授權來源，不能只查一條路徑。

Cloud管理員通常透過產品管理介面管理服務；Data Center的主機、檔案與資料庫維運不是本課的操作內容。看到要求直接修改Jira資料庫的文章，要先檢查部署平台，不要因標題含Jira就照做。

全域權限與群組授權

分享篩選器讓別人取得一個查詢物件，並不自動把查詢結果中的每張單授權給對方。兩人開啟同一個篩選器，可能因各自的專案與安全性權限而看到不同結果。第6.2節會再把報表物件、資料與訂閱串起來。

另外，Browse users and groups也不等於Browse Projects。前者涉及人員資訊的查找，後者涉及專案／工作項目的閱讀。題目故意使用相似的Browse文字時，先圈出後面的受詞。

專案權限與重用方案

錯誤說法：「把 board 分享給對方，他就能看 board 上所有工作項目。」釐清：分享控制的是 board／filter 物件的可用性；底層閱讀權限與工作項目安全性仍會過濾內容。

錯誤說法：「專案管理員能改任何共用權限方案。」釐清：本地角色成員管理與全站方案規則管理是不同層次。

錯誤說法：「給一個弱角色就能撤銷強角色。」釐清：需檢查所有授權來源與團隊管理型存取層級提供的基礎能力，不能假設最後加入的角色會覆蓋前者。

錯誤說法：「Link work items 權限存在，就不用檢查系統功能。」釐清：功能啟用與授權均需符合。

選擇專案型態與重用方式

錯誤說法：「公司管理型就是Scrum，團隊管理型就是Kanban。」釐清：管理治理與工作節奏是兩個維度。

錯誤說法：「使用相同模板就保證後續設定永遠同步。」釐清：同步影響來自實際引用的共用設定，不是模板名稱。

錯誤說法：「把管理型態改一下，不需要考慮資料與設定。」釐清：官方遷移流程涉及建立目標專案及搬移／對應，不能當作無成本的原地切換。

錯誤說法：「版本發布和sprint結束是同一件事。」釐清：版本是交付分組，sprint是時間安排。

元件與自動指派

工作類型與方案：讓每種工作走對設定

把共用的「Task」更名為「Operational task」，是在修改既有工作類型的名稱。原本使用這個類型的工作項目不會因此變成全新記錄；更名也不等於把它們搬到另一專案，或重新選擇流程。

影響範圍要沿「同一個類型物件被誰使用」追蹤。若多個公司管理型專案用到該類型，更名後使用者看到的名稱也會跟著改。只想改一個團隊的語意時，先評估是否真的需要獨立類型，避免把全站共用名稱當成本地文字。

更名前列出依賴名稱的 JQL、儲存篩選器、automation 條件、匯入範本、報表說明與第三方整合。這是變更檢查清單，不表示每個引用一定會壞，也不表示系統保證全部自動更新。管理物件的關聯與文字比對的依賴要分開驗證。

合成演練：如果網站流程以工作類型 ID 對應流程，但一份外部匯入表填著舊名稱，前者與後者的風險並不相同。更名後分別建立一筆測試工作與檢查匯入映射，才能確認使用者路徑與整合路徑都合理。

工作類型與方案：讓每種工作走對設定

「預約取餐」Story 可以拆成「後端驗證取餐時段」「設計錯誤訊息」「補回歸測試」三個 subtasks。每個子工作能有自己的承辦者與狀態，父工作則保留完整交付目標。當你需要知道一筆工作內部誰在做什麼，這種拆分很合適。

若一份工作需要獨立排進不同團隊的產品計畫、跨多個交付目標長期追蹤，先考慮標準工作與 Epic 或一般連結。不要只因為文字上「包含」就一律建 subtask；階層關系會影響操作與彙總方式。

有 subtasks 不代表 Jira 必然在最後一個子工作完成時自動關閉父工作，也不代表父工作一定不能先完成。若需要「所有子工作完成才可結案」，要另外設計 workflow condition；若要主動更新父項目，則可能用 automation。前者是禁止不合規動作，後者是代做動作。

同樣的概念適用 Scrum 和 Kanban。Scrum 規劃時常以標準工作承接衝刺範圍，再拆執行；Kanban 可用子工作追蹤同一需求的協作步驟。board 的呈現方式並不改變 parent-child 的資料關係。

工作類型與方案：讓每種工作走對設定

本課用 Epic → standard work item → subtask 當初學者的常見模型，幫助你分清成果、工作與執行拆分。這個模型不應被背成所有 Jira Cloud 版本都永遠禁止其他支援的關聯。

查核日的 Create a work item and a subtask 官方文件另明列：company-managed software 可使用 Add parent 將 subtask 直接連到 Epic 層。相對地，team-managed 的 subtasks 官方文件仍明列 subtask 建在標準工作之下，不能直接置於 Epic 層之下。這是管理型態與現行產品差異，本課原創題目不以未交代版本的絕對禁止句設陷阱。

目前 team-managed Epic 文件也要求 parent 關係維持相同管理型態：company-managed 工作對 company-managed parent，team-managed 工作對 team-managed parent。跨專案與跨管理型態是兩個不同問題。正式操作前仍需核對站台提供的入口和權限，不在正式資料上用試錯方式探索。

欄位與 context：讓資料可用、可填、可比較

虛構客服改善團隊想知道哪個需求是「法規要求、營運改善或顧客體驗」。如果每個人把理由自由寫在 Description，有人寫營運、有人寫門市、有人成本，後續統計會很難對齊。此時有受控選項的「改善理由」欄位，能讓篩選、分組與 automation 使用一致資料。

反過來，若資料只是偶爾補充的一句背景，Description 或留言可能足夠。每新增一個欄位，就增加填寫、維護、命名與查詢的成本。這是教材的設計建議：先說明欄位將支援哪個實際決策，再決定欄位是否值得存在。

不要先建一批同名欄位來解決每個團隊的差異。先查是否已有語意相同且適用的欄位，確認管理來源、field type 與 context。兩個都叫「Area」的欄位如果 ID 不同，資料並不會自動合併，報表和 automation 也可能選錯。

欄位與 context：讓資料可用、可填、可比較

Screen 或 layout 是呈現設定。把一個欄位從某個畫面移走，只能證明那個畫面不再提供原本的呈現；不能據此保證其他檢視、匯出、搜尋或整合都看不到資料。不要把「我在目前頁面看不到」當作已通過存取控制測試。

合成例：你想把人事評語從一般 Task 旁邊藏起來。正確的下一步是回到權限與工作項目可見性的設計，而不是承諾拖到 Hidden 就能安全保存機密。這裡說的是安全設計邊界，並不假裝本課已測試所有欄位的 API 行為。

如果遇到 Required 卻無可用輸入位置，先沿 context、field configuration、Create screen 檢查，不要單靠 UI 出不出現推論資料已有效。實際錯誤訊息與租戶配置才是定位依據。

Screen 與 layout：把資料放在正確的操作位置

第一步，界定症狀：誰在哪個專案、哪個 work type、哪個操作看不到哪個 field？若只有一位使用者的 Create 缺欄位，先檢查個人 Show fields／All fields；這比立刻修改共享 scheme 的風險低。

第二步，確認 field 身分與 context。名稱相同可能選錯欄位；context 不包含目前專案或類型時，要處理適用範圍。第三步，檢查 field configuration／field scheme 是否允許可用、是否隱藏或有必填要求。

第四步，沿兩層畫面方案找到真正的 Create/Edit/View screen，而不是只找名稱包含專案名的 screen。第五步，若是詳細頁問題，再檢查 layout 的 Hidden、Hide when empty、欄位空值以及共享 View screen。

最後，以原本受影響使用者及一筆合成資料重新驗證相同操作。若問題是權限或特殊欄位限制，按錯誤與官方規則另查；不把「多加到幾個 screen」當成萬用解法，也不把 screen 當成保護所有資料的防線。

公司管理型 workflow：從狀態、規則到正確結案

Workflow property 以 key-value 形式改變 status 或 transition 的某些行為。例如在 Done status 使用官方支援的 jira.issue.editable = false，可以限制該狀態的編輯；Resolution include／exclude 可限制某轉換提供的完成原因選項。

這些設定容易和專案權限、actor 行為及一般欄位編輯交互作用。使用者有 Edit work items 權限，不表示在任何狀態都一定可編輯；反過來，property 也不是自動授予原本沒有的專案權限。

Property、condition、validator、post function 不是同義詞。若需求是「只有 Reviewer 可批准」，優先用明確的轉換限制來表達，而不是隨意貼一個看不懂的 key。每個 property 要查官方適用位置、值格式與副作用；官方也警告部分 property 可能造成問題。

本課只要求辨識用途和判斷影響，不要求背所有 property 名稱或第三方 app 的自訂擴充。沒有在隔離練習環境驗證前，不應直接把範例貼進正式共用 workflow。

公司管理型 workflow：從狀態、規則到正確結案

Status 表示流程位置；Resolution 表示結束原因。一筆 Bug 可以在 Done，原因是 Fixed、Duplicate 或 Won’t do。用同一個完成狀態搭配不同 Resolution，能避免為每種結案原因都增加一個狀態。

Jira 多種功能依 Resolution 是否有值判斷 resolved，例如 Created vs Resolved、Open work items 篩選，以及部分刪除線呈現。若 Done 但 Resolution 空白，這些功能可能仍把它視為未解決；若重新打開仍留 Fixed，則可能已在 In progress 卻帶刪除線。

Unresolved 是沒有 Resolution 值的狀況。不要建立一個真的叫「Unresolved」或「None」的 Resolution 選項來假裝空白：只要選了這個實際值，它仍是非空，會造成錯誤判斷。真正清除是讓欄位回到空值。

同時也不要反過來宣稱「所有 Jira 報表只看 Resolution」。Board 最右欄有自己的完成判斷，status category 又提供分類。可靠的完成設計要讓狀態、分類、board 映射與 Resolution 彼此一致，而不是用其中一項取代全部。

公司管理型 workflow：從狀態、規則到正確結案

重新開啟不是只把 Done 改回 In progress。完成原因應被清除，讓依 Resolution 判斷的功能也恢復未解決口徑。舊編輯器可見 Clear Field Value post function；現行 Edit a workflow’s rules 文件則說明以 Update a work item field 的 Perform action 在重新開啟路徑清除 Resolution，並確認順序正確。實際空值選項依租戶介面查核。

合成完整路徑：Review → Complete → Done 時設定 Fixed；Done → Reopen → In progress 時清除 Resolution。若有 Done → Rework 與 Done → Reopen 兩條不同路徑，都要檢查清除邏輯。

更新 workflow 是在修往後會執行的行為，不會自動走訪所有既有錯誤工作並修資料。若歷史上已有 In progress 且 Resolution 非空的工作，需另外找出範圍、確認業務狀態、評估通知與報表影響，再安排授權過的資料修正。

本教材的自我檢查只讀合成資料，不要求在正式站台做 bulk transition、刪除或回填。能指出「未來規則已修、歷史資料尚未修」是管理者的重要驗收能力。

團隊管理型 workflow：為不同工作設計清楚的路徑

目前文件路徑為 Space settings → Work types → 選類型 → Edit workflow。完成修改後，按 Update workflow，確認這次 workflow 套用到哪些 work types，再保存。舊名稱可能仍是 Project settings / Issue types。

「我是從 Bug 點進來」不等於這次一定只影響 Bug。流程原本可能也用在 Task；更新時要把選定類型和需求比對。若要讓 Bug 獨立，就明確選擇相應範圍，並驗證 Task 還保有原本流程。

驗收至少包含兩面：建立一筆 Bug 看到新流程；建立一筆 Task 確認未被不小心套用。只測一筆 Bug 成功，不能證明影響範圍正確。這是教材的測試設計建議，所有實作僅限隔離且授權的練習環境。

這套工作方式不等於把公司管理型的 workflow scheme 搬進團隊管理型。應從該專案內的 work type 流程設定理解其作用，避免在全站尋找根本不適用的對應表。

團隊管理型 workflow：為不同工作設計清楚的路徑

更名改的是這個 status 的標籤；改 category 則可能改變它被歸類為待辦、進行中或完成的意義。這兩件事都不是「替工作執行正常 transition」的同義詞。變更時要知道是在改流程設計還是在移動個別工作。

同一 team-managed 專案內，status 可被多個 workflow 共用。若 Bug 與 Task 共用 In review，直接改名為 Security review，可能使同專案所有使用該 status 的流程一起改名。官方介面提供只為目前工作範圍變更的方式，會建立獨立副本；實際按鈕依版本確認。

刪除 status 會連帶移除與它相關的轉換和規則；在目前 workflow editor 刪除，表示從目前編輯的 workflow 移除，不表示無條件從所有 workflow 抹掉同名 status。若有工作正在該狀態，Jira 會要求把它們移到有效狀態。

合成變更清單：刪除 Waiting for supplier 前，列出目前在此狀態的 Bug、進出箭頭、附帶規則與 board mapping，再決定它們應轉往 Triage 還是 Fixing。不要為了讓畫面變短，把不同真實處理狀況一律塞到 Done。

團隊管理型 workflow：為不同工作設計清楚的路徑

合成 Bug 流程規定只有 Maintainer 角色可以從 Verification 結案，且所有必要資訊必須完整。第一種案例：Maintainer 且資訊完整，應成功；第二種：Maintainer 但資訊缺漏，要按實際驗證規則被阻止或提醒；第三種：普通成員，應不具備受限結案能力。

再測替代路徑。若另有 Any status → Done，且沒有相同限制，就可能繞過原本以為唯一的驗收路徑。管理者應盤點所有進入結束狀態的路，而不是只測自己最常按的箭頭。

最後測多 work type 的影響及 board 映射。同一規則可能在其中一種 work type 有需要的欄位，另一種類型沒有；規則處理差異應來自明確條件，而不是留下不可解釋的跳過或失敗。

Automation：用事件、條件、範圍與執行身分推導結果

合成團隊每當子工作完成，都要打開父工作、檢查其他子工作、再決定父工作是否能完成。如果交接頻繁，人容易漏查。Automation 能把這段一致且可驗證的流程交給系統執行，但它需要明確規則，不能只寫「幫我處理好」。

把需求改寫成：「當一筆 Subtask 轉到完成類別時，檢查它的父工作；只有當全部 subtasks 都完成、父工作還沒完成，才走父工作合法的完成轉換。」這句話已包含 trigger、相關工作範圍、condition 與 action，也揭露必須另查 actor 權限。

本課先用紙上資料和只寫合成值的 Log action 推演。不要一開始就用真實客戶工作測試大量編輯、外部通知、刪除或跨專案動作。先把一次執行說清楚，再逐步擴大。

Automation：用事件、條件、範圍與執行身分推導結果

{{issue.key}} 代表目前工作 key；{{issue.summary}} 代表摘要；{{issue.status.name}} 代表可讀的狀態名稱。雙大括號內是受支援的資料路徑，不是要貼上的中文欄名，也不是任意可執行程式。現行 UI 改叫 work item，這些語法仍保留 issue；project token 也仍對應 space。

合成資料：觸發工作是 DEMO-12，parent 是 DEMO-3。在主線讀 {{issue.key}} 得 DEMO-12；進入 parent branch 後，{{issue.key}} 得 DEMO-3，{{triggerIssue.key}} 仍得 DEMO-12。這樣才能寫「因 DEMO-12 完成而檢查 DEMO-3」而不把來源與目標搞反。

取值要知道型態。{{issue.status}} 與 {{issue.status.name}} 的意義不相同，前者在文件中是狀態 ID，後者是名稱。若把不符合動作期待的值送到 Transition，可能得到找不到目的狀態的錯誤。

若需要自訂欄位值，先從官方可用 smart values 與欄位身分確認正確路徑，再用 Log action 在合成工作上驗證。空值、缺 parent、選項物件與清單的情況都要測；不要看到預覽字串就假設所有資料都會有值。

JQL 與 smart values 也不同：JQL 像「statusCategory = Done」是查詢條件；smart value 是執行時取得實際資料。即使兩者放在同一個規則中，也要分清哪段在選資料、哪段在讀值。

Automation：用事件、條件、範圍與執行身分推導結果

先確認是否有本次 execution。若沒有，查規則是否啟用、trigger 是否真的發生、scope 是否涵蓋，以及事件是否來自另一條 automation 而不被允許觸發。不要先重建一整條規則。

若有 execution，逐步看 trigger 得到哪筆工作、哪個 condition 通過或停止、branch 選了哪些對象、smart value 解析成什麼，以及哪個 action 回報錯誤。使用最少的合成識別資訊寫 log；不要把敏感內容或憑證寫進稽核紀錄。

若 Transition 失敗，按順序查目前狀態是否有到目的狀態的適用路徑、目的值是否合法、actor 是否能查看及轉換、workflow condition／validator／property 是否允許。不能因為「automation 是系統做的」就預期跳過流程。

修正後重新測同一種合成案例，並讀實際工作歷史與相關欄位。規則能保存，只代表設定可被保存；一次 audit log 成功也只能證明該次執行，不能替代缺值、錯誤身分、跨專案等負面案例。

公司管理型通知 從事件到正確收件者

先記錄一筆合成事件的時間、操作者、工作項目、預期收件者與實際變更，再確認事件與方案。接著檢查候選收件關係、Browse權限、安全層級、個人通知偏好，以及郵件服務與收件匣。這能把「沒被選成收件者」「不能看資料」「自己關閉該類通知」「郵件傳遞問題」分開。

自我操作不寄信是常見原因：Jira預設不通知自己的變更，個人可調整。一般活動也可能合併成摘要，官方目前說可延遲最多約10分鐘；新指派、提及等重要通知有不同處理。測試時不要以按下按鈕後一秒沒信就判定方案失效。

誤解一：把使用者加到所有群組就能修好通知。這可能同時擴大資料存取，卻沒有修正錯誤事件。誤解二：個人勾選所有通知可以繞過管理者停用。個人設定是支援範圍內的篩選，不能自行新增管理者未提供的事件路徑。

團隊管理型通知 在專案內安排交接

專案管理者規劃誰應該知道；個人在支援的活動類別中決定哪些通知方式需要保留。個人設定會疊在管理者設定上，因此勾選「我是assignee」不能憑空恢復已被管理設定關閉的事件。

合成情境：LAB-T新指派事件包含Current assignee。測試員甲接手但沒收到信時，先確認他確實成為目前承辦者，再看可見性、其指派關係的個人郵件選項及傳送狀態。如果測試員甲是自己把工作指派給自己，也要檢查「自己的變更」。

不要將「關閉watcher郵件」解釋成退出角色或取消存取。通知偏好、watcher關係、角色成員與資料權限是不同層次。降低郵件量時，選擇符合個人需求的通知設定，比刪除協作角色或改動閱讀權限更精準。

個人通知偏好 減少雜訊並保留交接

取消watcher關係、關閉自動watch、關閉watcher活動email是不同動作：目前是否watch、之後是否自動加入、是否走郵件管道。閱讀設定前先問自己要改哪一件事，才不會誤把偏好當資料關係。

自己的變更通知也值得單獨檢查。用同一個帳號建立、指派、留言後等自己的信，可能測到的是「不通知自己」，不是團隊通知設定。可靠的隔離測試會清楚指定操作者與收件者；本教材只做推演，不要求操作真實帳號。

郵件處理器 將來信安全地變成工作

Default Reporter決定後備回報身分，CC Assignee嘗試選承辦者，CC Watchers管理關注者。三個選項名字相近但資料欄位不同，應在測試表各占一欄，不能用「預設人員」統稱。

JQL 從一句需求寫出可驗證的搜尋

=找符合單一值；IN (A, B)表示符合集合中的任一值。例如project IN (LAB, DOC)等同兩個project條件用OR連接。!=和NOT IN排除特定已存在的值，但不會自動把無值的工作算進來。若要包括未指派，應明寫assignee != currentUser() OR assignee IS EMPTY。

IS EMPTY／IS NULL測無值；IS NOT EMPTY測有值。不要把NULL放在引號裡當字串，不要把resolution != Done當成「未解決」的通用寫法。Resolution有值卻不是Done，也可能已用其他原因結案；要找未設定Resolution，應明確用resolution IS EMPTY並確認該專案欄位模型。

summary、description等文字欄位通常使用~或!~，不是一般=。日期或數值支援>、>=、<、<=等排序比較。WAS和CHANGED是歷史查詢用途，只有特定欄位支援，不能因為所有工作都有歷程就拿任意自訂欄位使用。確認官方field reference的supported operators比死背符號更可靠。

JQL 從一句需求寫出可驗證的搜尋

基本搜尋表單能表達的條件有限。複雜OR、NOT、EMPTY、某些比較運算子，或使用專案相依欄位卻未指定專案，可能無法轉回Basic。project IN (LAB, DOC)可能可由基本表單表達，與任意跨欄位OR並不相同。

看到語法錯誤時，先縮小到一個已知正確子句，再確認欄位名稱／ID、運算子支援、引號、括號配對與函式參數。看到語法合法但結果錯時，先檢查需求邏輯、無值處理、日期邊界與目前身分。這兩種錯誤不要用同一種修法。

練習不需要在Jira新增資料：用本課合成卡片先判斷入選，再寫查詢。即使使用自動產生JQL的工具，仍需用反例與邊界驗證；AI寫出的合法語法不是業務結果保證。生成工具本身屬於額外背景，ACP-120本課要建立的是你能自行解釋搜尋的能力。

篩選器 儀表板與訂閱 共享方法不等於共享資料

沒有信時先確認subscription是否存在、排程與時區是否符合、收件者是自己還是正確群組，以及空結果是否寄送。若群組不可選，確認建立者是否群組成員且有管理群組訂閱的全域能力。不要只查專案通知方案，因為這是另一種通知來源。

收到不同結果時依序比較filter本體／JQL版本、currentUser身份、Browse及安全層級，最後再看資料是否在不同時間更新和前200筆限制。若其中一人的gadget報錯，另外檢查他能否開底層filter；這不同於filter正常但只返回較少資料。

誤解一：把filter設public就能讓所有人看受限工作。資料權限仍存在，而public共享也可能洩露名稱與查詢內容。誤解二：分享dashboard就分享全部gadget資料。需分層授權。誤解三：群組訂閱永遠用建立者的currentUser。官方已明確逐收件者解算。

批次操作與搬移 先預測資料變化再確認

批次設定欄位可能把多筆原本不同值統一成同一值。先分清UI的replace、add、remove或retain等實際選項，不要用「更新」一詞掩蓋它會保留還是覆寫原值。對多值欄位尤其要檢查；若無相應追加選項，不應期待輸入一個新值會自動保留舊值。

一次變更多筆可能造成大量事件與郵件。文件的Send mail for this update若對目前使用者可用，可用來控制此次通知；但不是所有角色都可以關閉。也不要聲稱不勾它就必然阻止任何app、automation或外部通知，該選項只適用於其處理的通知路徑。

合成推演：兩筆標籤分別為legal與design，需求只要都加review。如果確認頁表示「replace with review」，結果會失去原標籤，不符合需求；應停止並改用支援追加的方式。先記錄各筆原值、目標值與通知對象，再用小集合核對，才谈擴大批次。

全站預設值與介面 先分清影響誰

Public sharing是是否允許公開分享的站台能力。打開它不會自動把現有資料公開；關閉它則不會自動撤回已經公開的filter或dashboard。要撤回既有公開分享，還要清查物件並逐項調整visibility。

合成情境：昨天建立的Dashboard A是Public，今天把Default access改Private，又把Public sharing關閉。不能因此保證A已私有。新物件的預設與未來分享能力已變，A的既有分享仍需處理。這三項設定應列成不同變更，不用一個「已關公開」概括。

類似地，修改預設dashboard不會把所有人自己建立的dashboard同步重排。管理者需確認對方看的是哪一個dashboard，再判斷是否應受影响。建立時間、物件身分與覆寫層次都是排查證據。

附件 工時與連結 三種功能的層次排查

看不到Log work時，先查該人能否閱讀工作、Work On Work Items，接著查Time tracking欄位在company-managed field configuration或team-managed work type中的可用性。若只是create/edit看不到original estimate，另查screens。不要把所有問題都歸咎於全站開關。

狀態 結案原因與優先順序 共用值的治理

一個status可被多個workflow引用；改這個status的名稱會傳到所有引用它的流程與專案，而不是只影響當前開啟的workflow。workflow複製也不應被當成已深度複製每個status；應先看共用物件關係，才決定改既有值或建立新的獨立值。

Resolution與Priority也是共用值。改名需讓使用中的團隊理解新舊詞彙的對應，並檢查JQL字面值、automation條件、報表說明和翻譯。這些是變更驗收清單，不是宣稱所有引用一定自動改寫或一定失效；只有實際檢查才能確定各種引用的行為。

合成例：兩個workflow都使用同一個Review status。設計團隊希望叫Design review，營運團隊仍需要通用Review。若改同一物件名稱，營運也會看到新名，超出需求。先評估建立獨立狀態並在特定流程替換，且對既有工作規劃必要對應，不能為了縮小範圍直接刪掉共用status。

官方明說status更新不會自動通知使用它的團隊；所以發布後還有溝通與驗收工作。名稱改善應同時更新教學指引，讓使用者知道原本Review去哪了，而不是等人報錯才解釋。

備份與匯入 先辨識工具再談還原

Import Jira Cloud文件警告：匯入entities.xml與activeobjects.xml會覆寫目的站資料庫；匯入attachments、avatars或logos也會覆寫對應媒體。不能把它說成將一個專案安全追加到仍有其他資料的站台。目的站確認、影響範圍與核准是啟動前的停止點。

文件建議把資料與媒體分成兩個匯入檔以降低逾時風險。規劃順序是：確認來源與相容性、完整性和時效；確認目的與可接受的覆寫影響；準備資料／媒體；執行前驗證；完成後抽樣檢查工作數、欄位、附件、使用者、權限、board與連結。這些是流程教學，不是要學員在正式站台按Import。

使用者合併可能讓既有帳號進入更多群組或取得額外存取；新使用者又未必自動取得app access。因此匯入後必須檢查授權，不能只測管理者自己能登入。來源Cloud的自訂郵件憑證不會完整照搬，跨應用連結也可能仍指回來源，需按核准流程重新檢查。

新Atlassian Backup and Restore的目的app必須沒有使用者資料，且同組織、同區域。封存或垃圾桶內資料仍算資料；「全部封存」不會讓app變成空。安全演練應先準備新建隔離app，不把清空或永久刪除正式資料當準備步驟。
