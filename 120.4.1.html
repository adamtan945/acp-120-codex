先認識名詞

Status：一筆工作目前所在的階段，例如 Ready、Building、Review。

Status category：把狀態歸入 To do、In progress、Done 等較高層分類；分類不等於特定狀態名稱。

Transition：允許工作從某狀態移到另一狀態的動作；可附加規則與輸入畫面。

Workflow：一組狀態、轉換及相關規則所構成的工作生命週期。

Resolution：工作結束的原因，例如完成、重複、不處理；空值表示尚未解決。

Workflow 是可走的路線，不只是畫面上的幾個方塊

合成團隊的工作從 Ready → Building → Review → Done。方塊是 status，箭頭是 transition。使用者目前在 Review，能否返回 Building，取決於是否有可用的退回轉換與是否滿足規則，不是看滑鼠能不能拖到左邊。

Transition 可以由特定來源出發，也可能是 Any status／global transition，允許從多個來源進入同一目的地。這裡的 global 指流程中的來源範圍，不是「這個使用者得到全站管理權」。Self-loop 則起點與終點相同，仍可能執行規則與後續動作。

Workflow scheme 把工作類型對應到流程。Bug 可以需要 Review，Task 可以比較簡單；同一流程也能被多專案重用。新增 workflow 後，要透過適當 scheme 指向目標 work type，才算使它真正被該類型使用。

初學者在設計時，先用自然語言寫每個狀態的進入與離開條件，再畫箭頭。若 Ready、Assigned、Open 都表示幾乎相同的待開始狀態，先問增加狀態能否帶來可採取行動的差異，避免只是讓流程更難操作。

把一個轉換拆成「可不可以用、要填什麼、通不通過、之後做什麼」

合成「Approve」轉換從 Review 到 Done。先用 condition／Restrict transitions 判斷目前這個人是否能使用，例如只准 Reviewer 角色。這是可用性檢查；在典型舊編輯器中，條件不成立時使用者不會看到轉換按鈕。

若需要當下補資料，可以設定 transition screen／Request input，要求填驗收紀錄或選 Resolution。畫面提供輸入機會，但「畫面上有欄位」本身不保證每條呼叫路徑都送入合法內容。

Validator／Validate details 檢查轉換前資料是否合格，包括剛在 transition screen 填的值。若驗收紀錄空白，validator 可拒絕完成。使用者可能看得到按鈕、開得了畫面，卻在提交時收到錯誤；這與 condition 的典型表現不同。

Post function／Perform action 則在轉換執行後處理附帶更新，例如設定 Resolution。Validator 失敗時，不應期待目的狀態或完成後動作照樣成功。設計時把「必須先滿足」放在檢查層，把「通過後寫入」放在動作層。

記憶方式不是背四個英文順序，而是問目的：「誰可以？」偏限制；「現在收什麼？」偏輸入；「輸入有效嗎？」偏驗證；「成功後改什麼？」偏動作。這是概念順序，不是允許你任意改動所有內建 post function 的系統執行順序。 現行 advanced workflow 文件特別警告：保留必要的 Generic event post function，不要修改、刪除或任意重排必要系統步驟。需要自訂事件時，依目前支援方式另外新增自訂 post function；較舊事件教學若示範修改既有 Fire a…，不能直接視為現行流程的安全步驟。

Property 是精確的 key-value 設定，不是萬用規則

Workflow property 以 key-value 形式改變 status 或 transition 的某些行為。例如在 Done status 使用官方支援的 jira.issue.editable = false，可以限制該狀態的編輯；Resolution include／exclude 可限制某轉換提供的完成原因選項。

這些設定容易和專案權限、actor 行為及一般欄位編輯交互作用。使用者有 Edit work items 權限，不表示在任何狀態都一定可編輯；反過來，property 也不是自動授予原本沒有的專案權限。

Property、condition、validator、post function 不是同義詞。若需求是「只有 Reviewer 可批准」，優先用明確的轉換限制來表達，而不是隨意貼一個看不懂的 key。每個 property 要查官方適用位置、值格式與副作用；官方也警告部分 property 可能造成問題。

本課只要求辨識用途和判斷影響，不要求背所有 property 名稱或第三方 app 的自訂擴充。沒有在隔離練習環境驗證前，不應直接把範例貼進正式共用 workflow。

Status、board column 和完成判斷是三個相連但不同的層次

Workflow 決定合法狀態與轉換；board 將查詢到的工作按狀態映射到 column。多個 statuses 可以放進同一欄，例如 Testing 和 Review 都放在「驗收中」。因此 column 數量不必等於 status 數量。

如果某個 status 沒有映射到 board 欄位，相關工作可能在此 board／backlog 消失，卻仍能透過搜尋找到。先確認 board filter、權限與 status mapping，不要把沒顯示誤當成資料刪除。

Scrum board 的完成判斷尤其要查最右欄。即使狀態叫 Done，若沒有映射到代表完成的最右欄，sprint 結束時可能被當成未完成。Kanban 的欄位映射也影響呈現與流動；特定 backlog、子篩選與隱藏完成工作設定另查相應功能。

將 Review 從一欄重新映射到另一欄，是改 board 呈現；把一筆工作從 Review 轉到 Done，是改工作狀態。兩者不能混為一談。若使用 simplified workflow，部分 board 管理動作會連帶建立狀態，這是有條件的整合行為，不能當成所有公司管理型 workflow 的規則。

Resolution 回答「為什麼結束」，不能只靠 Done 這個字

Status 表示流程位置；Resolution 表示結束原因。一筆 Bug 可以在 Done，原因是 Fixed、Duplicate 或 Won’t do。用同一個完成狀態搭配不同 Resolution，能避免為每種結案原因都增加一個狀態。

Jira 多種功能依 Resolution 是否有值判斷 resolved，例如 Created vs Resolved、Open work items 篩選，以及部分刪除線呈現。若 Done 但 Resolution 空白，這些功能可能仍把它視為未解決；若重新打開仍留 Fixed，則可能已在 In progress 卻帶刪除線。

Unresolved 是沒有 Resolution 值的狀況。不要建立一個真的叫「Unresolved」或「None」的 Resolution 選項來假裝空白：只要選了這個實際值，它仍是非空，會造成錯誤判斷。真正清除是讓欄位回到空值。

同時也不要反過來宣稱「所有 Jira 報表只看 Resolution」。Board 最右欄有自己的完成判斷，status category 又提供分類。可靠的完成設計要讓狀態、分類、board 映射與 Resolution 彼此一致，而不是用其中一項取代全部。

完成轉換：固定原因自動設值，多種原因讓使用者選

如果某條「完成修正」轉換的業務意義固定，適合由 workflow 動作設定 Resolution = Fixed。若同一條「關閉」可能代表完成、重複、不處理，則可透過 transition screen 請使用者選擇，再以驗證規則確保必要資料。

新編輯器的文件路徑為選 transition → Add rule → Perform action → Update an issue field → Resolution，再 Update workflow。舊編輯器可能是 Post functions → Update Issue Field。這裡教的是對應概念，實際按鈕依租戶版本確認。

盤點所有通往結束狀態的路徑，不能只修一條常見的 Complete，而漏掉 Cancel、Reject 或 global transition。若有人可透過 API 或 automation 轉換，也要驗證該路徑仍能正確設值；screen 只提供人工輸入，不是涵蓋所有路徑的資料保證。

通常不要把 Resolution 放在一般 Create／Edit screen 讓未完成工作隨手選成「已解決」。也避免同時由 workflow 與另一條 automation 互相搶寫不同 Resolution。指定清楚的寫入責任，再以正向、拒絕與替代路徑測試。

重新開啟：把狀態與 Resolution 一起帶回工作中

重新開啟不是只把 Done 改回 In progress。完成原因應被清除，讓依 Resolution 判斷的功能也恢復未解決口徑。舊編輯器可見 Clear Field Value post function；現行 Edit a workflow’s rules 文件則說明以 Update a work item field 的 Perform action 在重新開啟路徑清除 Resolution，並確認順序正確。實際空值選項依租戶介面查核。

合成完整路徑：Review → Complete → Done 時設定 Fixed；Done → Reopen → In progress 時清除 Resolution。若有 Done → Rework 與 Done → Reopen 兩條不同路徑，都要檢查清除邏輯。

更新 workflow 是在修往後會執行的行為，不會自動走訪所有既有錯誤工作並修資料。若歷史上已有 In progress 且 Resolution 非空的工作，需另外找出範圍、確認業務狀態、評估通知與報表影響，再安排授權過的資料修正。

本教材的自我檢查只讀合成資料，不要求在正式站台做 bulk transition、刪除或回填。能指出「未來規則已修、歷史資料尚未修」是管理者的重要驗收能力。

編輯與發佈：先確認共享範圍，再選對版本流程

公司管理型 workflow 常被多個專案或類型共用。發佈前先列出相關專案、類型、目前狀態及可達路徑；若只是某個團隊的特殊需求，評估複製流程並只調整該範圍的 scheme，而不是直接修改所有共用者。

傳統編輯器常有 active workflow draft，再 Publish draft；新編輯器文件則支援在同一介面編輯，按 Update workflow 發佈支援的變更。不要死背「所有 active workflow 的變更一律需要先複製」或「編輯一下立即影響使用者」這類過度概括。

若移除使用中的狀態或更換 workflow，要考慮既有工作如何映射到仍有效的狀態。預覽一張漂亮流程圖不代表資料遷移、轉換規則與 board mapping 已驗證。建議記錄變更前後、保留回復方案，並在隔離練習範圍先驗證。

紙上驗收：四筆資料、兩條轉換、兩種完成口徑

先以紙上推演完成。若要實際操作，只能使用另行授權、隔離且可丟棄的練習環境；使用合成資料，先確認沒有共用正式設定或真實通知收件者。這些步驟是文件查核的練習設計，並非已替你執行或驗證成功。

自我檢查與理由

自我檢查

流程圖畫了 Ready 與 Done，但沒有任何可用轉換連到 Done，能否靠狀態名稱完成工作？

查看答案與理由

不能。要有適用轉換，而且使用者或 actor 需滿足權限與轉換規則。

自我檢查

Approve 需檢查使用者剛輸入的 Approval note，應使用 condition 還是 validator？

查看答案與理由

Validator／Validate details。Condition 不用來驗證尚未在轉換畫面蒐集的輸入。

自我檢查

一個使用者有 Edit work items，但只有在 Done 無法編輯，除了權限方案還應查什麼？

查看答案與理由

查 Done status 的 workflow property 或其他狀態限制，例如是否設定不可編輯；不要先把所有人升成管理者。

自我檢查

Testing 與 Review 同在「驗收中」column，是否代表兩個 status 已合併？

查看答案與理由

沒有。它們仍是不同狀態，只是此 board 將兩者映射到同一欄。

自我檢查

一筆工作在 In progress，但 Resolution = Fixed。Created vs Resolved 類報表可能如何解讀它？

查看答案與理由

它可能仍被當作 resolved。要檢查重新開啟路徑是否清除 Resolution，不能只改狀態名稱。

自我檢查

有 Complete 和 Cancel 兩條路進入 Done，只在 Complete 設 Resolution，配置完整嗎？

查看答案與理由

不完整。Cancel 也需要符合其結案語意的 Resolution；所有通往結束狀態的路徑都應檢查。

自我檢查

今日加上 reopen 清除 Resolution，昨天已重新開啟卻留 Fixed 的工作會自動修好嗎？

查看答案與理由

不會因新增規則就自動修好。要另外辨識歷史資料並規劃受控修正。

自我檢查

同一 workflow 用在三個專案，想只讓其中一個多一道 Review，修改前最重要查什麼？

查看答案與理由

查 workflow 及 workflow scheme 的共享使用範圍，評估是否須複製並限定對應；不能把眼前專案當成唯一受影響者。
