管理者分工與最小權限

Jira把一份待完成的工作記成工作項目，團隊在專案中處理它。管理者的工作則是決定這個環境如何運作：誰能使用、要填哪些資料、哪些狀態能互相轉換，以及大家收到哪些通知。這些事情跨越不同範圍，因此「幫我開管理權限」不是完整需求。

先把請求改寫成具體動作。例如「需要幫專案加入維護人員」、「要調整三個專案共用的工作流程」和「要指定另一位組織管理者」，雖然都叫管理，處理者並不相同。選角色時看的是要操作的物件與影響範圍，而不是職稱有多高。

以下情境中的角色是權限安排，不是公司職位。主管可以只有一般使用權；工程師也可能被正式指定管理Jira。學會這個區分，可以避免為了一個小需求就給出超出需要的控制權。

管理者分工與最小權限

Organization admin（組織管理者）主要處理組織層級的使用者、群組、應用程式與安全管理。Jira admin則處理Jira自身的設定，例如建立公司管理型專案，管理欄位、工作流程及可重用方案。Project admin（目前介面也叫Space admin）處理特定專案中允許他管理的內容。

把它想成三張不同工作單：組織層的「人與存取」、Jira層的「共用設定」、專案層的「本專案安排」。同一個人可能同時持有兩張或三張工作單，但這不代表每種角色天然等同。

在公司管理型專案中，Jira管理員可在方案引用一個角色，再讓各專案管理者維護該角色在本專案的成員。如此不需要為每次團隊換人都改共用方案。反過來，專案管理者也不應因為能指定本專案的維護者，就被視為可以改整個組織的群組成員。

管理者分工與最小權限

官方文件把集中式（Centralized）與原始（Original）使用者管理介面分開說明。集中式介面的Users位於Atlassian Administration的Directory；原始介面則從Apps中的特定站台找Users。看到不同選單時，先辨認介面，不要直接照舊截圖點選。

以目前集中式管理為例，組織管理者可以在使用者資料中指定組織管理角色；授予Jira應用程式管理角色時，要檢查Jira Administration的App admin設定。正式操作前需確認目標組織、站台與人員身分，因為相同顯示名稱不保證是同一個帳號。

角色授予完成後，要檢查的是預期管理工作是否可做，而不是只看到「管理員」三個字就結束。驗證也應包含不該擁有的能力：例如只需維護一個專案的人，不應因此能變更組織安全政策。以下步驟是文件導覽與隔離環境中的人工驗證順序，不會在本教材內執行授權。

管理者分工與最小權限

虛構的晨光團隊有WEB與APP兩個專案。第一張需求是「指定另一位組織管理者」，第二張是「修改兩專案共用的欄位與流程設定」，第三張是「更換WEB專案中Reviewers角色的成員」。

第一張從組織管理流程處理；第二張交由可管理Jira共用設定的人；第三張在既有方案已授權給角色的前提下，從WEB的角色安排處理。這個拆解保留共用規則，也讓各專案能處理自己的日常人員變化。

如果第三張需求其實是「建立一個全新的角色定義，讓所有專案都可使用」，範圍就改變了。角色定義與某專案中誰扮演該角色不同，不能只因名字相似就交給同一層級。

全域權限與群組授權

全域（global）不是「權限最大」的同義詞，而是這項能力的設定範圍在整個Jira站台。有人需要分享報表，有人要管理群組訂閱，有人要批次操作工作項目，這些都是跨專案功能，但不必因此讓他管理全部Jira設定。

想像大樓入口提供某種工具的使用資格，進到每個房間仍要過該房間的門禁。Make bulk changes開啟批次作業能力，實際能改哪些工作項目仍依專案權限與其他限制。這是理解用的類比，不是Jira內部程式的完整授權演算法。

解題時先把需求拆成「跨專案功能」和「對資料做什麼」。若只看見bulk就勾選全域權限，忽略目標工作項目的Edit、Move或Transition等條件，仍無法說明為什麼有些資料可改、有些不可改。

全域權限與群組授權

Administer Jira用來管理Jira的共用組態。Browse users and groups與人員選擇、搜尋和提及的可見範圍有關。Share dashboards and filters讓使用者分享這些報表物件；Manage group filter subscriptions則處理群組篩選器訂閱。它們解決的是不同工作，不應一律給成管理者。

Make bulk changes用在多張工作項目的編輯、移動、刪除或轉換，但仍需相符的局部權限。Create team-managed spaces允許建立團隊管理型專案，不能當成建立公司管理型專案的通行證。

目前官方頁面還列出某些較新的全域功能。先學會按用途區分，再回到本考綱需要的管理與使用情境；不要把目前介面新增的一項開關自動視為新增考點。

全域權限與群組授權

在全域權限頁，授權對象是群組。你不是在每個專案重複設定這項全站能力，而是先建立符合職責的人員集合，再把該能力授予集合。群組中有人加入或離開，會改變他是否從這條路徑取得能力。

這也表示一個群組名稱本身沒有魔法。「report-editors」只有在相關設定確實引用它時，才形成授權關係。把某人放入一個聽起來很厲害的群組，不能保證他有你想要的能力；相反地，名字普通的群組也可能被授予重要權限。

公司管理型的project role則在各專案解析當地成員，很適合可重用方案。全域群組授權和專案角色授權並不是同一種入口，應根據功能所在層級選擇。

全域權限與群組授權

以「讓指定的報表維護者分享篩選器」為例，先列出應該獲准的人，再查他們目前屬於哪些群組。確認已有適當群組後，才在全域權限頁檢查該群組是否得到需要的能力。

目前管理介面可由Jira的System相關設定進入Global permissions；精確位置會隨導覽更新。教材的重點是辨認權限名稱、授權群組與影響範圍，實作時用本節的官方文件對照現場介面。

變更後用一個應該獲准與一個不該獲准的測試身分驗證。若移除某群組後能力仍存在，檢查其他群組或管理角色的授權，不要為了讓測試看起來通過就一次移除所有群組。

專案權限與重用方案

把專案想成共用工作區：閱讀、建立工作項目、編輯、指派、留言、轉移狀態與管理設定，是不同的能力。專案權限（project permissions；目前 UI 也稱 space permissions）回答「誰能在這個工作區做哪件事」。能登入 Jira，並不等於在所有專案都有這些能力。

公司管理型（company-managed）的權限方案（permission scheme）是一份可重用的授權規則。同一份方案可以連到數個專案；方案中的「Developers 角色可編輯」會在每個專案分別查該專案 Developers 裡有哪些人。你應先辨識規則本身，再辨識專案中的角色成員，避免只看人的職稱猜權限。

團隊管理型（team-managed）把存取層級與角色放在該專案內管理，不能把公司管理型的權限方案直接套上去。兩者都需要控管存取，但設定物件、管理入口與可重用範圍不同。

專案權限與重用方案

Open、Limited、Private 是團隊管理型的存取層級。官方目前的規則是：Open 讓站台上的人取得 Member 的基礎能力；Limited 讓站台上的人取得 Viewer 的基礎能力；Private 只讓被加入的人存取，Jira 管理員仍有文件描述的管理與可見性例外。這裡的 Open 指站台內的存取，不代表匿名網際網路使用者。

Member 與 Viewer 的差異不只是名稱。Viewer 著重閱讀與留言，並不等於可以建立、編輯工作；Member 可以參與工作。Administrator 則可管理專案設定。自訂角色提供更細的組合，但若存取層級已給某人基礎能力，就不能假設另加一個較弱的角色會撤銷既有能力。請從所有授權來源一起判讀。

操作時先進入該專案的 Space settings／Project settings → Access，查看存取層級、直接加入的人及其角色，再檢查自訂角色的能力。Free 方案在角色、權限與工作項目安全性方面有限制；題目若提到 Free，不能預設付費方案的細緻設定都存在。

專案權限與重用方案

Browse Projects／Browse spaces 是閱讀專案與其工作項目的基本入口；Create Issues／Create work items 是建立；Edit Issues／Edit work items 是修改一般欄位；Assign Issues／Assign work items 是更改承辦者；Assignable User／Assignable users 決定誰可被選為承辦者。能指派與能被指派是兩個不同角色，不能互相代替。

Transition Issues／Transition work items 控制能否執行工作流程轉移。工作流程條件或驗證器仍可能再限制某一次轉移，因此「有 Transition 權限」不是所有箭頭必定可按的保證。Schedule Issues／Schedule work items、Resolve Issues、Close Issues 與管理 sprint 等能力也各有目的，不能用一個 Edit 權限概括。

Administer Projects／Administer spaces 用於專案管理，不能直接推論可以改所有全站共用方案。Jira 管理員管理共享設定；專案管理員在授權範圍內管理本專案。對 workflow 或畫面的有限本地編輯能力，還要符合未共用等條件，不能把例外當成對全站任意修改的能力。

建立權限清單時以「人要完成的動作」為起點。例如服務窗口只要閱讀和留言，不必為了方便就加入管理員群組；開發人員需編輯與轉移，不表示需要刪除資料或管理共用方案。最小權限是把必要能力給足，而非只給一個看起來很高的角色。

專案權限與重用方案

移動工作項目到另一個專案，不是只在目的地按「接收」。操作人需要來源專案的 Move work items，以及目的地的 Create work items；還應具備閱讀與完成欄位對應所需的存取。目的地的工作類型、必填欄位與流程也可能要求對應，這些是設定條件，不是再多給一個管理員頭銜就自動完成。

跨專案連結需要考慮連結兩端。官方權限互動文件要求相關專案具備 Link work items，並能存取相關工作項目；全站工作項目連結功能也必須啟用。這是全站開關與專案授權的交集：關閉功能時，多給 Link 權限不會讓功能自行開啟。

Manage sprints 不會自動提供排程、編輯所有工作項目的權限；多專案 board 的 sprint 管理又可能涉及 board 篩選範圍中的數個專案。診斷時先釐清題目是在管理 sprint，還是在更改 sprint 內某張工作項目的欄位，不要把容器操作與內容操作混成同一件事。

閱讀方面還要加上第1.5節的工作項目安全性。Browse 是第一道檢查；若工作項目有安全性等級，還要符合該等級授權來源。共享 filter、dashboard 或 board 不會替讀者補足底層工作項目的權限。

單一工作項目的安全性：誰能看見這張單？

安全性方案（security scheme）像一套可選的閱讀限制規則集；安全性等級（security level）是規則集中的一個選項，例如「內部協作」或「限審核團隊」。等級名稱只是標籤，不代表數字較大就必然包含數字較小的所有人。實際可見者由授權來源決定。

公司管理型專案先關聯一份安全性方案，工作項目再選擇該方案中的等級。管理員應先定義用途及允許來源，再決定預設值與誰可以更改等級。不能只建立一個名為Confidential的標籤、工作類型或board欄，就認為閱讀限制已生效。

這個機制主要控制特定工作項目的可見性，不取代帳號存取、專案權限或每一項操作權限。即使看得到，編輯、留言、轉移或設定安全性等級仍需要相應能力。完整需求要把「能不能看」與「看見後能做什麼」分開。

選擇專案型態與重用方式

Jira 的工作項目是一筆需要追蹤的工作，例如修正登入錯誤或準備上市文案；它有摘要、狀態、承辦者等資料。專案（project，現稱 space）把一組工作及其設定組織在一起。board 則用欄與卡片呈現工作，讓你看出哪些尚未開始、進行中或已完成。

board 是觀看與安排工作的介面，不是權限方案，也不是資料副本。尤其公司管理型的 board 可由 filter 決定顯示範圍；同一筆工作可以出現在不同檢視。對公司管理型而言，選擇 board 的工作節奏與選擇專案的管理型態，是相關但不同的兩個決定。

團隊管理型重視團隊自行設定與本地自主性；公司管理型重視集中治理與跨專案共用方案。這不是「小公司一定用團隊管理、大公司一定用公司管理」的公司規模分類，而是設定的所有權與重用方式。

選擇專案型態與重用方式

團隊管理型讓專案管理員在專案內調整工作類型、欄位、流程、角色等設定。各專案的設定可以獨立演進；不需要為了每個小調整都先修改中央共用方案。代價是跨團隊一致性要另行治理，不能假設一個專案改完，其他專案會跟著更新。

公司管理型由 Jira 管理員管理可重用的工作類型、workflow、畫面、欄位、權限及通知等方案。多個專案可使用同一份設定，適合需要一致流程與管理標準的情境；同時必須評估共享變更的影響範圍。專案管理員仍能管理被授權的本地事項，並不表示所有事情都得由組織管理員處理。

功能會隨Jira Cloud更新。目前官方Add fields段落描述可重用符合條件的Jira管理員建立欄位；欄位context須符合Any work type等條件，並核對專案範圍、支援型態及實際介面。另一段仍有舊式概括禁用文字，因此教材明確保留版本差異，不教成「永遠不能重用」或「所有共用欄位都能用」。團隊管理型本地建立欄位仍須按本地範圍理解。

管理型態不能用一個切換按鈕就當作原專案原地轉換。官方建議建立目標管理型態的專案並移動工作項目，同時處理欄位、狀態及其他設定對應。資料移動與功能差異有注意事項，應以專門遷移文件規劃，而不是在正式站台為了試看看直接搬動。

選擇專案型態與重用方式

Scrum 使用 sprint，把選定工作放進一段有時間界線的期間，團隊規劃目標並在期間結束檢視結果。Jira 的 sprint 不是工作項目的狀態，也不是一個軟體版本；它是工作安排的時間容器。

Kanban 著重持續流動與可視化工作，不要求所有工作先放進固定期間的 sprint。若團隊持續接收需求並隨時拉取下一項，Kanban 往往是較自然的起點；若題設明確要求以固定兩週期間規劃與檢視，Scrum 的 sprint 模型較直接。

版本（version）回答「哪些工作屬於同一次交付／發布」，不回答「團隊這兩週做哪些工作」。Kanban 也可以管理版本；Scrum 的 sprint 結束不必等於版本發布。一個版本可能跨數個 sprint，某個 sprint 也可能處理不同版本的工作。

考題給需求時，把問題拆成兩欄：工作節奏要固定期間還是持續流動；設定治理要本地自主還是中央共用。不能因為看到 Kanban 就推論一定是團隊管理型，也不能因為看到公司管理型就推論一定使用 Scrum。

版本生命週期

版本（version）用來把工作項目連到一次產品交付或發布，例如「2026.10 行動版」。它是一個有名稱及相關日期／說明的專案設定物件，不是把每張工作項目的Status改成同一個字。

sprint 是一段工作時間，version 是交付分組。團隊可能連續三個 sprint 才完成一個版本，也可能在同一個 sprint 為兩個產品版本處理工作。Kanban 一樣能管理版本，因此發布不是 Scrum 專用功能。

版本生命週期

發布（release）把版本標記為已發布並記錄相應資訊；它本身不是把所有相關工作項目自動走完workflow。狀態、Resolution與版本發布旗標是不同資料，必須分別理解。

發布檢查會讓你看到版本裡未完成的工作。官方流程提供處理未完成工作的選項，例如保留在即將發布的版本，或移至另一個版本；應依題設需求與實際可用介面選擇。選擇保留未完成工作不表示那些工作因此完成，而是已發布版本仍可關聯未完成項目。

如果產品負責人說「本次只交付已完成部分，剩餘工作延後」，管理者應先確認哪些工作應保留在本次交付，哪些改到後續版本，再進行發布。若合規要求發布前不得有未完成項目，則要先完成或移除／重新安排這些項目；不要用按下Release掩蓋狀態問題。

發布後的報表要以資料含義解讀：已發布版本仍可能包含未完成工作，工作流程Done也未必代表實際發布。當兩者不一致，先檢查決策與欄位，不直接斷言系統計算錯誤。

版本生命週期

合併（merge）用於把一個版本併到另一個版本，讓相關版本參照移到目標版本。先確認來源與目標，避免把原本不同交付意義的資料混在一起；合併的意義不是把工作項目本身合成一張。

刪除版本（delete version）移除的是版本物件。官方管理介面會要求處理工作項目的相關版本參照，例如移到另一個版本或移除參照；這不是刪除這些工作項目。若題目問歷史資料還在不在，先區分「版本欄位參照」與「工作項目本體」。

發布（release）與取消發布（unrelease）改變版本的發布狀態；封存版本（archive version）則是降低它在日常選擇中的可用性，保留歷史用途。封存不等於取消發布，刪除也不等於封存。實際選單因版本狀態而異，應先讀操作名稱與確認內容。

封存版本、封存專案及封存工作項目是不同功能；本節只談版本。不要把第7.4節專案封存與備份匯入的行為套在版本上，也不要以版本封存當作敏感工作項目的閱讀安全控制。

元件與自動指派

Jira component（元件）可把同一專案內的工作按子系統、功能區或責任範圍分類，例如API、Web、Mobile。工作項目可選擇一個或多個元件，幫助查詢、整理與設定預設指派。

工作類型與方案：讓每種工作走對設定

在公司管理型專案，Jira 管理者建立工作類型，並選擇它是 standard 還是 subtask。Standard 通常位於 Story 這一層；Subtask 需要父工作。不要把新類型取名「Epic 2」就當成新增了 Epic 階層。進階階層設定屬另一個機制，本課不把付費方案的階層擴充當成基本步驟。

工作類型方案（issue type scheme）像一份專案可用分類清單。它決定可選類型、建立時預設類型，以及選項順序。建立「Audit Review」後，若沒有加入目標專案採用的方案，使用者仍可能無法在該專案建立此類型。

操作思路是先盤點既有類型與方案，再建立真正缺少的分類，將其放進新的或既有方案，最後確認方案套用到目標專案。現行管理入口為 Settings → Work items → Work types / Work type schemes；舊介面可能仍寫 Issues / Issue types。方案可被多個專案共用，編輯前先查使用者清單。

合成情境：兩個產品團隊需要同樣的 Bug、Story、Task，適合共用方案。只有內控團隊需要 Audit Review 時，先比較建立專屬方案與修改共用方案的影響。複製方案讓清單分開，不代表把原有工作類型本體也複製成新的物件。

工作類型與方案：讓每種工作走對設定

畫面線有兩層：工作類型畫面方案（issue type screen scheme）將 Bug 對應至某個 screen scheme；screen scheme 再把 Create、Edit、View 操作對應到 screen。Screen 裡才列出欄位與分頁。把欄位加進某個看似名稱正確的 screen，若對應鏈沒有走到它，使用者就不會看到預期結果。

傳統欄位設定線則由 field configuration scheme 將 Bug 對應到 field configuration，後者定義必填等欄位行為。這與 custom field context 的適用專案／類型、預設值／選項不同；第 3.2 課會把它們接起來。

Context 像是欄位的使用範圍與內容規則。它能限定專案、工作類型，並針對範圍提供選項與預設值。Global context 表示廣泛適用；專案限定的 context 則讓同一欄位在某些專案使用特定設定。

公司管理型 workflow：從狀態、規則到正確結案

合成團隊的工作從 Ready → Building → Review → Done。方塊是 status，箭頭是 transition。使用者目前在 Review，能否返回 Building，取決於是否有可用的退回轉換與是否滿足規則，不是看滑鼠能不能拖到左邊。

Transition 可以由特定來源出發，也可能是 Any status／global transition，允許從多個來源進入同一目的地。這裡的 global 指流程中的來源範圍，不是「這個使用者得到全站管理權」。Self-loop 則起點與終點相同，仍可能執行規則與後續動作。

Workflow scheme 把工作類型對應到流程。Bug 可以需要 Review，Task 可以比較簡單；同一流程也能被多專案重用。新增 workflow 後，要透過適當 scheme 指向目標 work type，才算使它真正被該類型使用。

初學者在設計時，先用自然語言寫每個狀態的進入與離開條件，再畫箭頭。若 Ready、Assigned、Open 都表示幾乎相同的待開始狀態，先問增加狀態能否帶來可採取行動的差異，避免只是讓流程更難操作。

公司管理型 workflow：從狀態、規則到正確結案

合成「Approve」轉換從 Review 到 Done。先用 condition／Restrict transitions 判斷目前這個人是否能使用，例如只准 Reviewer 角色。這是可用性檢查；在典型舊編輯器中，條件不成立時使用者不會看到轉換按鈕。

若需要當下補資料，可以設定 transition screen／Request input，要求填驗收紀錄或選 Resolution。畫面提供輸入機會，但「畫面上有欄位」本身不保證每條呼叫路徑都送入合法內容。

Validator／Validate details 檢查轉換前資料是否合格，包括剛在 transition screen 填的值。若驗收紀錄空白，validator 可拒絕完成。使用者可能看得到按鈕、開得了畫面，卻在提交時收到錯誤；這與 condition 的典型表現不同。

Post function／Perform action 則在轉換執行後處理附帶更新，例如設定 Resolution。Validator 失敗時，不應期待目的狀態或完成後動作照樣成功。設計時把「必須先滿足」放在檢查層，把「通過後寫入」放在動作層。

記憶方式不是背四個英文順序，而是問目的：「誰可以？」偏限制；「現在收什麼？」偏輸入；「輸入有效嗎？」偏驗證；「成功後改什麼？」偏動作。這是概念順序，不是允許你任意改動所有內建 post function 的系統執行順序。 現行 advanced workflow 文件特別警告：保留必要的 Generic event post function，不要修改、刪除或任意重排必要系統步驟。需要自訂事件時，依目前支援方式另外新增自訂 post function；較舊事件教學若示範修改既有 Fire a…，不能直接視為現行流程的安全步驟。

公司管理型 workflow：從狀態、規則到正確結案

Workflow 決定合法狀態與轉換；board 將查詢到的工作按狀態映射到 column。多個 statuses 可以放進同一欄，例如 Testing 和 Review 都放在「驗收中」。因此 column 數量不必等於 status 數量。

Scrum board 的完成判斷尤其要查最右欄。即使狀態叫 Done，若沒有映射到代表完成的最右欄，sprint 結束時可能被當成未完成。Kanban 的欄位映射也影響呈現與流動；特定 backlog、子篩選與隱藏完成工作設定另查相應功能。

公司管理型 workflow：從狀態、規則到正確結案

Status 表示流程位置；Resolution 表示結束原因。一筆 Bug 可以在 Done，原因是 Fixed、Duplicate 或 Won’t do。用同一個完成狀態搭配不同 Resolution，能避免為每種結案原因都增加一個狀態。

Jira 多種功能依 Resolution 是否有值判斷 resolved，例如 Created vs Resolved、Open work items 篩選，以及部分刪除線呈現。若 Done 但 Resolution 空白，這些功能可能仍把它視為未解決；若重新打開仍留 Fixed，則可能已在 In progress 卻帶刪除線。

Unresolved 是沒有 Resolution 值的狀況。不要建立一個真的叫「Unresolved」或「None」的 Resolution 選項來假裝空白：只要選了這個實際值，它仍是非空，會造成錯誤判斷。真正清除是讓欄位回到空值。

同時也不要反過來宣稱「所有 Jira 報表只看 Resolution」。Board 最右欄有自己的完成判斷，status category 又提供分類。可靠的完成設計要讓狀態、分類、board 映射與 Resolution 彼此一致，而不是用其中一項取代全部。

團隊管理型 workflow：為不同工作設計清楚的路徑

合成團隊維護門市預約服務。Task 是例行改善，走 To do → In progress → Done；Bug 則要先 Triage，再 Fixing、Verification、Done。差異是 Bug 需要額外診斷與驗證，而不只是卡片顏色不同，因此分開流程有實際理由。

公司管理型通知 從事件到正確收件者

通知的目的是讓需要接手工作的人知道變更。先從業務句子開始：「設計完成時，請負責驗收的人檢查」。再拆成發生什麼、誰需要知道、在哪些專案適用，以及是否能讀這筆資料。若一開始就把所有群組加到每個事件，會讓大家收到大量不需要的信，反而錯過真正的交接。

篩選器 儀表板與訂閱 共享方法不等於共享資料

一段JQL是查詢；儲存後的filter記住條件與名稱；dashboard是一張放gadget的頁面；subscription是何時把filter結果送給誰。它們相互關聯，卻不是同一個權限設定。共享dashboard不會自動共享它引用的每一個filter。

一份「My open work」filter可讓不同人使用相同方法，卻看到各自負責的工作。對多人共享時應清楚命名用途與欄位定義，例如「LAB 本週待覆核」，避免把個人角度的currentUser()條件命名成「全部團隊工作」。

儲存filter不是把目前搜尋結果固定成報表截圖。資料值、權限或currentUser上下文變動時，再執行會得到不同集合；需要固定交付物時應另行設計有時間與範圍標示的報表，不能以filter連結保證內容永遠相同。

批次操作與搬移 先預測資料變化再確認

批次可以edit、transition、move、delete、watch或unwatch。Edit改欄位；transition走流程；move更換專案或類型；delete移除工作及關聯資料。不要為了改狀態就直接當作任何欄位可編輯，也不要把搬移視為複製。

文件路徑是Search→View all work items，執行精確搜尋，再由More actions→Bulk change選工作、作業與值，最後審查。JQL結果數不一定等於最後勾選數，批次確認前要核對實際keys、數量與目標。查核日文件上限為一次1000筆；上限不是安全建議，更不表示應一次選滿。

合成案例：將LAB三筆漏填Priority的Task改成Medium，應先用project與確切keys或充分條件縮小範圍，選Edit，再確認值。若只是追蹤這三筆，應選watch；若只是讓完成工作不出現在board上，先檢查board和狀態設計，而不是選delete。

全站預設值與介面 先分清影響誰

管理者可在Settings→System→Default user preferences設定Email format、每頁工作項目數、Default access、自己的變更通知與Autowatch。官方說使用者帳號建立時套用預設，個人可以再調整支援的偏好。設計預設時先考慮大部分新使用者，避免把一人的習慣強套全站。

Default access決定新filter與dashboard的預設分享選擇；Private適合先完成內容再按核准對象共享。更改預設不等於把所有舊filter重新設權。Email format則有文件明示的Apply強制功能，使用後個人無法再改該項，不能把此例外擴張成所有預設都有相同效果。

實作前記錄原值、要改的對象與效果。例：希望新同仁預設不收到自己的變更通知，先改對應預設，再用新帳號建立情境驗證；不能用已自訂偏好的舊帳號當唯一測試，然後以「沒變」判定設定失敗。

附件 工時與連結 三種功能的層次排查

附件通常讓團隊保留截圖或規格。Jira Cloud預設啟用附件，但仍可在Settings→System→Advanced→Attachments檢查全站設定。Create Attachments決定誰能新增；Delete Own Attachments決定誰能刪自己上傳的檔，不代表可刪別人的檔。建立工作時Attachment欄位也不能被field configuration隱藏。

單檔大小與整體儲存額度不同。查核日文件預設單檔上限1GB、最大可設2GB；站台方案另有儲存額度。郵件匯入的單封25MB又是獨立限制，因此把全站上限提高不會讓所有25MB以上郵件自動可處理。這些數字是版本化產品資訊，正式作業需重查。

合成排錯：50MB圖片低於設定的100MB單檔上限，別人能上傳但測試員甲不行。先比較Create Attachments與欄位設定，不要立刻提高全站上限。若全員只能在建立畫面找不到附件，則先查該work type使用的Attachment欄位是否被hidden。

附件 工時與連結 三種功能的層次排查

Original estimate是開始時的估計，Remaining estimate是目前預估還要多少，Time spent彙整已記錄的實際工時。Story points則是相對估算，不能隨意視為小時。想讓團隊記實際工時，要檢查Work On Work Items及Time tracking欄位；想讓Scrum報表以點數估算，則另查board估算設定。

現行Cloud具體文件說time tracking一直啟用：company-managed以field configuration顯示／隱藏Time tracking，team-managed以work type新增／移除該欄位控制使用。文件前言仍有disable/re-enable歷史措辭，不能因此教一個不存在於當前路徑的全站停用按鈕。

若要在create/edit輸入original estimate，company-managed需要相關screens包含Time Tracking。全域設定在Settings→Work items→Time Tracking，定義每天工作時數、每週天數、顯示格式與未指定單位時的default unit。這是在定義時間的輸入／顯示規則，不等於設定每位員工的值班日曆。

狀態 結案原因與優先順序 共用值的治理

同一筆工作可以同時是High priority、In Review status、Resolution尚未設定。Priority回答先處理多重要；Status回答現在走到哪裡；Resolution回答為何結束。想表示客戶問題很急，應調Priority，而不是把狀態改成Urgent再讓流程與報表難以解讀。

Status category把多個細部狀態彙整。例如Writing與Review都屬In progress，不代表兩者是同一個status。改名Review→Peer review只是名稱變更；改category到Done則改變它的分類語意，應分別審查。

Resolution空值代表尚未設定結案原因。不要新增名為Unresolved或None的Resolution想表示未完成：它本身仍是有值，與真正空值不同。完成狀態也不應只憑名字判斷；company-managed workflow應在適當結案transition設定Resolution，報表才有一致依據。

備份與匯入 先辨識工具再談還原

若需求是把另一個工作追蹤工具的二十列Task帶入測試專案，CSV可表達Summary、Description、work type等欄位並做對應。若需求是用完整Jira Cloud備份恢復站台，才研究Backup Manager與Import Jira Cloud。CSV不是整站設定備份，也不能從CSV欄位推論專案封存旗標。

若來源是Server或Data Center，先查當前支援的遷移路徑，例如JCMA，不應看到歷史文件有XML字樣就假設所有舊入口仍適用。若來源是另一個Cloud且採Copy Data，這是另一套遷移機制。來源平台＋輸出格式＋匯入工具三者都寫出來，才有辦法回答資料會怎樣。

Atlassian Backup and Restore是目前產品補充，用來避免把兩種備份工具混為一談；它不是把2025考綱改成一套未公布的新範圍。官方FAQ明確說兩種備份格式互不相容；工具名字都含backup不代表ZIP或內容可以互相還原。

備份與匯入 先辨識工具再談還原

Backup Manager Cloud備份可包含工作項目欄位、留言、使用者群組設定、board/sprint與專案配置。attachments、avatars、logos等媒體需選擇包含。資料部分位於entities.xml與activeobjects.xml，媒體另在相應資料夾；只有XML不表示圖片檔本體也已備份。

文件查核路徑是Settings→System→Backup manager→Backup for cloud。規劃時選擇是否含媒體，等待備份完成，再下載並核對完整性、時間與保護方式。含附件、頭像或logo的備份需間隔48小時；不要把純資料備份的頻率假設套到媒體備份。

傳統Backup Manager不自動包含automation flows、第三方app與app data、app access設定等資料。Automation可按官方另行匯出，但那是分開步驟。備份計畫要寫「哪一類由哪種工具保護、何時驗證能恢復」，不要只記一個成功下載的檔名就宣布全站可恢復。

截至2026-10-05，官方已宣布2026-01-22起Backup Manager僅接受30天內備份進行還原。因此保存很久的ZIP即使可解壓，也不保證符合還原時效。頁面仍包含已宣布停用的Backup for server舊段落；本課不把它當現行Cloud→Data Center操作，也不教刪除team-managed專案來遷就舊路徑。
