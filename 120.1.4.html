先看懂這張圖

同一方案，不同角色成員

權限方案寫的是誰可做哪種動作，專案角色再於各專案解析成當地成員。閱讀、編輯和指派是不同能力；共享方案前先看引用範圍，不能把能看卡片當成能改工作。

用一個例子理解

合成LAB與DOC共用LAB-PERM方案：Developers可閱讀與編輯，Viewers僅閱讀。小安在LAB是Developer、在DOC是Viewer；他能改LAB-1，卻不能因角色名稱相同而改DOC-1。

動手驗證

驗證Viewer與Developer的差別

文件查核設計；未租戶實測。完成下列步驟後，以你看到的結果判斷是否成功。

這次要驗證

  • 先預測：Browse有了是否就能編輯？
  • 先預測：角色成員換人是否一定要改共用方案？

準備環境

角色
  • Jira管理員：建立及關聯獨立permission scheme。
  • LAB專案管理員：設定既有測試帳號的角色；甲、乙：已有Jira使用權的測試帳號。
方案與功能
  • Jira Standard、Premium或Enterprise；Free不可編輯此類scheme與角色。
  • 公司管理型LAB；不沿用正式或default scheme。
先備與假資料
  • Developers、Viewers與核准管理角色已由Jira管理員建立；甲乙為既有核准測試帳號，不新增正式使用者。
  • 準備只有合成資料的LAB-1；記錄目前scheme、角色名單及核准管理者的復原入口。
  • 介面分批推出可能顯示專案（project／space）、工作項目（issue／work item）、工作類型（issue type／work type）；依物件與官方文件辨認入口。
隔離範圍
  • 僅限已核准獨立教學站台的LAB專案（project／space）；資料、名稱與測試身分均為合成，不連正式站台。
  • 只用既有核准測試帳號，不邀請真實人員；測試站台須預先隔離郵件、外部整合與非實驗automation，未確認隔離時改用紙上模式。

    紙上推演 紙上寫甲與乙都能閱讀；甲在Developers、乙在Viewers時，誰能把LAB-1摘要改成「測試修正」？再預測乙被加入Developers後是否要改scheme。

    預期看到 兩項預測已填寫，稍後以帳號可見畫面驗證。

    配置專用方案

    操作

    預期看到 LAB-PERM明細列出上述角色；無Public、Any logged in user或廣泛app access授權。

    只關聯教學專案

    操作

    操作 於LAB的Project／Space settings→Permissions→Use a different scheme選LAB-PERM；確認它未引用其他非教學專案，再在People把甲放Developers、乙放Viewers。

    預期看到 LAB顯示LAB-PERM；角色頁分別列出甲與乙，管理者保有復原能力。

  4. 4

    驗證讀與改

    操作

    操作 甲、乙分別以核准測試登入開LAB-1。甲把摘要改為「測試修正」；乙嘗試找Edit並改摘要，若無權則停止，不嘗試繞過。

    預期看到 兩人可讀；甲變更記入歷史，乙無Edit能力或收到拒絕。

  5. 5

    只換角色成員

    操作

    操作 LAB管理員把乙加入LAB的Developers，乙重新整理LAB-1後改摘要成「第二次修正」；確認scheme內容未變。

    預期看到 乙取得Edit，工作歷史有第二次修正；scheme授權來源仍是角色。

先預測，再驗證

先預測：Browse有了是否就能編輯？

比較預測與理由

不會。依此設定，預期甲乙皆可讀、只有Developer可改；若觀察相符，即可驗證Browse與Edit不同。教材未實測租戶。

先預測：角色成員換人是否一定要改共用方案？

比較預測與理由

不必。既有scheme引用角色時，更新LAB角色成員即可；其他專案的同名角色名單不因此改變。

記住這個心像 方案是規則，角色是專案內的位置，成員是填進位置的人。

還原與收尾

  • 移除乙臨時加入的Developers，恢復原角色名單與LAB原scheme。
  • 還原LAB-1摘要；保留LAB-PERM並標註停用教學用途，不刪正式方案。

沒有支援的環境：無權限或無教學站台：觀察／紙上替代

  • 依本章官方來源辨認設定物件；只看文件，不在自己的正式站台尋找替代操作。
  • 在紙上列出本章假資料、每一步預測與可見結果，再逐項核對checks答案。

驗證界線 此替代只能證明理解與推演；未建立或修改Jira，不能記為租戶操作驗證。

深入查閱

把圖中的關係對回設定

以下保留本節考點與細節。沿用圖中的角色、假資料與步驟，逐段確認原因。

先認識名詞

Permission scheme：公司管理型可共用的專案權限規則集合。

Project role：每個專案分別安排成員的職責位置，可被共用規則引用。

Group：跨專案使用的帳號集合；成員變更可能影響多個專案。

User／group picker：讓工作項目選擇使用者或群組的欄位，可在支援情境成為動態授權來源。

為什麼看得到專案，仍然不能完成某項操作

把專案想成共用工作區：閱讀、建立工作項目、編輯、指派、留言、轉移狀態與管理設定，是不同的能力。專案權限（project permissions；目前 UI 也稱 space permissions）回答「誰能在這個工作區做哪件事」。能登入 Jira，並不等於在所有專案都有這些能力。

公司管理型（company-managed）的權限方案（permission scheme）是一份可重用的授權規則。同一份方案可以連到數個專案；方案中的「Developers 角色可編輯」會在每個專案分別查該專案 Developers 裡有哪些人。

你應先辨識規則本身，再辨識專案中的角色成員，避免只看人的職稱猜權限。

團隊管理型（team-managed）把存取層級與角色放在該專案內管理，不能把公司管理型的權限方案直接套上去。兩者都需要控管存取，但設定物件、管理入口與可重用範圍不同。

團隊管理型：先決定存取層級，再決定角色

方案入口不能直接套用到團隊管理型。

Open、Limited、Private 是團隊管理型的存取層級。官方目前的規則是：Open 讓站台上的人取得 Member 的基礎能力；Limited 讓站台上的人取得 Viewer 的基礎能力；Private 只讓被加入的人存取，Jira 管理員仍有文件描述的管理與可見性例外。

這裡的 Open 指站台內的存取，不代表匿名網際網路使用者。

Member 與 Viewer 的差異不只是名稱。Viewer 著重閱讀與留言，並不等於可以建立、編輯工作；Member 可以參與工作。Administrator 則可管理專案設定。自訂角色提供更細的組合，但若存取層級已給某人基礎能力，就不能假設另加一個較弱的角色會撤銷既有能力。

請從所有授權來源一起判讀。

操作時先進入該專案的 Space settings／Project settings → Access，查看存取層級、直接加入的人及其角色，再檢查自訂角色的能力。Free 方案在角色、權限與工作項目安全性方面有限制；題目若提到 Free，不能預設付費方案的細緻設定都存在。

公司管理型：把需求翻成精確的權限

Browse Projects／Browse spaces 是閱讀專案與其工作項目的基本入口；Create Issues／Create work items 是建立；Edit Issues／Edit work items 是修改一般欄位；

Assign Issues／Assign work items 是更改承辦者；Assignable User／Assignable users 決定誰可被選為承辦者。能指派與能被指派是兩個不同角色，不能互相代替。

Transition Issues／Transition work items 控制能否執行工作流程轉移。工作流程條件或驗證器仍可能再限制某一次轉移，因此「有 Transition 權限」不是所有箭頭必定可按的保證。

Schedule Issues／Schedule work items、Resolve Issues、Close Issues 與管理 sprint 等能力也各有目的，不能用一個 Edit 權限概括。

Administer Projects／Administer spaces 用於專案管理，不能直接推論可以改所有全站共用方案。Jira 管理員管理共享設定；專案管理員在授權範圍內管理本專案。對 workflow 或畫面的有限本地編輯能力，還要符合未共用等條件，不能把例外當成對全站任意修改的能力。

建立權限清單時以「人要完成的動作」為起點。例如服務窗口只要閱讀和留言，不必為了方便就加入管理員群組；開發人員需編輯與轉移，不表示需要刪除資料或管理共用方案。最小權限是把必要能力給足，而非只給一個看起來很高的角色。

一個動作可能需要一組權限

分享filter或board不會補足任何一個資料權限。

移動工作項目到另一個專案，不是只在目的地按「接收」。操作人需要來源專案的 Move work items，以及目的地的 Create work items；還應具備閱讀與完成欄位對應所需的存取。目的地的工作類型、必填欄位與流程也可能要求對應，這些是設定條件，不是再多給一個管理員頭銜就自動完成。

跨專案連結需要考慮連結兩端。官方權限互動文件要求相關專案具備 Link work items，並能存取相關工作項目；全站工作項目連結功能也必須啟用。這是全站開關與專案授權的交集：關閉功能時，多給 Link 權限不會讓功能自行開啟。

Manage sprints 不會自動提供排程、編輯所有工作項目的權限；多專案 board 的 sprint 管理又可能涉及 board 篩選範圍中的數個專案。診斷時先釐清題目是在管理 sprint，還是在更改 sprint 內某張工作項目的欄位，不要把容器操作與內容操作混成同一件事。

閱讀方面還要加上第1.5節的工作項目安全性。Browse 是第一道檢查；若工作項目有安全性等級，還要符合該等級授權來源。共享 filter、dashboard 或 board 不會替讀者補足底層工作項目的權限。

角色、群組與動態欄位：三種授權思考

專案角色是專案內的職責位置，例如 Developers。Jira 管理員在共享方案寫規則，專案管理員在自己的專案替角色安排成員。兩個專案都叫 Developers，成員可以不同。這讓共用標準與本地人員維護同時成立。

群組（group）是跨專案的帳號集合，通常由使用者管理範圍的人員維護。若權限方案直接給某群組，所有使用這個方案的專案都會評估同一個群組；改動成員可能同時改變很多專案的存取。單獨具名使用者同樣可能跟著共用方案散布到多個專案，因此不要把它誤認為只對目前開著的專案生效。

User picker 與 group picker 自訂欄位能在支援的權限項目中成為動態授權來源。例如「審核人」欄位選到誰，就依該工作項目的欄位值評估該人的權限；group picker 則依選到的群組及其成員評估。設定欄位的權限、欄位內容是否可被更改，以及空值時沒有對象可匹配，都要一起納入設計。

動態欄位不等於新建一個全站群組，也不會把人永久加進專案角色。它只是授權規則在某個情境下查詢的資料。不要把「這個欄位現在填了 Alex」翻譯成「Alex 在所有專案都有同一權限」。

實務診斷：由小到大找出缺少的條件

情境：Mei 能閱讀來源專案，卻不能把工作項目移到另一個專案。先記下她實際點的動作、兩邊專案管理型態、工作項目 key、錯誤訊息與發生時間。不要一開始就把她升為 Jira 管理員，因為這會掩蓋原本應該被修正的授權邊界。

接著確認來源的 Move、目的地的 Create、雙邊必要的 Browse 與安全性條件。公司管理型查看各自連到哪個 permission scheme，再追到其中的角色／群組／動態欄位。若只有一張工作項目失敗，優先比較它的安全性、欄位與流程，而不是假設整個站台壞掉。

修正前先列出共享方案的使用專案，與負責人確認變更範圍。在隔離環境以普通測試帳號驗證最小變更，確認預期可行的動作成功、原本不該允許的動作仍被阻擋。記錄變更原因、影響範圍與復原方式，才是可維護的管理工作。

常見誤解：權限不會因分享或頭銜自動補齊

錯誤說法：「把 board 分享給對方，他就能看 board 上所有工作項目。」釐清：分享控制的是 board／filter 物件的可用性；底層閱讀權限與工作項目安全性仍會過濾內容。

錯誤說法：「專案管理員能改任何共用權限方案。」釐清：本地角色成員管理與全站方案規則管理是不同層次。

錯誤說法：「給一個弱角色就能撤銷強角色。」釐清：需檢查所有授權來源與團隊管理型存取層級提供的基礎能力，不能假設最後加入的角色會覆蓋前者。

錯誤說法：「Link work items 權限存在，就不用檢查系統功能。」釐清：功能啟用與授權均需符合。

圖解與逐步理解

確定操作

先分清閱讀、移動或連結需求，不能以管理者職稱跳過檢查。

相關權限

檢查全域功能與相關專案權限；不同操作的必要權限不同。

工作項目安全

讀取還須符合這張工作項目的安全等級授權。

操作特定條件

完成移動／連結仍須查兩端權限、配置及題設條件。

自我檢查與理由

自我檢查

「能開啟專案首頁」可以證明有編輯工作項目的權限嗎？

查看答案與理由

不能。閱讀與編輯是不同權限；還要確認管理型態、授權來源及工作項目安全性。

自我檢查

Limited 專案裡，某人沒有被列為 Member，就一定完全看不到專案嗎？

查看答案與理由

不一定。Limited 為站台使用者提供 Viewer 基礎存取；還要看題設是否有其他限制。

自我檢查

Assign work items 和 Assignable users 的差別是什麼？

查看答案與理由

前者允許執行指派，後者表示這個人可以成為承辦者。管理員須分別確認操作人與被指派人的資格。

自我檢查

來源專案給了 Move，目的地只有 Browse，足以把工作項目移過去嗎？

查看答案與理由

不足。目的地還需要 Create work items；其餘設定對應也必須符合。

自我檢查

兩個專案共用方案，但需由各專案自己維護開發者名單，方案應優先引用什麼？

查看答案與理由

引用專案角色，再由各專案安排該角色的成員。直接引用同一群組會使兩邊跟隨同一組人。
