動手驗證

用直接連結驗證受限假資料

文件查核設計；未租戶實測。完成下列步驟後，以你看到的結果判斷是否成功。

這次要驗證

  • 先預測：Set Security等於能讀Restricted嗎？
  • 先預測：None代表拒絕所有讀者嗎？

準備環境

角色
  • Jira管理員配置LAB專用security scheme；甲具Set Work Item Security並列在等級中。
  • 乙有LAB Browse但不在Restricted；核准管理者保留等級存取與復原能力。
方案與功能
  • Standard、Premium或Enterprise；Free不可編輯security schemes。
  • 公司管理型LAB，不把team-managed角色限制當成同一入口。
先備與假資料
  • 管理員已在LAB專用screen提供Security欄位；甲乙具Browse；LAB-11/12均合成且無真附件。
  • 介面分批推出可能顯示專案（project／space）、工作項目（issue／work item）、工作類型（issue type／work type）；依物件與官方文件辨認入口。
隔離範圍
  • 僅限已核准獨立教學站台的LAB專案（project／space）；資料、名稱與測試身分均為合成，不連正式站台。
  • 只用既有核准測試帳號，不邀請真實人員；測試站台須預先隔離郵件、外部整合與非實驗automation，未確認隔離時改用紙上模式。

深入查閱

把圖中的關係對回設定

以下保留本節考點與細節。沿用圖中的角色、假資料與步驟，逐段確認原因。

先認識名詞

Project／Space：專案／空間

Issue／Work item：議題／工作項目

Issue type／Work type：議題類型／工作類型

Browse Projects／Browse spaces：瀏覽專案／瀏覽空間

Set Issue Security／Set work item security：設定議題／工作項目安全性

Issue security scheme / level／Work item security scheme / level：工作項目安全性方案／等級

Sub-task／Subtask; some team-managed flows say child work item：子任務；不可把所有父子階層一概視為子任務

先問要保護什麼

同一專案大多數工作都能公開協作，但其中幾張單含有尚未公開的產品漏洞。這時可用工作項目安全性縮小特定單據的可見範圍，不必為每張敏感單另建專案。

看得到：通過瀏覽權限，再通過該單的安全性限制

公司管理型空間中，Browse Projects 是基本門檻。若該單已指定安全性等級，使用者還要符合那個等級的授權。只通過其中一關不夠；未指定等級則沒有這一層額外限制。

能設定：不要把三種權力混在一起

Administer Jira 用來管理安全性方案、等級及其授權來源；Set Issue Security 用來變更工作項目的安全性等級；成為等級允許的成員，才與看見該單有關。授予設定權限，不等於直接授予所有受限單的閱讀權限。

先辨型，再判斷繼承

公司管理型用方案與等級，團隊管理型軟體空間用角色式限制。子任務會繼承父項目的安全性設定；但使用動態欄位決定成員時，繼承同一等級不代表實際可見者完全相同。

從零理解：方案、等級、授權來源與工作項目的關係

安全性方案（security scheme）像一套可選的閱讀限制規則集；安全性等級（security level）是規則集中的一個選項，例如「內部協作」或「限審核團隊」。等級名稱只是標籤，不代表數字較大就必然包含數字較小的所有人。實際可見者由授權來源決定。

公司管理型專案先關聯一份安全性方案，工作項目再選擇該方案中的等級。管理員應先定義用途及允許來源，再決定預設值與誰可以更改等級。不能只建立一個名為Confidential的標籤、工作類型或board欄，就認為閱讀限制已生效。

這個機制主要控制特定工作項目的可見性，不取代帳號存取、專案權限或每一項操作權限。即使看得到，編輯、留言、轉移或設定安全性等級仍需要相應能力。完整需求要把「能不能看」與「看見後能做什麼」分開。

1. 先用兩道門排除錯誤答案

把判斷拆開：第一道門檢查該使用者的 Browse Projects；第二道門檢查這張單目前的安全性等級。安全性等級可以縮小可見範圍，不能補上缺少的專案瀏覽權限。這是一般工作項目閱讀情境的教學模型，不是所有 Jira 存取路徑的完整授權引擎。

2. 公司管理型：先備妥方案，再讓合適的人選等級

設定順序可記成「方案、等級、成員、關聯、操作入口」。Jira 管理員建立方案與等級，設定成員，將方案關聯到目標空間；再確認需要操作的人具備 Set Issue Security，以及 Security Level／Work item security 欄位出現在相應版面或畫面。

不要只加欄位就以為安全性已啟用。

3. 等級成員可以跟著這張單改變

Reporter不是所有曾回報過工作的人。

Reporter 代表該單的回報者，Current assignee 代表目前受指派者。User custom field value 讀取指定使用者選擇器，Group custom field value 讀取指定群組選擇器。填入一般文字、標籤或顯示名稱，不會因此變成這些授權來源。

「案件協作」等級允許 Reporter、Current assignee 與「審查人員」使用者選擇器中的人。以這張單的欄位值判斷誰符合；調整受指派者或審查人員時，應重新檢查實際可見者。多個允許來源是替代的授權途徑，不是要求同一人同時符合全部來源。

4. 分清楚三種『空』，再談預設值

None不是空的讀者名單；仍依Browse判斷。

Default 是建立時未指定等級的起始選擇。該等級若沒有授權給回報者，建立完成後，回報者可能看不到自己剛建立的單。這不能靠『是我建立的』推翻。

目前建立方案文件對 Default 的文字較概括，不能據此教成『改預設值會自動回填所有既有單』。本課不把這個未驗證邊界當作考題答案。

該單沒有安全性等級（None／未設定）：沒有工作項目安全性這一層額外限制，仍須符合 Browse Projects 等基礎存取要求。

方案沒有預設等級：不要據此判斷每張既有單都沒有等級；檢查個別單據的實際值。建立途徑、規則及明確輸入也要一起確認。

已選定某等級，但沒有符合的成員：不能當作 None。依允許名單模型，沒有匹配授權不會變成公開。此句是根據成員規則的推論；操作前以測試案例驗證，避免把所有操作人員鎖在外面。

5. 子任務繼承等級，不是複製一份永遠固定的讀者名單

公司管理型子任務沿用父項目的安全性等級，不能另選一個獨立等級。先記住這條規則，再看成員是否由使用者／群組欄位動態決定。官方 Cloud 範例顯示，同一繼承等級可因各項目的群組選擇器值不同，產生不同的實際可見者。

本課的繼承箭頭只指向 subtask。不要看到 epic、story 或一般 Parent 關係，就自動假設套用相同安全性繼承規則。團隊管理型子任務的角色限制同樣從父項目繼承，不能逐一另改。

6. 團隊管理型：以角色限制，而且要分清新單與舊單

目前官方文件支援在團隊管理型軟體空間中，為個別工作項目選擇允許閱讀的角色。需要 Restrict any work item 權限。管理員也能替工作類型設定新單的預設角色限制，但這項變更不會回溯改掉先前建立的單。

不要沿用『團隊管理型只能按類型限制、不能限制單張』的舊口訣。建立入口的限制處理也可能不同；實務上應按官方支援的建立流程測試，不能假設每個快速建立入口都會套用你期待的限制。

把設定需求寫成可驗證的案例

假設「產品修復」專案一般工作可由團隊閱讀，但少數尚未公開的漏洞只允許審核者與目前承辦者閱讀。先寫出至少四類測試身分：有Browse且符合等級、有Browse但不符合等級、符合等級但無Browse，以及能更改等級的人。每類預期結果要明確，不能只用管理員帳號看得到就宣布設定正確。

再確認使用哪個管理型態、付費方案是否支援、目標專案關聯哪份方案、等級有哪些授權來源、操作人是否有Set Issue Security，以及欄位是否在適當的畫面或版面。若等級使用動態欄位，測試換承辦者或修改picker值後的可見性變化。

對子工作項目加一個專門案例：先確認繼承的等級，再檢查動態來源引用的是哪個工作項目的欄位。這能避免只比對父子等級名稱，卻漏掉兩者實際允許對象不同。

沒有隔離測試環境時，可依題設做紙上推演，並把結果標為文件推導。不能把未測試的Default回填、空允許名單或快速建立入口差異，寫成所有站台均已實證的保證。

正確理解：它是設定能力；可見性仍要檢查瀏覽權限與等級成員。

錯誤說法：安全性等級選 None，等於誰也看不到

正確理解：None 是移除該層限制，不是空的允許名單。

錯誤說法：加入 Reporter 權限來源，意思是每個回報過問題的人都能看

正確理解：Reporter 是這一張單的欄位值。

釐清：子任務可以挑一個與父項目不同的安全性等級

錯誤說法：子任務可以挑一個與父項目不同的安全性等級

正確理解：子任務繼承等級；動態欄位造成的讀者差異是另一件事。

正確理解：官方說明是保留既有方案、限制編輯，不能把保留與可修改混為一談。

正確理解：用直接開啟與權限檢查驗證。搜尋結果本來就受使用者存取權限影響，不是完整的稽核清單。

安全等級

具體缺失

任一道門未通過時，指出該條件，不給管理員萬能捷徑。

自我檢查與理由

自我檢查

什麼需求適合使用單一工作項目的安全性？

查看答案與理由

在同一專案仍要合作，但只有部分工作項目需縮小可見範圍時。

自我檢查

名為Secret的level一定比Internal包含更少人嗎？

查看答案與理由

不能只看名稱判斷；要檢查每個等級實際授權來源。

自我檢查

某人已在等級允許的群組內，但沒有 Browse Projects。他就能看見受限單嗎？

查看答案與理由

不能；先補查專案瀏覽權限，而不是再加一次等級成員。

自我檢查

看得到受限單，卻不能調整它的等級，是否一定要加入更多等級成員？

查看答案與理由

不一定。先查設定權限與欄位／操作入口，因為能看與能設定是不同能力。

自我檢查

把『僅限稽核』放進 Labels，就會讓其他人看不到嗎？

查看答案與理由

不會。分類標籤本身不是這個安全性等級的成員規則。

自我檢查

查到 level is EMPTY，是否代表全網際網路都能看？

查看答案與理由

不是；它只表示沒有設定等級，搜尋本身也只會回傳你有權限閱讀的工作項目。

自我檢查

『父項目與子任務使用同一等級』能否證明任何人對兩張單的閱讀結果都相同？

查看答案與理由

不能。先看等級的成員來源與各項目欄位值，不要只比對等級名稱。

自我檢查
