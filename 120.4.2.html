團隊管理型 workflow：為不同工作設計清楚的路徑

先理解用途，再判斷設定與結果。

官方目標 4.2 · 來源內容版 2026-10-05.complete-draft

閱讀前提

知道 status 是階段、transition 是合法移動路徑。

理解公司管理型與團隊管理型的設定邊界不同；不必先背所有公司管理型 scheme。

先認識名詞

Team-managed workflow：在團隊管理型專案中，供一種或多種 work type 使用的本地流程。

Any status transition：可從此流程其他狀態進入目的狀態的路徑；不是全站或跨專案權限。

Workflow rule：加在轉換上的限制、資料驗證或附帶更新規則。

Shared status within a space：同專案多個流程可能使用同一個 status；改該 status 名稱／分類可能連帶影響其他流程。

先決定工作為何不同，再決定要幾個流程

合成團隊維護門市預約服務。Task 是例行改善，走 To do → In progress → Done；Bug 則要先 Triage，再 Fixing、Verification、Done。差異是 Bug 需要額外診斷與驗證，而不只是卡片顏色不同，因此分開流程有實際理由。

團隊管理型專案可以讓不同 work type 使用不同 workflow，也可以讓多種 work type 共用一個流程。同一張 board 因此可以呈現不同工作流，不代表只能有一套狀態。

不要為每個承辦者建立一份 workflow。先問「合法步驟、准許者、必要資料」是否真的不同；只是承辦人換了，可能用 Assignee 即可。如果兩類工作邏輯一致，共用可減少維護負擔。

設定流程時，特別留意 Update workflow 的套用對象

目前文件路徑為 Space settings → Work types → 選類型 → Edit workflow。完成修改後，按 Update workflow，確認這次 workflow 套用到哪些 work types，再保存。舊名稱可能仍是 Project settings / Issue types。

「我是從 Bug 點進來」不等於這次一定只影響 Bug。流程原本可能也用在 Task；更新時要把選定類型和需求比對。若要讓 Bug 獨立，就明確選擇相應範圍，並驗證 Task 還保有原本流程。

驗收至少包含兩面：建立一筆 Bug 看到新流程；建立一筆 Task 確認未被不小心套用。只測一筆 Bug 成功，不能證明影響範圍正確。這是教材的測試設計建議，所有實作僅限隔離且授權的練習環境。

這套工作方式不等於把公司管理型的 workflow scheme 搬進團隊管理型。應從該專案內的 work type 流程設定理解其作用，避免在全站尋找根本不適用的對應表。

新增 status 之後，還要檢查可達路徑與 board 欄位

新增 status 時先選分類，再給狀態名稱。例如 Waiting for supplier 通常仍是 In progress 類別，因為工作尚未結束；名稱叫「已送出」也不一定應屬 Done，要看團隊對交付完成的定義。

目前官方文件指出，透過團隊管理型 workflow editor 新建 status 時，預設有 Any status 入向轉換，讓其他狀態的工作可進入。若流程需求是「只有 Verification 能進入 Done」，就必須檢查這種廣泛路徑是否應限制，不能只畫一條看似正確的箭頭就以為別的路已消失。

新 status 在 workflow 出現後，預設未指派 board column，因此工作可能不在 board 顯示。更新時的 column assignment 或專案 Board → Columns and statuses 是另一個檢查點。合法可達與可見呈現要分開測試。

合成例：Bug 進入 Waiting for supplier 之後從 board 不見了。先查該 status 是否有 column 映射，並確認 filter；不要立刻把這些 Bug 當成已刪除，也不要為顯示問題把它們誤轉成 Done。

更名、改分類、刪除：影響不是一樣的

更名改的是這個 status 的標籤；改 category 則可能改變它被歸類為待辦、進行中或完成的意義。這兩件事都不是「替工作執行正常 transition」的同義詞。變更時要知道是在改流程設計還是在移動個別工作。

同一 team-managed 專案內，status 可被多個 workflow 共用。若 Bug 與 Task 共用 In review，直接改名為 Security review，可能使同專案所有使用該 status 的流程一起改名。官方介面提供只為目前工作範圍變更的方式，會建立獨立副本；實際按鈕依版本確認。

刪除 status 會連帶移除與它相關的轉換和規則；在目前 workflow editor 刪除，表示從目前編輯的 workflow 移除，不表示無條件從所有 workflow 抹掉同名 status。若有工作正在該狀態，Jira 會要求把它們移到有效狀態。

合成變更清單：刪除 Waiting for supplier 前，列出目前在此狀態的 Bug、進出箭頭、附帶規則與 board mapping，再決定它們應轉往 Triage 還是 Fixing。不要為了讓畫面變短，把不同真實處理狀況一律塞到 Done。

選擇 workflow rule：限制、檢查、更新各有用途

「只有值班負責人能結案」是人員限制；「風險等級為低才可走快速流程」是欄位值限制；「必須經過 Verification 才能完成」是歷史狀態檢查。這些需求都與允許哪些轉換有關，不只是換欄位的文字。

如果需求是轉到某階段時自動指派負責人、更新日期或複製父工作某欄位，則是在設定成功轉換後的附帶行為。資料複製也有前提，例如選了從 parent 複製但工作沒有 parent，規則可能略過；不能把「沒有更新」一律當成系統壞掉。

歷史狀態規則要讀清選項。曾經通過某狀態，與「最近一次就是那個狀態」、是否計入目前狀態、是否忽略同狀態 loop 的紀錄，是不同條件。合成例：一筆 Bug 去年曾驗證通過但今天重新修正，單純「曾經通過 Verification」不一定滿足這次修正也要驗證的要求。

選規則時先寫一句可以被驗收的業務需求，再查看該管理型態與編輯器提供的規則。文件中的 Remind people to update empty fields，不能只從名稱就當成一定會阻擋的硬驗證；要閱讀選定規則的當前行為，測有值、空值與不符合身分三種情境。

Team-managed workflow rules 不等於獨立的 automation rule。前者附在某個 workflow transition；後者可由排程、欄位變更等事件觸發，並可能處理相關工作。本課先把轉換當下的規則設定清楚，第 4.3 再學事件式自動化。

把流程驗收寫成可預測的案例

合成 Bug 流程規定只有 Maintainer 角色可以從 Verification 結案，且所有必要資訊必須完整。第一種案例：Maintainer 且資訊完整，應成功；第二種：Maintainer 但資訊缺漏，要按實際驗證規則被阻止或提醒；第三種：普通成員，應不具備受限結案能力。

再測替代路徑。若另有 Any status → Done，且沒有相同限制，就可能繞過原本以為唯一的驗收路徑。管理者應盤點所有進入結束狀態的路，而不是只測自己最常按的箭頭。

最後測多 work type 的影響及 board 映射。同一規則可能在其中一種 work type 有需要的欄位，另一種類型沒有；規則處理差異應來自明確條件，而不是留下不可解釋的跳過或失敗。

紙上雙流程演練：Bug 與 Task

先以紙上推演完成。若要實際操作，只能使用另行授權、隔離且可丟棄的練習環境；使用合成資料，先確認沒有共用正式設定或真實通知收件者。這些步驟是文件查核的練習設計，並非已替你執行或驗證成功。

自我檢查與理由

自我檢查

Bug 要診斷與驗證，Task 不需要。可以在同一團隊管理型專案為兩者用不同 workflow 嗎？

查看答案與理由

可以。專案管理者可按 work type 調整流程，更新時確認套用哪些類型。

自我檢查

從 Bug 開啟 workflow 後直接更新，是否足以證明 Task 不受影響？

查看答案與理由

不足。要檢查更新時選中的 work types，以及同專案的共享設定，並另外驗證 Task。

自我檢查

新增 Waiting for supplier status 後工作可進入，但 board 看不到，應先查哪個關聯？

查看答案與理由

查新 status 是否已映射到 board column；還需排除 filter 與可見性問題。

自我檢查

Bug 與 Task 在同一專案共用一個 status，只想替 Bug 改名，應注意什麼？

查看答案與理由

不要直接改共享本體而假定 Task 不受影響；先看共享警告與只為目前範圍建立獨立 status 的支援方式。

自我檢查

要記錄「交給供應商」這次轉換發生的日期，應先找限制轉換規則，還是更新日期欄位的動作規則？

查看答案與理由

先找適用的欄位更新動作規則；限制決定能否使用路徑，更新動作處理通過後的資料。

自我檢查

一條受限的 Verification → Done 已測成功，還需要檢查 Any status → Done 嗎？

查看答案與理由

需要。另一條入向轉換可能提供不同路徑與規則，必須一起驗證，才能確立業務限制。
