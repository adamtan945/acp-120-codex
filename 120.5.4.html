郵件處理器 將來信安全地變成工作

先理解用途，再判斷設定與結果。

官方目標 5.4 · 來源內容版 2026-10-05.complete-draft

閱讀前提

先理解Create work items、Add comments、Assign和Assignable的權限差異。

本節是Jira一般mail handler，不把JSM客服email channel的免授權寄件者行為移植過來。

只使用合成信件範本；任何真實信箱授權或測試寄信都需另行批准。

先認識名詞

Incoming mail server：Jira讀取新來信的來源信箱連線。

Mail handler：決定來信要建立工作項目、加入留言及採用哪些預設值的處理設定。

Default Reporter：來信地址無法配對現有使用者時，處理器可使用的回報身分；不是預設承辦者。

CC Assignee：依處理器規則嘗試從收件欄位選承辦者的選項。

先分清收信 轉換與通知

Incoming mail是把信箱資料讀入Jira；mail handler是把讀到的資料轉成工作；notification則是Jira因事件寄出的信。三者方向與目的不同，停用寄出通知不代表停止從信箱建立工作。

管理者先確認來源信箱、認證方式、掃描資料夾、掃描間隔與處理器型態。官方一般mail handler文件要求Jira管理權限；實際可見的郵件管理入口與外部信箱同意仍須驗證，不能把能管理專案視為能連接任何信箱。

目前Google與Microsoft流程採OAuth，不應把舊Basic Authentication教成通用建議。連接信箱會授予持續讀取能力，需走組織核准程序。這是安全背景補充，課程不會要求輸入密碼、建立token或接受外部授權。

依目的選處理器與選項

「Create a new work item or add a comment」會依主旨是否含工作項目key分流：有key時把內容加到既有工作，沒有時在設定的預設專案建立。相反地，「Create a new work item from each email」每封都建立新工作。因此重複票可能是選了不同型態，而不是主旨辨識失效。

留言處理器可取完整內容、去掉引用行，或在指定分隔標記前截取。Strip quotes與Split regex處理正文；Catch Email Address檢查To或CC是否有指定地址，適合共用信箱的不同別名。預設專案與工作類型決定新工作去處，不會把主旨中的既有key改寫成新專案。

Default Reporter在寄件地址找不到帳號時提供後備回報者，這個身分仍需Create或Add comments等適當權限。原始寄件地址可能寫入Description，因此要把來信轉工作視為資料傳送，不能在未核准時把私人信件導到公開專案。

Bulk選項處理有自動化／大量郵件標記的來信，可忽略、轉寄狀態、接受或刪除。實務要防止系統彼此回信形成循環。這裡只學習選項意義，不以永久刪除作練習。Forward Email是處理問題的狀態收件者，仍需確認收件對象可以接收相關資訊。

逐層排查由郵件建立的承辦者

若啟用CC Assignee，官方描述先找CC中的第一個有效對應使用者，找不到才查To，再找不到才查BCC；全部找不到，處理器本身不設定assignee。題目或排查紀錄必須說明候選是否為有效使用者，不應單憑畫面上有一個地址就宣稱可指派。

這個選項與CC Watchers不同：一個嘗試選承辦者，一個把Jira使用者加成watchers。Default Reporter又是另一種身分。把測試員甲設成Default Reporter，並不表示所有工作都應分派給甲。

若處理器未設定assignee，下一步才查專案或元件的預設指派、是否允許未指派、候選的Assignable條件，以及建立後的automation或workflow是否再改值。不要從「mail handler沒選人」直接跳到「最後一定Unassigned」，也不要先改全站指派政策。

完整診斷先記錄實際新工作，查看建立時與之後的變更歷程，再比對信件收件欄位順序、handler選項與其他規則。這樣才能辨識是處理器選錯、使用者不能被指派，或後續規則覆蓋。對沒有直接文件保證的多機制優先關係，應用隔離測試驗證而不是猜測。

合成信件分流與排錯

合成信件A主旨為「LAB-23 補充重現條件」，採create-or-comment處理器；寄件者有該工作可見性與留言權限。因此應預測為LAB-23新增留言，不是因預設專案不同而另建工作。信件B無key，預設專案LAB、類型Task，因此預測新建Task。

信件B啟用CC Assignee；CC只含無對應帳號的地址，To的第一個有效可指派Jira使用者是測試員乙，BCC有另一位有效使用者。依此合成條件，先在To找到乙，不繼續用BCC覆蓋。Default Reporter是測試員甲，也不改變這個選人推導。

排錯還要看來信時效與附件：現行文件說超過7天的寄送日期不處理，單封訊息資料與附件總量上限25MB；若SPF校驗適用而失敗會拒收。這些是截至查核日的產品限制，不能從沒建工作就斷定assignee有問題。

來源信箱處理有分支：Google／Microsoft OAuth文件說已處理郵件標為已讀且不刪除；一般POP／IMAP段落描述成功處理後刪信。不要把後者套用為所有連線模式。規劃測試前要先確認實際模式與保留策略。

避免以錯誤身分與預設值推論結果

Default Reporter決定後備回報身分，CC Assignee嘗試選承辦者，CC Watchers管理關注者。三個選項名字相近但資料欄位不同，應在測試表各占一欄，不能用「預設人員」統稱。

不要把一般Jira mail handler當成免費公共客服入口。一般文件以有產品授權的使用者為常態；JSM email channel另有客服模型。若是對外服務需求，先辨識產品與授權模型，這是邊界說明，並非在ACP-120內擴展成JSM完整課程。

圖解與逐步理解

處理器與 key

create-or-comment 依主旨 key 分流留言或建立新工作。

CC

啟用 CC Assignee 時先找有效、可指派的 CC 使用者。

To

沒有 CC 候選才查 To。

BCC

前面沒有候選才查 BCC。

未設定

無候選時 handler 不設定承辦者；不是直接保證最終為 Unassigned。
