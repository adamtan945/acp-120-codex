備份與匯入 先辨識工具再談還原

先理解用途，再判斷設定與結果。

官方目標 7.4 · 來源內容版 2026-10-05.complete-draft

閱讀前提

先知道來源平台是Cloud或Server／Data Center，目的平台與實際工具名稱。

必須具備相應管理能力與資料處理授權；能力存在不等於已獲准覆寫資料。

本節只做合成資料的備份清單、對應和還原計畫。不執行匯入、刪除、清空站台、提供憑證或故障單腳本。

先認識名詞

CSV import：把表格列與欄位／值對應到工作項目，适合從其他工具移入或受控更新。

Backup Manager：Jira傳統站台備份工具，Cloud備份含XML資料，媒體需選擇包含。

Import Jira Cloud：讀入Cloud備份的站台匯入路徑；XML會覆寫目的資料庫。

Atlassian Backup and Restore：組織管理中的另一個備份服務，其格式與Backup Manager不能互用。

Archive／Restore archived project：在現有站台封存與解除封存，和讀入備份是不同動作。

JCMA／Copy Data：Jira Cloud Migration Assistant與Cloud-to-Cloud Copy Data是不同遷移機制；行為不能互相類推。

用需求選工具 不要只看Import這個字

若需求是把另一個工作追蹤工具的二十列Task帶入測試專案，CSV可表達Summary、Description、work type等欄位並做對應。若需求是用完整Jira Cloud備份恢復站台，才研究Backup Manager與Import Jira Cloud。CSV不是整站設定備份，也不能從CSV欄位推論專案封存旗標。

若來源是Server或Data Center，先查當前支援的遷移路徑，例如JCMA，不應看到歷史文件有XML字樣就假設所有舊入口仍適用。若來源是另一個Cloud且採Copy Data，這是另一套遷移機制。來源平台＋輸出格式＋匯入工具三者都寫出來，才有辦法回答資料會怎樣。

Atlassian Backup and Restore是目前產品補充，用來避免把兩種備份工具混為一談；它不是把2025考綱改成一套未公布的新範圍。官方FAQ明確說兩種備份格式互不相容；工具名字都含backup不代表ZIP或內容可以互相還原。

CSV先建立對應 再驗證資料意義

CSV的首列是欄位標題，必須有可對應Summary的資料欄。含逗號、換行或引號的內容應妥善引用；UTF-8可保留中文，日期格式需和匯入設定一致。先用兩三列合成資料檢查，不把大量真實資料當格式測試。

管理者路徑是Settings→System→External System Import→CSV，現行文件另有新舊介面分支。依序設定目的專案、欄位對應與必要的值對應；來源狀態必須對應目的有效狀態，不能假設匯入器自動建立任何新狀態。父子資料需提供適當ID與Parent，父列在子列前。

若CSV包含對應到Work Item Key的既有key，可能是更新既有工作而非只新增。Resolution來源寫Unresolved時應對應成空值，不應建立同名結案原因。附件欄位通常用Jira可存取的URL；這不是把本機檔案路徑填進去就保證上傳成功。

隱私要在匯入前處理。官方特別警告JSM的Comments body對應可能使留言公開；這是跨產品邊界風險提示，非本課擴張到完整JSM管理。要做任何真實匯入前，需確認內容、目的站與接收群體，不能只因CSV格式通過就按下匯入。

備份清單要包括資料 媒體與排除項

Backup Manager Cloud備份可包含工作項目欄位、留言、使用者群組設定、board/sprint與專案配置。attachments、avatars、logos等媒體需選擇包含。資料部分位於entities.xml與activeobjects.xml，媒體另在相應資料夾；只有XML不表示圖片檔本體也已備份。

文件查核路徑是Settings→System→Backup manager→Backup for cloud。規劃時選擇是否含媒體，等待備份完成，再下載並核對完整性、時間與保護方式。含附件、頭像或logo的備份需間隔48小時；不要把純資料備份的頻率假設套到媒體備份。

傳統Backup Manager不自動包含automation flows、第三方app與app data、app access設定等資料。Automation可按官方另行匯出，但那是分開步驟。備份計畫要寫「哪一類由哪種工具保護、何時驗證能恢復」，不要只記一個成功下載的檔名就宣布全站可恢復。

截至2026-10-05，官方已宣布2026-01-22起Backup Manager僅接受30天內備份進行還原。因此保存很久的ZIP即使可解壓，也不保證符合還原時效。頁面仍包含已宣布停用的Backup for server舊段落；本課不把它當現行Cloud→Data Center操作，也不教刪除team-managed專案來遷就舊路徑。

還原是受控變更 不是把一個ZIP丟進去

Import Jira Cloud文件警告：匯入entities.xml與activeobjects.xml會覆寫目的站資料庫；匯入attachments、avatars或logos也會覆寫對應媒體。不能把它說成將一個專案安全追加到仍有其他資料的站台。目的站確認、影響範圍與核准是啟動前的停止點。

文件建議把資料與媒體分成兩個匯入檔以降低逾時風險。規劃順序是：確認來源與相容性、完整性和時效；確認目的與可接受的覆寫影響；準備資料／媒體；執行前驗證；完成後抽樣檢查工作數、欄位、附件、使用者、權限、board與連結。這些是流程教學，不是要學員在正式站台按Import。

使用者合併可能讓既有帳號進入更多群組或取得額外存取；新使用者又未必自動取得app access。因此匯入後必須檢查授權，不能只測管理者自己能登入。來源Cloud的自訂郵件憑證不會完整照搬，跨應用連結也可能仍指回來源，需按核准流程重新檢查。

新Atlassian Backup and Restore的目的app必須沒有使用者資料，且同組織、同區域。封存或垃圾桶內資料仍算資料；「全部封存」不會讓app變成空。安全演練應先準備新建隔離app，不把清空或永久刪除正式資料當準備步驟。

每一種匯入權限都要獨立確認

一般專案管理者不是整站備份／還原操作的當然執行者。管理者CSV匯入文件要求Jira administrator；但全域權限頁又明確表示單獨Administer Jira不涵蓋整站import/export。不要把CSV與整站XML兩種動作混成一張權限表。

對傳統Backup Manager／Import Jira Cloud，應由負責站台資料管理的組織／站台管理人員確認當前管理介面中的實際可用權限與政策。已讀現行匯出／匯入頁未完整列出所有集中式與原始管理介面的最低角色組合，因此本課不編造「只要某群組名稱就一定可以」。已確立的是：僅能管理專案或僅有Administer Jira，不能作為整站備份權限已驗證的證據。

新Atlassian Backup and Restore FAQ則明確要求organization admin加app admin。還原後app access可能涉及帳務，文件要求再確認才套用。組織也能封鎖匯出；看到按鈕或持有某個稱號不能繞過資料政策。正式計畫應記錄來源讀取、目的覆寫、匯出限制與執行者的能力，缺一項就停止。

封存狀態要按來源與工具分支

第一種Restore是Archive清單中的解除封存：它讓現有站台的專案恢復使用，不是讀取備份。封存不會刪掉共享workflow與scheme，工作會離開一般搜尋，但原本有權的人仍可能透過直接連結查看且不可編輯。封存不是安全性封鎖，也不是備份。

第二種是Server／Data Center XML匯入Cloud。官方紀錄JRACLOUD-81072描述來源先封存、再匯出Server XML並匯入Cloud後，目的專案變未封存。這是明示來源平台與工具的已知案例，不能擴張成任何Cloud備份都會取消封存。

第三種是Cloud-to-Cloud Copy Data。CLOUD-12072記錄此路徑的封存專案在目的站變未封存。第四種JCMA則有官方遷移指引說可在Cloud的Archived projects查看與restore遷移的封存專案。兩種工具不能互相覆蓋對方的資料；要看記錄描述的確切路徑。

第五種新Atlassian Backup and Restore的支援表明列Archived projects，表示它包含封存專案這類資料；表格沒有明說所有還原後archive旗標。第六種Cloud來源Backup Manager完整備份經Import Jira Cloud還原：本次讀取的直接官方資料仍未確立archive旗標究竟保留或取消，也未證實「匯出前必須先解除封存」。

所以這裡的正確管理能力包括說清楚未知範圍。不能把舊site-import網址轉向JCMA後的內容當成原XML機制的證據，也不能用Server XML或Copy Data的已知問題替Cloud Backup Manager猜唯一答案。若正式遷移必須保證archive狀態，應先取得針對此路徑的官方確認或在隔離授權環境驗證。

合成還原計畫 把成功標準寫在執行前

情境：教學站台LAB有三筆工作、兩個PNG附件、一份company-managed workflow、一個封存專案ARC及一條automation。需求是可重建教學資料，不可碰正式站台。第一步列來源為Jira Cloud、工具為Backup Manager、目的為新建隔離Cloud站台；備份包含媒體，automation需另列保護方式。

第二步寫驗收：三筆工作可查到、兩個附件可開、workflow與欄位對應正確、授權測試人可讀且非授權人不可讀、app access符合核准範圍。ARC的資料是否存在與archive旗標是兩個驗收欄；對未有直接證據的Cloud備份路徑，先標為待確認，不把某個結果當標準答案。

第三步計算時程：媒體備份與上次包含媒體的備份相隔至少48小時，還原備份年齡符合30天限制，且資料／媒體檔確認完整。如果申請的目的站已有使用中的DOC專案，則整站XML覆寫與「不可碰DOC」衝突，必須停止修改計畫。

第四步寫恢復與溝通責任，而不是直接執行：哪位有權管理者核准、誰保管匯出資料、誰確認結果、若失敗如何保全現況。課程本身不會發起任何還原，也不包含官方缺陷單中需要SQL、API token或大量封存的替代腳本。

圖解與逐步理解

CSV

處理欄位映射，不能當完整系統備份。

傳統 XML

Backup Manager／Import 的格式與目的限制需分開核對；還原可能覆寫目的資料庫。

Copy Data／JCMA

各工具的來源平台、支援資料與封存結果分別看直接官方證據。

新 Backup and Restore

格式另立且需空目的地；不把傳統 XML 的結論套用。

證據不足

沒有直接來源時明示未知，不補成功圖示。

自我檢查與理由

自我檢查

二十列外部Task與整站XML還原，應分別評估什麼工具？

查看答案與理由

Task列可評估CSV欄位／值對應；整站Cloud備份另查Backup Manager與Import Jira Cloud，後者有覆寫風險。

自我檢查

只保留entities.xml與activeobjects.xml就代表附件已備份嗎？

查看答案與理由

不代表。媒體需選擇包含並核對相應檔案；automation等排除項另行規劃。

自我檢查

目的站有正在使用的DOC，能否直接匯入整站XML而保證保留DOC？

查看答案與理由

不能，XML匯入會覆寫目的資料庫；此要求衝突，應停止並更改遷移方案。

自我檢查

新Atlassian Backup and Restore要求哪兩種管理能力？

查看答案與理由

organization admin與app admin；仍需目的、資料處理授權和政策符合。

自我檢查

Copy Data的取消封存缺陷能否證明Cloud Backup Manager也如此？

查看答案與理由

不能。來源與工具不同。Cloud-origin Backup Manager archive旗標的直接官方證據仍未確立，應保留未知。

版本與實測範圍

完整原創內容；官方文件查核完成，租戶實測與網站呈現驗收尚未執行
