工作類型與方案：讓每種工作走對設定

看圖建立心像，用例子理解，再動手驗證。

官方目標 3.1 · 來源內容版 2026-10-05.complete-draft

先看懂這張圖

類型先進方案，再連到流程與畫面

新增工作類型只是定義分類，還要讓目標專案的work type scheme包含它。接著核對workflow、screen與欄位行為的對應；Epic與subtask描述階層，不是拿工作狀態取代成果分類。

用一個例子理解

合成LAB新增標準類型「LAB Audit Review」，使用審查流程與驗收畫面；DOC仍只用Task。LAB-51「合成登入稽核」可有兩筆subtask，Epic「教學登入改善」則統整較大的成果。

閱讀前提

先知道專案是一組工作的容器；工作項目是一筆可追蹤的工作。

不必先操作 Jira；本課先用「產品上市」案例建立模型。

先預測：新增類型就代表已在LAB可用？

比較預測與理由

不代表，還要在LAB的work type scheme與其他設定對應中配置。

先預測：subtask可當獨立跨專案成果嗎？

比較預測與理由

不能用這個練習推論。subtask隸屬父工作；較大成果用Epic與其支援的標準工作關係理解。

記住這個心像 類型是分類入口，scheme提供集合，再沿類型找到流程、畫面與欄位。

還原與收尾

  • 保留合成工作供觀察；復原LAB原scheme與對應。
  • 新類型不直接刪除；標註教學用途，若移除可用集合須先確認其合成工作對應。

沒有支援的環境：無權限或無教學站台：觀察／紙上替代

  • 依本章官方來源辨認設定物件；只看文件，不在自己的正式站台尋找替代操作。
  • 在紙上列出本章假資料、每一步預測與可見結果，再逐項核對checks答案。

驗證界線 此替代只能證明理解與推演；未建立或修改Jira，不能記為租戶操作驗證。

深入查閱

把圖中的關係對回設定

以下保留本節考點與細節。沿用圖中的角色、假資料與步驟，逐段確認原因。

先認識名詞

Work item / issue：一筆可被指派、更新與追蹤的工作，例如「修正付款失敗」。

Work type / issue type：工作項目的分類，例如 Bug、Task、Story；分類也可用來選擇流程與畫面。

Scheme：可重用的設定對照表。名稱相似的方案可能管不同事情。

Epic / standard work item / subtask：預設階層中，Epic 統整較大成果，標準工作承接可交付工作，subtask 拆分一筆標準工作的執行步驟。

先分清楚「這是什麼工作」和「工作做到哪裡」

想像一家虛構咖啡訂購服務正在加入預約取餐。團隊可能有「顧客可選取餐時間」Story、「跨日時間顯示錯誤」Bug，以及「準備內部說明」Task。它們都是工作項目；工作類型回答工作性質，Status 則回答目前是待辦、進行中還是完成。

如果把「待主管確認」新增成工作類型，只是為了表示等待階段，將很難一致地追蹤工作生命週期。先判斷差異是分類、流程階段、優先順序還是標籤，再選設定；不要因為名稱不同就新增一整套管理物件。

Scrum 和 Kanban 是管理工作流動的方式，並不把工作類型固定成互斥選擇。Scrum 團隊仍會處理 Bug；Kanban 團隊仍可使用 Epic 組織大型成果。

建立類型後，還要把它放進專案可用的類型方案

在公司管理型專案，Jira 管理者建立工作類型，並選擇它是 standard 還是 subtask。Standard 通常位於 Story 這一層；Subtask 需要父工作。不要把新類型取名「Epic 2」就當成新增了 Epic 階層。

進階階層設定屬另一個機制，本課不把付費方案的階層擴充當成基本步驟。

工作類型方案（issue type scheme）像一份專案可用分類清單。它決定可選類型、建立時預設類型，以及選項順序。建立「Audit Review」後，若沒有加入目標專案採用的方案，使用者仍可能無法在該專案建立此類型。

操作思路是先盤點既有類型與方案，再建立真正缺少的分類，將其放進新的或既有方案，最後確認方案套用到目標專案。現行管理入口為 Settings → Work items → Work types / Work type schemes；舊介面可能仍寫 Issues / Issue types。

方案可被多個專案共用，編輯前先查使用者清單。

合成情境：兩個產品團隊需要同樣的 Bug、Story、Task，適合共用方案。只有內控團隊需要 Audit Review 時，先比較建立專屬方案與修改共用方案的影響。複製方案讓清單分開，不代表把原有工作類型本體也複製成新的物件。

更名是改同一個分類的標籤，不是資料搬家

把共用的「Task」更名為「Operational task」，是在修改既有工作類型的名稱。原本使用這個類型的工作項目不會因此變成全新記錄；更名也不等於把它們搬到另一專案，或重新選擇流程。

影響範圍要沿「同一個類型物件被誰使用」追蹤。若多個公司管理型專案用到該類型，更名後使用者看到的名稱也會跟著改。只想改一個團隊的語意時，先評估是否真的需要獨立類型，避免把全站共用名稱當成本地文字。

更名前列出依賴名稱的 JQL、儲存篩選器、automation 條件、匯入範本、報表說明與第三方整合。這是變更檢查清單，不表示每個引用一定會壞，也不表示系統保證全部自動更新。管理物件的關聯與文字比對的依賴要分開驗證。

合成演練：如果網站流程以工作類型 ID 對應流程，但一份外部匯入表填著舊名稱，前者與後者的風險並不相同。更名後分別建立一筆測試工作與檢查匯入映射，才能確認使用者路徑與整合路徑都合理。

沿三條對應線找到流程、畫面與欄位行為

對公司管理型的一筆 Bug，先看專案使用哪些方案，再以工作類型找對應。工作流程方案（workflow scheme）決定 Bug 使用哪個 workflow；這條線管理狀態、轉換與規則。

畫面線有兩層：工作類型畫面方案（issue type screen scheme）將 Bug 對應至某個 screen scheme；screen scheme 再把 Create、Edit、View 操作對應到 screen。Screen 裡才列出欄位與分頁。

把欄位加進某個看似名稱正確的 screen，若對應鏈沒有走到它，使用者就不會看到預期結果。

傳統欄位設定線則由 field configuration scheme 將 Bug 對應到 field configuration，後者定義必填等欄位行為。這與 custom field context 的適用專案／類型、預設值／選項不同；第 3.2 課會把它們接起來。

找不到明確類型對應時，要檢查該方案的 Default 對應，而不是直接假設類型没有任何設定。新類型新增後，測試「Create 看什麼、Edit 能填什麼、走哪些狀態、有哪些必填要求」比單看清單更完整。

版本提醒：現行 Jira 正逐步把 field configuration 與 field configuration scheme 合為 field schemes。考綱沿用傳統兩層術語；若實際站台已顯示新名稱，先辨識使用哪種經驗，再按目前官方說明查看欄位可用性及必填設定。

不要硬找已不存在的舊選單。

Subtask 適合拆分一筆工作的執行，不適合冒充跨團隊成果

「預約取餐」Story 可以拆成「後端驗證取餐時段」「設計錯誤訊息」「補回歸測試」三個 subtasks。每個子工作能有自己的承辦者與狀態，父工作則保留完整交付目標。當你需要知道一筆工作內部誰在做什麼，這種拆分很合適。

若一份工作需要獨立排進不同團隊的產品計畫、跨多個交付目標長期追蹤，先考慮標準工作與 Epic 或一般連結。不要只因為文字上「包含」就一律建 subtask；階層關系會影響操作與彙總方式。

有 subtasks 不代表 Jira 必然在最後一個子工作完成時自動關閉父工作，也不代表父工作一定不能先完成。若需要「所有子工作完成才可結案」，要另外設計 workflow condition；若要主動更新父項目，則可能用 automation。前者是禁止不合規動作，後者是代做動作。

同樣的概念適用 Scrum 和 Kanban。Scrum 規劃時常以標準工作承接衝刺範圍，再拆執行；Kanban 可用子工作追蹤同一需求的協作步驟。board 的呈現方式並不改變 parent-child 的資料關係。

工時彙總要分清楚父工作自己的數字與加總數字

Time tracking 至少要分辨 Original estimate（原始估算）、Remaining estimate（剩餘估算）與 Time spent（已登錄工時）。父工作可以有自己的工時；子工作也可以各自記錄。查看彙總時，並不是把所有子工作的 worklog 複製到父工作。

合成資料：父工作自己已用 1 小時、剩餘 2 小時；子工作 A 已用 2 小時、剩餘 1 小時；子工作 B 已用 3 小時、剩餘 4 小時。若畫面選擇 Include subtasks，已用合計為 6 小時，剩餘合計為 7 小時。父工作本身仍是已用 1、剩餘 2；報表的 Σ 類欄位代表加總口徑。

不要把「父工作估算 7 小時」再加上已包含同一批工作內容的子工作 7 小時，誤以為真正有 14 小時工作。先約定父工作自己記錄的是額外協調時間還是整包工作的估計，並在閱讀報表時標明是否含子工作。

本段只談時間追蹤。Story points 是另一種估算尺度，不能因為工時會彙總，就推論所有 Scrum 報表的 Story points 都以相同方式加總；也不能把 Epic、父工作及 subtask 的各種報表口徑混為一談。

Epic 用來統整較大成果，也能支援公司管理型跨專案工作

Epic 適合描述需要多筆標準工作才能交付的成果，例如「推出預約取餐」。它可包含網站 Story、營運 Task 及修正該成果必要問題的 Bug。Subtask 則是在一筆標準工作之下分解執行，兩者處在不同層級。

在公司管理型情境，Epic 可以統整不同專案中的工作。合成例：WEB 專案負責預約畫面、OPS 專案負責門市作業，兩者連到同一個產品 Epic。要在 board 檢視完整成果，board filter 必須涵蓋需要的專案／工作，查看者也須能讀取相關工作。單有父子連結不會把其他專案全部資料搬進此專案。

Scrum 中 Epic 往往跨越多個 sprint；Kanban 中也能用 Epic 分組較大工作，實際卡片與 Epic panel 的顯示依 backlog 等設定而異。Epic 不是 sprint，也不要求一次完成所有成員工作。

目前官方文件建議新 JQL 用 parent 尋找 Epic 的子工作；舊 Epic Link 名稱仍常出現在教材與既有查詢。看到 parent 時先問父項目處於哪個層級，不能一律解讀為 subtask 的父工作。

跨管理型態及特定建立入口的行為，必須依當前功能確認，本課的跨專案題目明確限定 company-managed。

操作導讀：從父工作建立 subtask，從成果建立 Epic

Epic的子工作關係與標準工作底下的subtask是不同層級；Scrum與Kanban都可用Epic。

在文件查核的現行建立方式中，先開啟要拆分的父工作，選摘要下方 Add or create related work，再依管理型態選 Create subtask 或 Add a child work item，填摘要與必要欄位。

公司管理型若沒有選項，查 subtasks 是否啟用、類型是否在專案方案中，以及 Create work items 權限；團隊管理型則查專案是否已有 Subtask 類型。

Scrum 的公司管理型 backlog 可開 Epic panel，建立 Epic，再把標準工作放入相應成果；也可由全域 Create 選 Epic。

Kanban 也有這些用途，但該 board 的 backlog 和 Epic panel 要先啟用，不能因 panel 沒出現就斷言 Kanban 不支援 Epic。團隊管理型也可從全域 Create 或已啟用的 backlog 建立 Epic。

連到 Epic 的目前欄位常叫 Parent；較舊 Kanban 文件仍可能寫 Epic Link。從 Epic 移除一筆工作的父子關聯，不等於刪除那筆工作。若文件另談 Epic Status，要與一般 workflow Status 分開理解；

一個 Epic 的彙整狀態也不能證明所有子工作已經過合法完成轉換。

產品差異補充：不要把常見階層當成永久禁止清單

本課用 Epic → standard work item → subtask 當初學者的常見模型，幫助你分清成果、工作與執行拆分。這個模型不應被背成所有 Jira Cloud 版本都永遠禁止其他支援的關聯。

查核日的 Create a work item and a subtask 官方文件另明列：company-managed software 可使用 Add parent 將 subtask 直接連到 Epic 層。

相對地，team-managed 的 subtasks 官方文件仍明列 subtask 建在標準工作之下，不能直接置於 Epic 層之下。這是管理型態與現行產品差異，本課原創題目不以未交代版本的絕對禁止句設陷阱。

目前 team-managed Epic 文件也要求 parent 關係維持相同管理型態：company-managed 工作對 company-managed parent，team-managed 工作對 team-managed parent。跨專案與跨管理型態是兩個不同問題。

正式操作前仍需核對站台提供的入口和權限，不在正式資料上用試錯方式探索。

團隊管理型：先在專案內定義需要的工作類型

團隊管理型專案由專案管理者從 Space settings／Project settings → Work types／Issue types 管理本地工作類型。不要照抄公司管理型的全域 issue type scheme 教學路徑。

新增類型之後，還可以調整它的欄位與 workflow，讓 Bug 與一般 Task 蒐集不同資訊、走不同程序。

模板是起點：文件列出的初始 Kanban 類型是 Task，Scrum 是 Story，但這不是「Kanban 不能有 Story」或「Scrum 不能有 Task」的限制。先依團隊語言和需求選分類，再設計流程，避免為了模板名稱扭曲實際工作。

同名不代表同一個管理物件。兩個團隊管理型專案都有 Bug，不足以證明它們共用欄位、workflow 或工作類型本體。診斷時需要確認專案管理型態與物件來源；第 3.2 課再說明本地欄位與目前可重用的 Jira-admin shared fields。

目前 team-managed 官方文件限定自行建立的是 standard work type；若需要 Epic 或 Subtask 的特殊功能，應新增其建議的內建類型，不要另造一個同名的普通類型來假扮。名稱相同不會自動帶來階層、board 分組或進度功能。

紙上設定演練：Audit Review 的四項驗收

本節的具體步驟、假資料、預期結果與還原方式，已整理在動手驗證。請依該處的角色、方案與隔離條件選擇操作或紙上推演；未在你的租戶實測。

圖解與逐步理解

關係 1

專案使用類型方案；方案允許 Audit Review

關係 2

專案各自連到流程、畫面、欄位方案；以 Audit Review 查對應

關係 3

同一類型可在不同專案得到不同方案對應

自我檢查與理由

自我檢查

「Bug 已完成」包含哪兩種資訊？

查看答案與理由

Bug 是工作類型；已完成是流程狀態。兩者回答不同問題。

自我檢查

已建立 Audit Review，但專案的 Create 選單沒有它，第一個設定關聯要查哪裡？

查看答案與理由

查目標專案所用的工作類型方案是否包含 Audit Review，並確認自己查看的是正確專案與管理型態。

自我檢查

為什麼「只是改名字」仍要通知共用該類型的專案？

查看答案與理由

名稱屬於共用類型；其他專案的顯示及依名稱運作的查詢、教學或整合可能受影響。改名不是只改眼前這個專案。

自我檢查

想讓 Audit Review 用自己的 Create screen，應追哪條鏈？

查看答案與理由

專案 → 工作類型畫面方案 → Audit Review 對應的 screen scheme → Create 操作 → 目標 screen；不是只修改工作類型方案。

自我檢查

父工作有兩個未完成子工作，能否直接斷言父工作不能完成？

查看答案與理由

不能。要查該轉換是否有子工作阻擋條件或其他規則；階層本身不等於已設定阻擋。

自我檢查

在上述資料取消 Include subtasks 後，父工作自己的剩餘估算是多少？

查看答案與理由

2 小時。7 小時是含子工作彙總後的口徑，不能當成父工作本身欄位的原始值。

自我檢查

「推出預約取餐」跨兩個公司管理型專案，適合 Epic 還是把全部工作做成同一筆 Task 的 subtasks？

查看答案與理由

適合以 Epic 統整兩個專案的標準工作；subtasks 比較適合拆分同一筆標準工作的執行。board 顯示仍要檢查 filter 與權限。

自我檢查

Kanban backlog 沒有 Epic panel，下一步應先查什麼，而不是直接改成 Scrum？

查看答案與理由

確認該 board 是否已啟用 Kanban backlog 與 Epic panel，並查類型可用性與權限；Kanban 本身可使用 Epic。

自我檢查

一份舊筆記說「subtask 永遠不能直接連 Epic」，應如何處理？

查看答案與理由

先分辨管理型態與產品版本。現行官方文件已明列 company-managed software 的支援方式，而 team-managed 文件仍有直接 Epic 下的限制。

自我檢查

在團隊管理型專案只想為本團隊新增 Interview 類型，是否一定先建立全站類型方案？

查看答案與理由

不需要照公司管理型方案流程；從該專案的 Work types 設定著手，並確認自己的專案管理權限。
