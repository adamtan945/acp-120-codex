角色

  • 學員有Create、Edit與Browse。
方案與功能

先預測，再驗證

先預測：Create無欄位就代表全站沒這欄位？

比較預測與理由

不代表。context適用且Edit screen有它時可在建立後填。

先預測：hide when empty會清除原值嗎？

比較預測與理由

不會由此設定概念推論刪值；它控制閱讀呈現，原值需從資料/歷史核對。

記住這個心像 依類型找scheme、依操作找screen；閱讀位置再找layout。

還原與收尾

  • 恢復三screen欄位列表、scheme對應與LAB layout；恢復合成欄位原值。
  • 不刪除screens或欄位，先解除臨時關聯並保留教學樣本。

沒有支援的環境：無權限或無教學站台：觀察／紙上替代

  • 依本章官方來源辨認設定物件；只看文件，不在自己的正式站台尋找替代操作。
  • 在紙上列出本章假資料、每一步預測與可見結果，再逐項核對checks答案。

驗證界線 此替代只能證明理解與推演；未建立或修改Jira，不能記為租戶操作驗證。

深入查閱

把圖中的關係對回設定

以下保留本節考點與細節。沿用圖中的角色、假資料與步驟，逐段確認原因。

先認識名詞

Screen：一組欄位及分頁配置，供特定操作使用。

Screen scheme：把 Create、Edit、View 等操作對應到 screen 的表。

Issue type screen scheme：把工作類型對應到 screen scheme，再由專案使用。

Layout：工作項目詳細檢視中欄位的位置、順序與隱藏方式。

Transition screen：在執行某個 workflow 轉換時要求輸入的畫面；不同於一般 Create/Edit/View。

先用人的行為理解三種畫面

當使用者按 Create，問題是「建立這筆工作要蒐集哪些資訊？」按 Edit，問題是「後續可更新哪些資訊？」開啟工作項目詳細頁，問題是「閱讀者應先看到什麼？」這三個時機可能共用畫面，也可能有不同需求。

合成例：建立設備維修申請時只需要地點、設備類型、故障說明；後續編輯才補維修紀錄；閱讀畫面則把設備位置放在顯眼處。這不表示只要調整一個 layout，就會改到所有 Create 或轉換畫面。

Screen 是設定物件，使用者看到的完整介面還會受到欄位可用範圍、欄位行為與新版 work item view 影響。因此排錯時先記錄專案、工作類型、操作及使用者，才有辦法查對設定。

公司管理型 screen：建立、放欄位、分頁與順序

在公司管理型，Jira 管理者從 Settings → Work items → Screens 管理 screen。可建立或複製合適的 screen，加入欄位，依使用情境分頁及排序。新建 screen 只是準備可使用的表單配置；若未接到 scheme，目標專案不一定會採用它。

新增欄位前，先確認欄位存在、context 適用、相關欄位行為允許顯示。把欄位加進 screen 不能修好所有範圍問題；例如「設備序號」context 只適用 REPAIR，放到 SALES screen 也不能假設它在 SALES 的任何類型上都可用。

分頁適合把不同時機查閱的欄位整理成清楚群組，例如「申請資訊」「處理紀錄」。不要用大量分頁藏住建立時必填資訊；把重要的輸入放到使用者自然會經過的位置。這是表單設計建議，不是額外考試規定。

修改共用 screen 會影響所有走到這個 screen 的操作。只要為某類型加一欄，應先確認 screen 是否也被其他類型或專案使用；需要隔離時，複製正確層級並重新對應，不要假設改名就已解除共享。

兩層 screen scheme：先選類型，再選操作

讀取順序是「專案 → issue type screen scheme → 指定 work type 的 screen scheme → 目前操作的 screen」。每一層都是對照表，不能省略。

例子：REPAIR 的類型畫面方案把 Bug 對應 Bug screens，把 Task 對應 General screens。

Bug screens 中 Create 使用 Intake screen，Edit 使用 Diagnosis screen，Default 使用 Detail screen。建立 Bug 走 Intake；編輯 Bug 走 Diagnosis；

沒有明確設定 View 時，走 Default 的 Detail。

兩種 Default 也要分清楚。類型畫面方案的 Default 是「沒有明確類型對應時用哪個 screen scheme」；screen scheme 的 Default 是「沒有明確操作對應時用哪個 screen」。同一個字放在不同層，處理的是不同缺省情況。

Transition screen 是 workflow 上的另一路輸入點。例如「關閉」時要求 Resolution、檢查結果，不應只靠 Create/Edit/View 的 screen scheme 推論；要查該 transition 上是否要求顯示畫面。

Company-managed layout：閱讀順序與空值呈現

Layout 是詳細頁的閱讀配置。現行官方文件說明，其可用欄位源自該類型的 View screen；Jira 或專案管理者可以安排欄位順序、描述區、context fields、Hide when empty 與 Hidden fields。

Layout 不會憑空創造 field 或擴大 context。

Hide when empty 適合「有值才重要」的補充資訊。當欄位沒有值時，它可能收進 More fields；一旦有值，就出現在 Details。Hidden fields 則是這份 layout 不想顯示的欄位區。這些都是呈現選擇，不是存取權限。

合成例：故障描述放最前方，設備序號永遠顯示，維修廠商放 Hide when empty。尚未指派廠商時頁面乾淨；有廠商後資訊自然浮現。做調整後應各看一筆空值和一筆有值的測試工作，而不只檢查預覽。

公司管理型 layout 是專案層級；不能假設兩個專案共用 View screen 就一定共用同一份 layout。不過同一專案中使用相同 View screen 的工作類型，會作為一組配置 layout。如果想讓 Bug 與 Task 擁有獨立布局，先檢查這個共享來源。

個人釘選 context fields 也會影響某個人的閱讀視角。當甲、乙描述畫面不同，先問是否同專案同類型同操作、是否有個人偏好；不要立刻改全站 screen。

Team-managed：直接按工作類型安排欄位

團隊管理型從專案 Work types 選 Bug、Task 等類型，加入或拖動欄位，決定每種工作所需資訊。這裡不是先建立公司管理型 screen scheme；管理者應使用該管理型態提供的編輯介面。

合成例：Bug 放「重現步驟」「實際結果」，Task 放「預期交付物」。需要共用「作業區域」時，重用同一專案已建立的欄位，或依 3.2 的條件選 eligible admin-created shared field；不要為排版方便就建立一堆同名副本。

把某欄位從 work type 配置移出，與刪除欄位本體是不同決策。移除前仍應查資料、報表與 automation 的使用方式。若欄位在同專案多個類型共用，變更其名稱或選項可能一起影響其他類型；移動顯示位置則是另一種設定責任。

實際介面會隨欄位管理新版本更新。教學操作先確認 Space settings 的 Work types／Fields 顯示方式，再讀當前官方頁面；不要用舊截圖上的像素位置當必要知識。

欄位看不到時：用固定順序排查

順序是排查策略，不是假設Jira只有這四項限制。

第一步，界定症狀：誰在哪個專案、哪個 work type、哪個操作看不到哪個 field？若只有一位使用者的 Create 缺欄位，先檢查個人 Show fields／All fields；這比立刻修改共享 scheme 的風險低。

第二步，確認 field 身分與 context。名稱相同可能選錯欄位；context 不包含目前專案或類型時，要處理適用範圍。第三步，檢查 field configuration／field scheme 是否允許可用、是否隱藏或有必填要求。

第四步，沿兩層畫面方案找到真正的 Create/Edit/View screen，而不是只找名稱包含專案名的 screen。第五步，若是詳細頁問題，再檢查 layout 的 Hidden、Hide when empty、欄位空值以及共享 View screen。

最後，以原本受影響使用者及一筆合成資料重新驗證相同操作。若問題是權限或特殊欄位限制，按錯誤與官方規則另查；不把「多加到幾個 screen」當成萬用解法，也不把 screen 當成保護所有資料的防線。

自我檢查與理由

自我檢查

「在詳細頁看得到，但 Create 看不到」是否已證明資料被刪除？

查看答案與理由

沒有。Create 與 View 可能用不同 screen，也可能有個人的 Show fields 設定。先查操作別。

自我檢查

複製一份 screen 並加入欄位後，為什麼目標專案可能完全沒變？

查看答案與理由

因為專案的類型／操作方案仍指向舊 screen。需要確認完整的對應鏈。

自我檢查

Task 沒有明確 View 操作對應，應查哪個 Default？

查看答案與理由

先由 Task 找到它的 screen scheme，再查該 screen scheme 的 Default screen；不是直接用任意全站預設 screen。

自我檢查

在同一專案的 Task 和 Subtask 共用 View screen，調整其中一組 layout 時應預期什麼？

查看答案與理由

它們可能作為同一組一起配置，不能假設這次只影響眼前的 Task。先查共享 View screen。

自我檢查

Bug 與 Task 都需「作業區域」，是否應先建立兩個同名欄位？

查看答案與理由

先評估重用同一欄位；這有助一致搜尋與報表。工作類型的版面可以不同，不必因此複製資料定義。

自我檢查

所有人 Create 都缺 Area，但詳細頁有值且看得到。你會先查 layout 還是 Create 對應鏈？

查看答案與理由

先查 Create 對應的 screen、context 與欄位行為；既然詳細頁已能顯示，只改 View layout 未必對準問題。
