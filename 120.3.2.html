欄位與 context：讓資料可用、可填、可比較

看圖建立心像，用例子理解，再動手驗證。

官方目標 3.2 · 來源內容版 2026-10-05.complete-draft

先看懂這張圖

同一欄位，範圍與行為分開

欄位型別決定資料如何輸入，context決定它在哪些專案與類型適用；必填或Hidden等行為屬另一層。畫面能否看到也要另查。只想讓兩個團隊有不同選項，先評估同一欄位的不同context。

用一個例子理解

LAB與DOC合成Bug都用「LAB 測試環境」單選欄位：LAB選Sandbox／Mock，DOC選Draft／Demo，預設不同但不重疊。隱藏欄位只改呈現與配置，不拿來保護機密值。

已理解工作項目與工作類型；如果還不熟悉 scheme，先讀 3.1 的對應圖。

深入查閱

把圖中的關係對回設定

以下保留本節考點與細節。沿用圖中的角色、假資料與步驟，逐段確認原因。

先認識名詞

Field：工作項目中的一個資料位置，例如 Summary、Due date、風險等級。

Custom field：因組織需求另外建立的欄位；同名欄位可能有不同 ID，不能只憑名稱當成同一欄位。

Field type：欄位可接受與處理的資料種類，例如日期、數字、單選、文字。

Context：替同一自訂欄位定義適用專案／類型，以及依範圍不同的選項、預設值等。

Field configuration：傳統公司管理型模型中管理必填、隱藏、文字呈現等欄位行為的設定。

先問要作什麼決策，再決定是否需要新欄位

虛構客服改善團隊想知道哪個需求是「法規要求、營運改善或顧客體驗」。如果每個人把理由自由寫在 Description，有人寫營運、有人寫門市、有人成本，後續統計會很難對齊。此時有受控選項的「改善理由」欄位，能讓篩選、分組與 automation 使用一致資料。

反過來，若資料只是偶爾補充的一句背景，Description 或留言可能足夠。每新增一個欄位，就增加填寫、維護、命名與查詢的成本。這是教材的設計建議：先說明欄位將支援哪個實際決策，再決定欄位是否值得存在。

不要先建一批同名欄位來解決每個團隊的差異。先查是否已有語意相同且適用的欄位，確認管理來源、field type 與 context。兩個都叫「Area」的欄位如果 ID 不同，資料並不會自動合併，報表和 automation 也可能選錯。

建立自訂欄位：資料型態要符合使用方式

Field type 是資料契約。需要日期比較與到期條件，就選日期欄位；需要加總數量，就選數字；希望只有一種一致分類，就選 single select。單純把文字欄位命名為「日期」不會自動提供日期資料的特性。

單選與多選也不是只差輸入方便。單選適合「主要責任領域只有一個」，多選適合「可能涉及多個平台」。設計時先回答是否能同時成立、空值代表什麼，以及是否允許使用者自行新增值；不要讓答案在報表時才由管理者猜測。

在現行 Jira admin 的 Fields 頁建立欄位時，先選適合的類型，給具體名稱，再配置使用範圍及適用的填寫說明。官方現行建立頁明列：欄位建立後不能變更 field type。若需求改成不同資料結構，先規劃新欄位與資料轉換、驗證相依查詢和整合，不要承諾原欄位可無損切換型態。

合成例：「預估受影響門市數」用 Number；「預計恢復日期」用 Date；「影響面」若可同時選網站與門市，可用多選。別把這三者都塞進一個名為「其他」的文字欄位，再期待精準分析。

Context：重用同一欄位，也能讓不同範圍有合適選項

Context 像是欄位的使用範圍與內容規則。它能限定專案、工作類型，並針對範圍提供選項與預設值。Global context 表示廣泛適用；專案限定的 context 則讓同一欄位在某些專案使用特定設定。

合成例：共用的「作業區域」欄位，在 WEB 專案提供 Checkout、Account，在 STORE 專案提供 Counter、Kitchen。兩個 context 都使用同一個欄位，因此報表可依同一欄位查詢，但選項不必強迫全站使用一大串不相關清單。

規劃 context 時，列出「哪個專案 × 哪些類型 → 哪些選項 → 預設值」。避免給同一範圍含糊或重疊的規則；若畫面不允許某種重疊，要改規劃，而不是假設多個 context 的值會一起合併。檢查既有 global context 也很重要，否則只盯新 context 容易漏掉真正使用的範圍。

Context 名稱是管理者辨識用的，不等於使用者會看到另一個欄位名稱。設定預設值是在支援往後的資料輸入，不是已驗證的歷史資料回填方案。若要改既有值，另做資料影響分析與授權過的變更計畫。

Context 有效不等於欄位一定出現在每個操作畫面。公司管理型還要檢查 screen 與欄位行為；team-managed 要檢查該 work type 的欄位安排。這是第 3.3 課排錯流程的起點。

Required、Hidden 與 renderer 各管一件事

本lab不設全站必填，也不示範把敏感值藏在欄位。

Required 表示資料不能留空。把「風險說明」設為所有 Bug 的必填欄位，會讓受該設定影響的輸入操作必須提供值。應先確認使用者能在 Create screen 填它、現有資料是否有空值、整合是否會提交它；「設成必填」不是讓系統自動替大家寫答案。

Hidden 在傳統 field configuration 是欄位行為設定，可能讓欄位即使在 screen 上仍不呈現。從 screen 移除欄位，則是改某操作介面；layout 的 Hidden 或 Hide when empty 又是查看版面安排。三個層次都能造成「我看不到」，但修正位置不同。

Renderer 控制文字怎麼呈現。官方目前的 field configuration 文件提供 Wiki renderer／rich text 與 plain text 的選擇，用於支援該呈現方式的文字欄位。這不是把文字變成數字，也不是改欄位 context。

更改時要抽查含格式、連結與純文字的合成資料，確認學員和使用者仍看得懂。

在同一份 field configuration 上改 Required 或呈現行為，可能影響所有經 scheme 對應到這份設定的工作類型與專案。若只有 Audit Review 必須填證據，應評估以不同 field configuration 做類型映射，而不是把所有 Task 都一起設成必填。

如果需要「建立時可空白，轉為已核准時才必填」，先考慮 transition validator／Validate details 這種時間點規則。把欄位在一般 field configuration 全程設為 Required，可能比需求更嚴格；第 4.1 課會詳細比較。

「藏起來」不能當成敏感資料保護設計

Screen 或 layout 是呈現設定。把一個欄位從某個畫面移走，只能證明那個畫面不再提供原本的呈現；不能據此保證其他檢視、匯出、搜尋或整合都看不到資料。不要把「我在目前頁面看不到」當作已通過存取控制測試。

合成例：你想把人事評語從一般 Task 旁邊藏起來。正確的下一步是回到權限與工作項目可見性的設計，而不是承諾拖到 Hidden 就能安全保存機密。這裡說的是安全設計邊界，並不假裝本課已測試所有欄位的 API 行為。

如果遇到 Required 卻無可用輸入位置，先沿 context、field configuration、Create screen 檢查，不要單靠 UI 出不出現推論資料已有效。實際錯誤訊息與租戶配置才是定位依據。

團隊管理型：區分本地欄位與 Jira 管理者提供的共用欄位

團隊管理型專案可以在專案內新增本地欄位，再把它拖入所需 work type 的欄位配置。已在同一專案其他類型建立的欄位可重用；重用同一欄位時，它的名稱與選項是共用資料定義，不能假設每個 work type 都得到獨立副本。

本地新建欄位通常限定該 team-managed 專案，不可因為別的專案也取同名就當成跨專案共用。若組織需要一致欄位，現行文件另提供重用 Jira 管理者建立之 eligible shared field 的方式。

先查 Add fields 是否列出該欄位，以及來源是否為 Jira-admin 管理的欄位。

官方 context 文件明確指出：要在 team-managed 使用欄位，其 context 的 work type 選擇必須包含 Any work type。還要檢查相關專案範圍、支援的欄位種類與當前功能；不能把 Any work type 當成單一充分條件，保證任何欄位都出現在任何專案。

版本釐清：目前同一篇 team-managed fields 文件同時包含新版的管理者欄位重用步驟與較舊的不可跨管理型態共用句子。本課採「本地欄位保持本地；合資格的全域管理欄位按 context 與可用介面查核」的精確說法。

考題若問某個實際操作，本教材會明列欄位來源與條件，不出以矛盾敘述猜答案的題目。

現行介面補充：field schemes 合併兩層設定

April 2025 考綱使用 field configuration 與 field configuration scheme 兩個術語。現行官方文件說明 field schemes 正逐步取代兩者，把欄位可用性、不同類型的必填與說明整合在一處。

因此本課的概念學習要保留兩個問題：「哪個欄位可在這種工作使用」以及「欄位在此處有何行為」。如果你的租戶已切換 field schemes，以新介面查它；context 仍有選項與預設值的角色。不要把新 field scheme 與原本 field context 當作同義詞。

這是產品版本對照，不是自行宣告考綱已更新，也不要求你背誦尚未在租戶出現的按鈕。實際工作先核實介面版本，再參照當前官方頁面。

自我檢查與理由

自我檢查

兩個欄位都叫 Risk level，能否直接假設兩個專案共用同一組資料？

查看答案與理由

不能。先確認欄位 ID、管理來源與 context。同名只能說顯示文字相同。

自我檢查

若要比較哪筆工作的預計恢復日期較早，為什麼不只用文字欄位？

查看答案與理由

日期型態能以日期的意義處理值；自由文字容易有格式與排序歧義。先選型態，再決定 context 與畫面。

自我檢查

WEB 和 STORE 需要同一個分類欄位，但選項不同。先考慮兩個同名欄位，還是一欄位多個 context？

查看答案與理由

先評估重用同一欄位並以 context 分配選項與範圍；前提是語意與型態相同，且適用範圍沒有不清楚的重疊。

自我檢查

想在核准時要求 Approval note，但建立時不要求，是否應直接讓所有該類型的 Create 都必填？

查看答案與理由

不一定。需求只在轉換時生效，適合評估該轉換的 validator／Validate details，並提供可填寫欄位的適當輸入介面。

自我檢查

把薪資欄位從 View layout 隱藏，就能保證其他有專案權限的人不能讀取薪資嗎？

查看答案與理由

不能。這只是畫面呈現變更，沒有建立完整存取隔離；應另按敏感性設計權限與資料存放範圍。

自我檢查

一個 Jira-admin shared field 的 context 只選 Bug，是否已符合官方所述 team-managed 使用條件？

查看答案與理由

未符合。官方 context 文件要求 Any work type；調整後仍需確認專案範圍、支援型態與 Add fields 可用性。

自我檢查

站台只有 Field schemes 選單，是否表示 context 的預設值與選項功能也消失？

查看答案與理由

不是。新 field schemes 管可用性與行為，contexts 仍處理選項與預設值等內容設定。

版本與實測範圍
